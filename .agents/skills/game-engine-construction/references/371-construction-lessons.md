# 371 施工经验：性能、构建与导出

适用：施工长期未收敛、连续性能修复、构建/导出返工、平台测量阻塞。第1–5节为2026-10-13审计；第6节为2026-10-21导出经验。
这是历史案例及处理依据，不是新的产品合同、必跑测试清单或施工授权。
当前状态仍读49/54及本路登记的当前施工文档和范围；不要把本记录的历史结论冒认为后续版本结果。

## 1. 先审验收口径，再继续优化

确认：下层静态运行 harness 曾以快速 Trace probe 的 CPU/GPU 时间预算阻止三轮正式 Summary。
371-A §6.1规定快速反馈不授正式规模资格，§6.3规定 Trace 不证明正式预算。
最近一轮已修正 harness，并以高 Trace 成本、Summary预算边界和超预算拒绝的确定用例验证。

下次：核对上位合同、实际测量模式和真正失败断言。诊断成本超限不等于正式性能失败。
正确性、资源身份、样本完整性等独立准入仍须保持；不能以纠正错误门槛为理由降低正式预算。
历史上没执行的正式窗口记为未资格，不能倒推通过。

## 2. 短运行不代表短诊断

确认：CPU-Submit 的一次诊断，准备到Cook发布约598秒，Cook到build发布约1024秒，
Player实际约17.7秒；这两个发布区间不能全部称作纯编译耗时。
完整工程构建成为短诊断的主要成本，不能继续作为每次局部修复的内循环。

下次：先用已有报告定位，必要时做一次有界真实复现，再转已有owner的最小红例。
缩小输入用于定位，正式验收仍消费原冻结规模；不要新增一个同样昂贵的诊断工程。

## 3. 连续同类热点要整体定界

确认：多轮分别发现重复摘要/校验/绑定/加锁等问题；曾有10000 draw产生10002 graph passes。
这些修复有实际价值，但逐个暴露造成长期串行推进。局部操作次数下降和测试通过，
不能证明正式整帧改善；CPU-Submit记录明确保留了未改善的测量结果。

下次：同一症状跨窗口仍未关闭时，汇总现有分段和计数，确认已有效的复用，
按残余成本选择owner。避免重复建设已生效的缓存/bundle；嵌套时间不相加，Debug不直接比Release。

## 4. 构建失败要定位阶段和内存，而非盲重跑

确认：Unique-Submit曾遇LLVM内存不足/metadata mmap失败；Hot-Path后来两个BM-03尝试
均只产生Cook，未发布build或运行Player：先见Stack overflow，改变启动日志路径后的一次
有界重试明确报 `memory allocation of 632 bytes failed`。这些证据不能证明同一根因。
事后机器内存数据不足以确定失败时峰值，也不能直接认定某处clone或页文件是根因。

下次：保留首错和阶段边界；重试须带来有意义的因果或观测变化。
重复失败后转阶段/owner定位、峰值观测和最小复现，不反复付完整Cook/Build成本。
编译并发限制不能替代export/package内存验证；无Player时运行性能记pending。

## 5. 平台观测和整块进度必须收敛

确认：S1-D形成多份ETW/TDH/显示链子阶段记录，最终显示资格仍未闭合。
不能据此否定全部观测工作，也不能把源码子项通过等同于Windows显示链完成。
最新BM-02三Summary通过，但BM-03运行、其它资格以及G/H仍有缺项；Android已由用户延期。

下次：按整块退出结果报告完成/部分完成，明确剩余功能、测量、平台和工具消费。
权限失败、观测未关联、性能超预算是不同问题。不要以继续扩展解码器替代真实事件证据，
也不要为了宣布阶段完成擅自删改上位要求。三小时限制不是施工低效的原因解释。

## 6. Compiler导出输入与构建环境（2026-10-21）

确认：普通项目资源变化施工中，一次导出472.226秒后因修改了live project被
`game_project_compiler.execution_project_drifted`正确拒绝；另一次导出144.932秒因漏传
`CARGO_BUILD_JOBS=1`形成不同环境身份，额外执行engine build阶段116.865秒。
这是施工输入/调用方式不一致，不是已证明的缓存实现缺陷。两次外层时长包含必要准备与可复用产物，
不能全部当作可节省的编译时间；本轮全部导出789.422秒也不是纯Cargo时间。

正确流程沿现有owner执行，不新增runner或每次全量检查：

1. 先完成当前修改与便宜的owner验证，再生成/刷新该项目的prepare与request。
   从prepare到该次导出/验证终结，保持它消费的项目、引擎及工具输入不变。
   下一变体按“修改→刷新身份→导出结束→下一修改”串行；需要并行编辑时绑定独立项目副本，
   不能编辑运行中的同一源目录。生成器也可能覆盖输入，不在导出期间运行。
2. 371 Windows直接引擎开发继续走`rust/Invoke-EngineBuild.ps1`，固定SSD target、1.96.0、
   `--locked -j1`及当前合法profile。Compiler内部engine/project artifact缓存仍由原owner选择，
   外层`--target-dir`不等于迁移它的缓存。
3. 本路Compiler导出每次在启动producer的**同一个shell调用**中显式设置
   `$env:CARGO_BUILD_JOBS='1'`。外层Cargo的`-j1`不等于给Compiler传入这个环境值，
   上一次exec里的设置也不保证延续。若复用交互shell，结束后恢复该变量原值；不写全局环境。
   同时沿用确切工具链/target/profile/features及合法环境；不清除未知Rust flags来强行命中，
   Release不支持的flags由既有owner明确拒绝。
4. 使用已有artifact-build报告核对`enginePlayerIdentity`、`enginePlayerCacheStatus`、
   项目`cacheStatus`及真正Cargo步骤。源/环境未改却miss时先比较身份与配置；
   源确已变则支付一次必要构建，不清缓存、不反复完整导出验证猜测。
5. 遇到drift先保留失败、停止修改，按新revision重新prepare；保留旧有效缓存。
   终验前先查真实SDK/会话消费者：导入材质保留完整subAsset，3D prefab退场走既有typed命令，
   更新回调的创建回执与只读观察的实际存活不能混为一谈。不为这些消费者错误放宽引擎拒绝边界。

已验证的稳态范围：最终主项目导出27.529秒（内嵌build24.956秒），三个单项源修改
12.822/11.839/12.596秒且引擎缓存全部命中；不承诺所有规模或首次构建都达到此值。
证据及首红见[28记录](../../../../框架设计/引擎总体架构/阶段完成记录/2026-10-18-371-S2-Execution-Chain-Continuation/28-普通项目资源变化与安全退场.md)，
实际入口见[构建反馈](../../../../rust/BUILD_FEEDBACK.md)。本节替代每窗口重猜命令和重复全量构建，
不新增发布资格、测试矩阵或施工授权。
