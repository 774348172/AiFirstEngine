## 混合项目数据模型流程

> 当前解释：项目逻辑边界以 `195` / `196` 为准。本文中的 DSL / Graph / IR 表述应理解为 Feature / Gameplay Rule Asset 内的受限 RuleSlot 表达，不表示 IR 可以承载所有项目逻辑或复杂 UI 工作流。

本引擎不采用单一数据模型承载全部职责，而是采用混合模型：

```text
Spec-first + Scene View + ECS Runtime + Asset Database + Architecture Governance
```

不同层负责不同问题：

```text
Spec-first：解决 AI 理解、功能意图、长期维护和 Bug 追踪
Scene View：解决用户可视化编辑、场景查看、对象选择和 Inspector 操作
ECS Runtime：解决运行时执行、性能、确定性模拟和系统调度
Asset Database：解决资源依赖、平台变体、打包、热更和包体控制
Architecture Governance：解决复杂项目中的边界、依赖、耦合和维护风险
```

默认用户心智不是上述内部层级，而是：

```text
功能
场景与对象
资源
界面
玩法规则
测试结果
发布结果
```

没有编程基础的用户通过自然语言、Feature View、Scene、Inspector、Graph 和 Report 完成主流程。只有少量编程基础的用户可以展开结构化规则和受控项目代码视图，但不要求理解 Rust Runtime、ECS storage、Projection 或构建派生产物。

### 端到端流程

标准流程：

```text
用户用自然语言表达目标
  -> AI 生成可审查 Spec
  -> 引擎生成 Patch Plan
  -> 架构治理层阻止坏设计
  -> 验证层保证合法
  -> 编辑器展示 Scene / Graph / Inspector
  -> runtime 使用 Rust ECS / IR Interpreter / Rust AOT 执行
  -> Asset DB 管理资源和热更
  -> Build Pipeline 输出 PC / Android / iOS / Web
```

这意味着自然语言只是入口，不是最终工程真相。  
用户默认不直接管理代码，但项目也不是 AI 随便写代码。即使复杂功能最终由项目 Rust Module 承载，AI 生成或修改也必须在 Feature scope、Patch、Compile、Test 和 Report 约束内完成。项目由以下结构共同约束：

```text
Feature Spec
Patch Plan
DSL / Graph
Scene / Prefab
ECS Component Data
System Registry
Module Contract
Asset Database
Build Profile
Validation Report
Patch History
```

### 用户输入到项目变更

用户输入：

```text
给玩家加一个冲刺技能，冷却 2 秒，冲刺时有蓝色拖尾，手机端也要有按钮。
```

AI 首先生成 Feature Spec，而不是直接修改文件：

```text
功能意图
目标对象
玩法规则
输入方式
表现需求
平台需求
测试需求
```

用户确认后，引擎生成 Patch Plan：

```text
新增或修改 Component
新增或修改 DSL / Graph 规则
新增或修改输入绑定
新增或修改资源引用
新增或修改 UI
新增或修改测试
更新 Feature Ledger / Patch History
```

Patch Plan 必须先经过 Architecture Governance Layer：

```text
检查系统边界
检查跨层依赖
检查模块契约
检查热更等级
检查确定性风险
检查影响范围
检查测试覆盖缺口
```

再进入 Validation Layer：

```text
Schema Validation
Dependency Validation
IR / Rust AOT Compile Validation
Asset Validation
Render Validation
Platform Capability Validation
Performance Budget Validation
Automated Tests
Build Check
```

通过后，补丁以事务方式应用到项目。

### 代码与逻辑生产

AI 生成逻辑时，默认不应该直接生成大量自由代码。  
优先级应为：

```text
1. Spec：表达功能意图
2. Feature Asset / Feature Folder：聚合 ui / rules / logic / tests，作为 AI patch scope
3. AUI Document / Gameplay Rule Asset / Data Asset：表达项目可编辑资产
4. Rule Graph / DSL：表达 Gameplay Rule Asset 内的受限规则视图
5. Canonical Rule IR：表达受限 RuleSlot 的内部规范语义
6. IR Interpreter：用于编辑器预览、验证和热更覆盖
7. Rust AOT：用于正式发布的高性能规则执行
8. Rust：用于引擎核心、复杂项目模块、复杂 UI 工作流和高性能标准模块
```

默认路径：

```text
Natural Language
  -> Feature Spec
  -> Feature Asset / Feature Folder
  -> Project Assets
       AUI Document
       Gameplay Rule Asset
       Data Asset
       Scene / Prefab
  -> Rule Graph / DSL view
  -> Canonical Rule IR for Contract-bound RuleSlot
  -> IR Interpreter / Rust AOT
  -> ECS Runtime execution
```

编辑器预览、验证、热更覆盖和正式发布必须使用同一份受限 IR 语义。  
Lua 不作为核心逻辑路线，避免出现“开发期预览正常，但发布版 AOT 行为不同”的问题。

IR 的当前红线：

```text
IR 不是 Lua / Blueprint 式脚本语言。
IR 不承载完整战斗流程、行为树、技能状态机、A* 寻路、复杂 UI 交互、任意函数、while / 递归、任意数组 / map 编程。
复杂 gameplay 流程、复杂算法、复杂 UI 工作流默认进入 Rust Project Module / Rust Framework。
```

Rust 原生代码主要用于：

```text
ECS
Renderer
Physics
Audio
Input
Asset Loader
Platform Layer
Deterministic Simulation Module
Animation / Navigation 等标准模块
AUI Runtime Core
复杂 Project Rust Module
```

用户自然语言不应直接生成或修改 Rust 原生引擎代码。  
Rust 原生模块变更通常属于引擎版本升级，需要重新打包发布。

### 资源生产与 Asset DB

AI 生成资源后，资源不能只是被放入目录。  
所有资源必须进入 Asset Database，并记录：

```text
Asset ID
Asset Type
Source File
Import Settings
Dependencies
Platform Variants
Compression Format
Bundle Policy / Bundle Plan
Hash
Version
Hot Update Level
License / Source Metadata
```

Asset DB 负责：

```text
资源依赖检查
平台压缩
资源变体
Asset Bundle / Pak 构建
热更包生成
包体控制
资源回滚
```

### 编辑器展示

用户主要通过以下视图理解项目，而不是直接读底层代码：

```text
Scene View：查看场景和对象
Inspector：查看 Entity / Component / Asset 属性
Graph View：查看技能、状态机、行为树、材质图
Feature View：查看自然语言功能规格和历史
Patch Review：查看 AI 准备修改什么
Asset Browser：查看资源、依赖和热更信息
Build View：查看平台构建配置
Validation View：查看错误、风险和修复建议
```

编辑器展示的是面向用户的工程视图。  
runtime 执行时使用的是 Rust ECS / IR Interpreter / Rust AOT / Rust Native Module。  
二者通过 schema、DSL、Asset DB 和 Build Profile 保持一致。

### 打包与目标平台运行

Build Pipeline 读取：

```text
Project Schema
Scene / Prefab
ECS Component Data
DSL / IR
Asset Database
Module Manifest
Build Profile
Platform Capability
Quality Profile
Hot Update Manifest
```

输出目标：

```text
Windows：EXE + Rust runtime + data package + asset bundle + Rust AOT rule package / IR hotfix package
Android：APK / AAB + native runtime + mobile asset bundle + Rust AOT rule package / IR hotfix package
iOS：IPA + native runtime + iOS asset bundle + Rust AOT rule package / 受控 IR rule package
Web：HTML / JS / web runtime + web asset bundle + IR / Web backend rule package
```

运行时启动流程：

```text
启动平台壳
初始化 Rust runtime
初始化 Engine RHI 渲染后端
加载 Project Manifest
加载 Asset Bundle
加载 Scene / Prefab
构建 ECS World
加载 DSL / IR 规则
注册 Rust AOT 规则函数
加载 IR Interpreter 热更覆盖规则，可选
进入主循环
```

主循环：

```text
Input
  -> Logic Update
  -> ECS Systems
  -> Event Dispatch
  -> Animation / VFX / Audio
  -> Render Graph
  -> Present
```

手机端和电脑端共享项目数据模型，但使用不同平台配置：

```text
输入方式不同
资源压缩不同
Quality Profile 不同
性能预算不同
权限模型不同
热更策略不同
发布签名不同
```

例如：

```text
Windows 使用 desktop_high、键鼠 / 手柄输入、更高质量阴影和粒子数
Android / iOS 使用 mobile_high_60fps、触摸 UI、ASTC 贴图和更严格热更限制
```

### 最终原则

混合模型的核心原则：

```text
用户通过自然语言表达目标
AI 生成可审查工程计划
引擎用 schema / governance / validation 约束修改
编辑器用 Scene / Graph / Inspector 呈现结果
runtime 用 Rust ECS / IR Interpreter / Rust AOT 执行结果
Asset DB 管理资源、依赖、打包和热更
Build Pipeline 输出多平台可发布游戏
```

这个模型的目标不是让用户管理代码，而是让用户在不理解底层代码的情况下，仍然得到可维护、可验证、可发布的工程。
