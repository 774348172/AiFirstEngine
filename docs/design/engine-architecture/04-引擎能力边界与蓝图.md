# 引擎能力边界与蓝图

## 引擎能力边界

本引擎不应把所有可能的游戏系统都塞进核心。  
为了避免重蹈传统大型引擎“核心过厚、状态复杂、AI 难以掌控”的问题，架构采用：

```text
薄核心 + 标准模块 + 系统蓝图 / 游戏蓝图 + 项目层
```

判断某个能力是否应该进入引擎核心，需要看五个条件：

```text
1. 是否跨大多数游戏类型通用？
2. 是否是 AI 生成、验证、修复工程所必需？
3. 是否是平台发布和运行时基础所必需？
4. 如果放到项目层，是否会造成大量重复和不稳定？
5. 如果缺少它，零基础用户是否会被迫理解底层代码、工具链或平台细节？
```

只有满足这些条件的能力才进入 Core Engine。

### Core Engine 核心层

Core Engine 只放所有游戏都需要，且 AI / 验证 / 导出流程必须依赖的能力。

Core 应该提供：

```text
Entity / Component 基础
Scene / Prefab 基础
Transform
Asset Reference
Event 基础
Time / Update Loop
Input 抽象
Resource Loading
Renderer 接口
Audio 接口
Platform Abstraction
Serialization
Schema Validation
Patch Transaction
Undo / Redo / Diff
Build / Export 基础
Permission / Capability Model
Module System
```

Core 还必须提供 AI 原生工程能力：

```text
Feature Spec
Patch Plan
Validation Report
Context Scanner
Patch Validator
Auto Fix Loop
User Decision Gate
Patch History
Guided Workflow / Safe Default
Human-readable Diagnostic / Recovery
```

Core 不应该提供：

```text
具体游戏规则
具体网络模型
具体战斗体系
具体技能体系
具体经济体系
具体任务体系
具体自走棋规则
具体 RPG 背包规则
具体 FPS 武器规则
```

这些应放在模块、系统蓝图、游戏蓝图或项目层。

### Standard Modules 标准模块层

Standard Modules 是官方提供的通用能力，但项目可以选择是否启用。

示例：

```text
Rendering RHI Module
Physics Module
Animation Module
UI Module
Navigation Module
Particle / VFX Module
Ability Module
Buff Module
Dialogue Module
Inventory Module
Save / Load Module
Localization Module
Deterministic Simulation Module
Replay Module
Networking Module
```

这些模块不属于所有游戏必需能力，因此不进入 Core。

项目启用模块后，AI 才能调用该模块能力。例如：

```json
{
  "enabledModules": [
    "rendering_rhi",
    "ability",
    "buff",
    "grid_board",
    "deterministic_simulation"
  ]
}
```

这能让 AI 明确知道当前项目可用能力，避免调用未启用系统。

### System Blueprints / Game Blueprints 蓝图层

当前解释：

```text
本文早期使用的 System Blueprint / Game Blueprint 名称，
后续按 195 收敛为 System Contract / Game System Contract 理解。

它们不是 UE Blueprint 式节点脚本层，
不是用户日常编写脚本的地方，
而是系统结构、RuleSlot、Command、Event、Query、验证规则和测试的契约。
```

传统“整类游戏模板”容易限制用户想象力，也容易生成同质化项目。  
因此本引擎的模板体系应以系统级蓝图为主，而不是以固定游戏规则模板为主。

正式分为两类：

```text
System Blueprint：可组合玩法系统蓝图
Game Blueprint：多个 System Blueprint 的推荐组合
```

System Blueprint 是主力。当前应读作 System Contract。  
它不是写死具体玩法，而是定义某个通用游戏系统的：

```text
系统职责
数据结构
规则槽位
事件 / 命令 / 查询接口
验证规则
测试场景
热更策略
确定性策略
不同项目架构下的适配 Profile
```

示例：

```text
Shop Blueprint
Equipment Blueprint
Skill Blueprint
Buff Blueprint
Quest Blueprint
Inventory Blueprint
Dialogue Blueprint
Crafting Blueprint
Economy Blueprint
Turn Flow Blueprint
Combat Resolver Blueprint
UI Menu Blueprint
Reward Selection Blueprint
```

Game Blueprint 只是系统蓝图组合包，不是固定玩法。  
示例：

```text
Auto Chess Blueprint = Grid + Shop + Economy + Ability + Buff + Round Flow + Presentation Binding
ARPG Blueprint = Inventory + Equipment + Quest + Skill + Dialogue + Combat
Card Game Blueprint = Deck + Hand + Turn Flow + Card Effect + Resource
3D Shooter Blueprint = Input + Projectile + Health + Ability + VFX + Level Flow
```

Game Blueprint 的价值是提供工程骨架、默认规则槽位、默认测试和 AI 约束，而不是限制用户必须做某一种玩法。

当前边界：

```text
System Contract 不承载复杂脚本逻辑。
复杂系统流程和算法进入 Rust Project Module / Rust Framework。
可验证、可热更的公式、条件、权重进入 Contract-bound IR RuleSlot。
复杂功能默认通过 Feature Asset / Feature Folder 聚合 ui / rules / logic / tests。
```

### System Blueprint 示例：Shop

Shop Blueprint 不应该等同于“自走棋商店”。  
它应该提供一个可适配的商店系统骨架：

```text
Responsibility:
  商品展示、购买、刷新、库存、价格规则

Commands:
  BuyItem
  RefreshShop
  LockShop
  SellItem

Events:
  ShopRefreshed
  ItemPurchased
  PurchaseFailed
  ShopLocked

Queries:
  GetShopItems
  GetItemPrice
  CanPurchase

Rule Slots:
  price_rule
  refresh_rule
  stock_rule
  discount_rule
  rarity_weight_rule
```

验证规则示例：

```text
UI 只能通过 Query 读取商品
购买必须通过 Command
商店系统不能直接修改战斗状态
帧同步模式下随机必须来自 Deterministic RNG
热更只能在安全时机切换规则版本
```

### System Blueprint 适配 Profile

同一个系统蓝图必须能适配不同项目架构。

例如 Shop Blueprint 可以有：

```text
single_player
lockstep_deterministic
server_authoritative
offline_rpg
roguelike_run
live_ops_mobile
```

帧同步项目 Profile：

```text
determinism: required
randomSource: DeterministicRng
updateTiming: prepare_phase
networkSync: input_command_only
hotUpdate: between_matches_only
```

普通单机 RPG Profile：

```text
determinism: not_required
randomSource: LocalRandom
updateTiming: anytime
networkSync: none
hotUpdate: allowed
```

服务器权威项目 Profile：

```text
authority: server
clientCanPreview: true
clientCanCommitPurchase: false
networkSync: server_result
```

这让同一个商店系统可以服务不同项目，而不是把用户锁进固定模板。

### System Blueprint 和 Standard Module 的区别

边界定义：

```text
Standard Module = 引擎提供的运行时能力
System Blueprint / System Contract = 基于模块能力的可组合系统契约
Project System = 用户项目中实例化后的具体系统
```

例如：

```text
Inventory Module
  提供物品容器、堆叠、查询、事件、存档基础能力

Equipment Blueprint
  使用 Inventory Module + Attribute Module + UI Module
  定义装备系统结构、规则槽位、验证规则和适配 Profile

Project Equipment System
  当前游戏实际装备规则
  例如 6 个装备槽、装备有词条、战斗中不可更换
```

简化原则：

```text
模块负责能跑
蓝图负责怎么组织
项目负责具体规则
```

### 自走棋作为组合，而不是固定模板

自走棋不应作为不可变的完整玩法模板。  
它应该是一个 Game Blueprint，用来组合系统蓝图：

```text
Auto Chess Blueprint
  Grid Board Module
  Deterministic Simulation Module
  Ability Module
  Buff Module
  Presentation Binding Module
  Shop Blueprint，可选
  Economy Blueprint，可选
  Synergy Blueprint，可选
  Round Flow Blueprint，可选
  Reward Selection Blueprint，可选
```

用户可以替换其中任何系统：

```text
没有传统商店，改用地图事件获得单位
没有羁绊，改用地形共鸣
不是 8x8 棋盘，改用环形棋盘
战斗不是传统回合制，改用半实时规则
胜负不是血量结算，改用区域占领
```

蓝图只负责提供可维护工程结构和验证规则，不负责限制用户玩法想象力。
