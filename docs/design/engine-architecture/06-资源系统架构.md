# 资源系统架构

> 热更新当前实现基线见 `201-热更新方案收敛与当前实现基线.md`。本文中的资源热更、Delta Update、Full Content Update 和 Hot Update Manifest 是长期资源系统边界；当前代码只具备本地 RuntimeAssetIndex、Bundle mount、asset load/release 和资源索引 patch 原语。

## 当前归属说明：AssetProjection

本文档中历史出现的 `Render Asset Bridge / RenderAssetBridge`，从 `110-World-Projection-Adapter统一跨域同步规则.md` 起统一归属为：

```text
AssetProjection
```

含义：

```text
RuntimeAssetRef / RuntimeAssetLoader
  -> typed runtime resource binding
  -> GPU resource request / handle
```

它不是新的独立 Bridge 系统。后续新增模型、材质、贴图、音频等资源类型时，只新增对应 `AssetProjectionAdapter` 或 Type Loader，不新增新的 Bridge 名称。

## 资源系统架构

资源系统采用一步到位的 AI-native Asset Graph 方案。  
它综合传统编辑期 Asset Database、发布期 Cook / Bundle / Pak、以及 AI 原生资源治理能力。

核心目标：

```text
AI 可以生成资源
AI 可以修改资源
AI 可以删除资源
资源引用可追踪
资源生命周期可控
多平台资源可差异化
热更可验证、可回滚
用户不需要手动维护底层 Bundle，运行时加载 / 释放由项目策略驱动、引擎接口执行
```

### 资源对象范围

所有工程对象都算 Asset，包括：

```text
Texture
Material
Mesh / Model
Animation
Audio
VFX
UI Layout
Font
Prefab
Scene
DSL
IR Rule / Logic Asset
Build Profile
System Blueprint
Game Blueprint
```

原因：

```text
它们都需要 ID
都可能被引用
都可能被 AI 修改
都可能进入 Bundle
都可能参与热更
都需要版本、依赖和影响分析
```

### 核心概念

资源系统只保留以下核心概念：

```text
Asset
AssetSlot
AssetSet
AssetRef
Bundle
```

取消独立的 Asset Group 和 DynamicAssetSet 概念，统一由 AssetSet 承担。

定义：

```text
Asset = 单个资源对象
AssetSlot = 语义资源槽，用于给某个功能绑定一个资源或 AssetSet
AssetSet = 一组资源，按 usage 支持管理、构建、热更、预加载、运行时选择和动态选择
AssetRef = 编译后的底层稳定引用
Bundle = 构建器生成的运行时加载单位
```

### AssetSlot

AssetSlot 是用户和 AI 主要操作的资源绑定入口。  
用户可以在编辑器 UI 中选择具体资源，但项目文件中保存的是语义槽位绑定，而不是到处散落裸 AssetRef。

示例：

```json
{
  "slotId": "player_dash.trail_vfx",
  "type": "VFX",
  "current": "vfx_dash_trail_blue",
  "fallback": "vfx_dash_trail_default",
  "policy": {
    "requiresFallback": true,
    "allowAiReplace": true
  }
}
```

用户说：

```text
把冲刺拖尾换成红色闪电
```

AI 修改的是：

```text
AssetSlot: player_dash.trail_vfx
```

而不是在多个文件中直接替换具体资源 ID。

### AssetSet

AssetSet 是统一资源集合概念。  
通过 `usage` 区分用途。

推荐 usage：

```text
management
runtime_selection
dynamic_runtime_selection
bundle_hint
hot_update_scope
preload_scope
```

管理 / 构建 / 热更用 AssetSet：

```json
{
  "setId": "player_dash_assets",
  "type": "AssetSet",
  "usage": "management",
  "members": [
    "vfx_dash_trail",
    "mat_dash_blue",
    "tex_dash_noise",
    "audio_dash"
  ],
  "ownerFeature": "player_dash",
  "policy": {
    "hotUpdate": true,
    "bundleHint": "feature",
    "preload": "before_match",
    "release": "after_match"
  }
}
```

运行时静态选择集合：

```json
{
  "setId": "explosion_vfx_variants",
  "type": "AssetSet",
  "usage": "runtime_selection",
  "assetType": "VFX",
  "members": [
    "vfx_explosion_small",
    "vfx_explosion_medium",
    "vfx_explosion_large"
  ],
  "selection": {
    "mode": "weighted",
    "weights": {
      "vfx_explosion_small": 60,
      "vfx_explosion_medium": 30,
      "vfx_explosion_large": 10
    }
  }
}
```

运行时动态选择集合：

```json
{
  "setId": "fire_skill_vfx_dynamic",
  "type": "AssetSet",
  "usage": "dynamic_runtime_selection",
  "assetType": "VFX",
  "allowedTags": ["fire", "skill", "hit"],
  "allowedBundles": ["battle_vfx"],
  "maxCandidates": 20,
  "selectionRule": "by_skill_element"
}
```

AssetSet 的意义：

```text
AssetSet 负责表达哪些资源属于一组
Bundle 负责表达这些资源最终怎么被打包加载
```

正式边界：

```text
AssetSet 是语义集合
Bundle 是构建产物
```

AssetSet 面向用户、AI 和项目规则。  
它回答的是：

```text
这些资源属于哪个功能
这些资源是否一起预加载
这些资源是否属于同一个热更范围
这些资源是否允许运行时选择
这些资源是否有移动端降级策略
```

Bundle 面向 Build Graph 和 Runtime。  
它回答的是：

```text
这些资源最终被打进哪个运行时包
这个包依赖哪些其它包
这个包什么时候下载 / mount / unmount
这个包在目标平台上的体积和 hash 是多少
```

用户和 AI 不直接维护底层 Bundle。  
用户只配置 AssetSet / Bundle Policy / Hot Update Policy 等策略；Build Graph 根据 Asset Graph、依赖关系、平台 Profile 和策略自动生成 Bundle Plan。

### Bundle Plan v1 落地规则

当前代码已经实现最小 Bundle Plan v1。  
它是 Build Graph 根据 Asset Database / Asset Report / Asset Dependency Graph 自动生成的解释型构建产物。

当前产物：

```text
bundle-plan.json
```

正式边界：

```text
用户不手写 bundle-plan.json
AI 不直接把资源塞进某个最终 Bundle
AI 只能修改项目资源引用、AssetSet、Bundle Policy 或 Build Profile
Build Graph 根据这些输入重新生成 Bundle Plan
```

Bundle Plan v1 当前采用保守的 scene-first 分包策略：

```text
startup bundle = active scene 及其非共享依赖
scene-* bundle = 其它 scene 及其非共享依赖
shared bundle = 被多个 scene / prefab 闭包引用的共享资源
loose bundle = 未被 scene 闭包引用的资源
```

每个 Bundle 必须解释：

```text
bundleId
reason
assets
dependsOn
states
estimatedSize
warnings
```

缺失资源在 v1 中记录为 missing / warning，不直接让 Bundle Plan 生成失败。  
是否阻止最终构建由后续 Build Profile / Platform Profile / Release Policy 决定。

Bundle 依赖由 Asset 依赖自动推导：

```text
Asset A 在 Bundle X
Asset A dependsOn Asset B
Asset B 在 Bundle Y
=> Bundle X dependsOn Bundle Y
```

Bundle Dependency Graph 必须保持确定性输出，方便 AI 比对、回归测试和构建问题定位。  
如果发现 Bundle 依赖循环，Build Graph 必须报告明确错误或警告，并给出可解释路径。

### Bundle Build v1 落地规则

当前代码已经实现最小 Bundle Build v1。  
它把 `bundle-plan.json` 转换成可被 Runtime Asset Loader 消费的朴素目录产物。

当前产物：

```text
bundles/
  startup/
    bundle.json
    assets/<assetId>/<sourceFile>
  shared/
    bundle.json
  scene-*/
    bundle.json
  loose/
    bundle.json

bundle-manifest.json
```

Bundle Build v1 的职责：

```text
读取 Bundle Plan
按 Bundle 复制 current 状态的源资源
为 missing / modified / copy-failed 资源保留可解释记录
生成每个 Bundle 的 bundle.json
生成全局 bundle-manifest.json
保留 Bundle dependsOn 关系
记录每个资源的 buildState / bundlePath / hash / size
```

Bundle Build v1 暂不负责：

```text
压缩包格式
平台纹理 / 模型 / 音频 Cook
Shader Variant 编译
远程 CDN 上传
热更差异包生成
运行时 mount / unmount 具体策略
```

原因：

```text
先稳定 Asset DB -> Bundle Plan -> Bundle Manifest 的可解释链路。
等资源图、运行时加载接口和平台 Profile 稳定后，再引入真实 Cook / Pack / Compress。
```

AI 查错时应优先读取：

```text
asset-database.json
asset-report.json
bundle-plan.json
bundle-manifest.json
bundles/<bundleId>/bundle.json
```

它们共同回答：

```text
资源是否存在
资源为什么进入这个 Bundle
资源是否被复制
资源复制到了哪里
Bundle 依赖哪些其它 Bundle
缺失或失败的资源在哪里
```

### Runtime Asset Loader v1 落地规则

当前代码已经实现最小 Runtime Asset Loader v1。  
它读取 `bundle-manifest.json`，在运行时建立 Bundle / Asset 索引，并提供最小资源解析能力。

引擎侧提供：

```text
mountBundle(bundleId)
unloadBundle(bundleId)
resolveAsset(assetId)
listMountedBundles()
report()
```

项目侧负责：

```text
什么时候 preload
什么时候 release
切场景前后加载哪些 Bundle
哪些 Bundle 跨场景常驻
战斗中是否允许替换资源
热更完成后何时重新 mount
```

正式边界：

```text
资源加载接口由引擎控制。
加载时机和释放时机由项目策略控制。
项目逻辑可以请求加载 / 卸载，但不能依赖底层 Bundle 文件名作为长期语义。
```

Runtime Asset Loader v1 的行为：

```text
mountBundle 默认递归 mount dependsOn
resolveAsset 只能解析已 mount Bundle 中 buildState=copied 的资源
unloadBundle 默认阻止卸载仍被其它 mounted Bundle 依赖的 Bundle
missing / not-copied / copy-failed 资源返回可解释错误
```

当前导出的桌面 runtime 启动时会尝试读取：

```text
build-manifest.json
bundle-manifest.json
```

如果存在 Bundle Manifest，runtime 会 mount `startup` Bundle，并把 mounted bundle 状态显示在运行时状态栏。  
如果这些文件不存在，runtime 仍回退到直接读取 `game-project.json`，保证开发期和旧导出产物可继续运行。

### Render Asset Bridge v1 落地规则

当前代码已经实现最小 Render Asset Bridge v1。  
它负责把 ECS / Runtime Package 中的 `mesh.assetRef / materialRef / textureRef` 解析成 RenderExtract / RenderCommand / RenderSceneState 可理解的资源绑定状态。旧文档中的 `RenderSnapshot.renderables[]` 只代表过渡 MVP 的输入形态，不再是正式渲染主链路。

引擎侧提供：

```text
resolveRenderableAsset(renderable, runtimeAssetLoader)
resolveRenderableAssetBindings(renderable, runtimeAssetLoader)
createRenderAssetBridgeReport(renderables, runtimeAssetLoader)
```

其中：

```text
resolveRenderableAsset = 兼容旧模型引用，只返回 model binding
resolveRenderableAssetBindings = 返回同一个 renderable 的 model / material / texture 多资源绑定
```

当前绑定状态：

```text
none = renderable 没有资源引用，直接使用 primitive
resolved = assetRef 已通过 RuntimeAssetLoader 解析为 bundle 内 URL
fallback = assetRef 存在，但资源未 mount / missing / not-copied / copy-failed
```

当前桌面 runtime 行为：

```text
如果 model assetRef resolved，记录 URL 和绑定状态
如果 materialRef / textureRef resolved，记录 URL 和绑定状态
如果尚未接入真实 model loader，仍使用 primitive / fallbackPrimitive 显示
如果 model assetRef fallback，model 降级为 cube
状态栏显示 RenderAssets resolved/total
```

正式边界：

```text
Render Asset Bridge 只负责“资源引用 -> 渲染资源绑定状态”。
它不负责 glTF 解码、Texture 解码、GPU 上传、材质实例化。
这些属于后续 Runtime Asset Type Loader / Render Asset Backend。
```

Bevy 的 AssetServer / Handle / Assets<T> 对本项目有参考价值，但只作为内部机制参考：

```text
AssetServer 负责异步加载和路径到资源句柄的解析。
Handle 用于运行时引用资源。
Assets<T> 保存已加载资源实例。
AssetProcessor / Loader 负责导入和转换。
```

本项目不照搬 Bevy 用户模型：

```text
AssetRef / AssetSlot / AssetSet / Bundle 仍是项目和 AI 面向的正式模型。
Handle 只属于 Runtime 内部资源句柄，不进入项目源数据。
引用计数不能替代大型项目的 preload / release / 常驻 / 热更策略。
资源生命周期仍由项目策略表达，引擎执行受控加载、卸载、依赖和内存预算。
```

这样设计的原因：

```text
AI 和用户能看到资源到底是 resolved、fallback 还是 none。
渲染失败不会变成黑盒。
后续接入 glTF / Texture / Material 时，不需要改变 Asset DB / Bundle / Loader 的边界。
```

### Runtime Asset Type Loader v1 落地规则

当前代码已经实现最小 Runtime Asset Type Loader v1。  
它位于 Render Asset Bridge 之后，负责把 `resolved` 的资源绑定转换成类型化 runtime resource 记录。

当前支持的类型：

```text
model
texture
material
audio
unknown
```

当前能力：

```text
loadFromBinding(binding, expectedType)
unload(assetId, type)
get(assetId, type)
report()
```

当前加载模式：

```text
decodeMode = url-only
```

也就是说，v1 只确认：

```text
资源绑定已经 resolved
资源类型符合预期
资源 URL 可交给后续解码器
资源进入 runtime cache
错误和 warning 可解释
```

v1 不负责：

```text
解析 glTF
上传 GPU Buffer
创建 Texture
创建 Material Instance
创建 Audio Buffer
管理 GPU 生命周期
```

这些属于后续具体 Asset Type Decoder / Render Backend。  
但后续解码器必须继续沿用 Type Loader 的 cache / report / error 边界，避免每个资源类型各自实现一套不可追踪的加载规则。

当前桌面 runtime 行为：

```text
每帧从 Render Asset Bridge 获取绑定
resolved 绑定进入 Runtime Asset Type Loader
状态栏显示 TypedAssets ready/cached
渲染仍使用 primitive / fallbackPrimitive
```

这样做的原因：

```text
先稳定资源类型加载的可解释状态和缓存边界。
真实模型、贴图、材质解码以后接入时，不需要改变项目数据、Bundle Manifest 或 Render Asset Bridge。
```

### Model Decoder v1 落地规则

当前代码已经实现最小 Model Decoder v1。  
它位于 Runtime Asset Type Loader 之后，只消费 `type=model` 的 typed runtime resource。

当前能力：

```text
decode(modelTypedAsset)
unload(assetId)
get(assetId)
report()
```

当前解码模式：

```text
decodeMode = metadata-only
```

v1 只负责：

```text
确认 typed asset 是 model
识别 glb / gltf / unknown 格式
建立 model decoder cache
输出 ready / failed 统计
保留 warning / error
给 runtime 状态栏和 AI Debug 提供模型解码状态
```

v1 不负责：

```text
调用 Three.js GLTFLoader
解析 glTF 场景树
创建 Mesh / SkinnedMesh / Animation
上传 GPU Buffer / Texture
替换当前 primitive 渲染
```

后续真实模型加载必须挂在 Model Decoder 后面，而不是绕过：

```text
RuntimeAssetLoader
RenderAssetBridge
RuntimeAssetTypeLoader
ModelDecoder
```

这样可以保证：

```text
资源缺失可解释
类型错误可解释
格式错误可解释
解码失败可回退
AI 能定位模型加载失败发生在哪一层
```

当前桌面 runtime 行为：

```text
resolved model binding -> Runtime Asset Type Loader
typed model asset -> Model Decoder
状态栏显示 Models ready/cached
渲染仍使用 primitive / fallbackPrimitive
```

### Material Runtime Backend v1 落地规则

当前代码已经实现最小 Material Runtime Backend v1。  
它是桌面 runtime 的 Three.js 适配层，挂在 Texture Decoder / Material Decoder 之后。

当前链路：

```text
RenderAssetBridge.resolved(material / texture)
  -> RuntimeAssetTypeLoader(material / texture)
  -> MaterialDecoder(metadata-only)
  -> TextureDecoder(metadata-only)
  -> MaterialRuntimeBackend.createMaterial
  -> Three.js MeshStandardMaterial / TextureLoader
```

当前能力：

```text
根据 Mesh 基础参数创建 MeshStandardMaterial
如果 texture 已经 resolved + decoded，则用 TextureLoader 加载 map
缓存 Texture 和 Material
输出 Material Runtime report
失败时保留基础颜色材质，不阻断渲染
```

正式边界：

```text
Material Runtime Backend 可以依赖具体渲染库。
Asset DB / Bundle Plan / Runtime Asset Loader / Render Asset Bridge / Type Loader / Decoder 不依赖具体渲染库。
```

这意味着：

```text
当前桌面版可以用 Three.js MeshStandardMaterial / TextureLoader。
未来 Native RHI / Rust 渲染后端必须实现同样的 Material Runtime Backend 契约和 report / fallback 语义。
```

v1 暂不负责：

```text
Material Graph
Shader IR
Render Graph Pass 绑定
真实 GPU Pipeline 管理
平台压缩贴图加载
PBR 参数完整解析
```

### Audio Runtime Backend v1 落地规则

当前代码已经实现最小 Audio Runtime Backend v1。  
它是桌面 runtime 的浏览器 / Electron 适配层，挂在 Audio Decoder 之后。

当前链路：

```text
Scene / Prefab Entity Audio Component
  -> Asset DB dependency
  -> Bundle Plan / Bundle Build
  -> RuntimeAssetLoader.resolveAsset(audio)
  -> RuntimeAssetTypeLoader(audio)
  -> AudioDecoder(metadata-only)
  -> AudioRuntimeBackend.applySource
  -> HTMLAudioElement
```

当前能力：

```text
读取 Audio Component 的 clipRef / volume / loop / autoplay
加载并缓存 HTMLAudioElement
支持 autoplay source 的一次性触发
输出 Audio Runtime report
失败或浏览器阻止播放时记录 warning / error
```

正式边界：

```text
Audio Component 是纯数据。
Audio Decoder 只识别资源格式和缓存 decoded resource。
Audio Runtime Backend 可以依赖当前平台 API。
项目侧决定什么时候播放、停止、切换、预加载和释放。
引擎侧提供受控接口、缓存、report 和 fallback 语义。
```

v1 暂不负责：

```text
Audio Graph
Mixer / Bus
3D spatialization
DSP
streaming music
ducking
platform audio cook
complex gameplay trigger rules
```

### Mesh 资源引用规则

当前 Mesh Component 支持三类资源引用：

```text
assetRef / assetId = model
materialRef = material
textureRef = texture
```

Asset Database 必须把这三类引用都纳入依赖图：

```text
Scene / Prefab Entity Mesh
  -> model asset
  -> material asset
  -> texture asset
```

正式边界：

```text
Entity / Mesh 只声明“使用哪些资源”。
Asset DB 负责依赖图。
Bundle Plan / Bundle Build 负责把依赖资源带进构建产物。
Runtime Asset Loader 负责解析 mounted bundle 中的 URL。
Render Asset Bridge 负责生成 model / material / texture binding。
Type Loader 和各 Decoder 负责缓存、识别和报告。
真实渲染应用由后续 Render Backend / Material System 执行。
```

### Audio Component 资源引用规则

当前 Audio Component 支持：

```text
clipRef = audio
volume = 0..1
loop = boolean
spatial = boolean
autoplay = boolean
```

Asset Database 必须把 Audio Component 的 `clipRef` 纳入依赖图：

```text
Scene / Prefab Entity Audio
  -> audio asset
```

正式边界：

```text
Audio Component 只声明“这个 Entity 使用哪个音频资源以及基础播放参数”。
Audio Component 不包含 play / stop / update 等行为方法。
具体播放时机属于项目规则、System Blueprint、IR Rule 或 Runtime Command。
运行时播放机制由 Audio Runtime Backend 执行。
```

### Model Runtime Backend v1 落地规则

当前代码已经实现最小 Model Runtime Backend v1。  
它是桌面 runtime 的 Three.js 适配层，挂在 Model Decoder 之后。

当前链路：

```text
RenderAssetBridge.resolved(model)
  -> RuntimeAssetTypeLoader(model)
  -> ModelDecoder(metadata-only)
  -> ModelRuntimeBackend.instantiateModel
  -> Three.js GLTFLoader
```

当前桌面 runtime 使用：

```text
game-runtime/model-runtime-backend.js
three/build/three.module.js
three/examples/jsm/loaders/GLTFLoader.js
three/examples/jsm/utils/BufferGeometryUtils.js
three/examples/jsm/utils/SkeletonUtils.js
```

`index.html` 通过 import map 把 ESM `three` 映射到本地文件：

```text
"three" -> "./three/build/three.module.js"
```

正式边界：

```text
Model Runtime Backend 可以依赖具体渲染库。
Asset DB / Bundle Plan / Runtime Asset Loader / Render Asset Bridge / Model Decoder 不依赖具体渲染库。
```

这意味着：

```text
当前桌面版可以用 Three.js GLTFLoader
未来 Native RHI / Rust 渲染后端必须实现同样的 Model Runtime Backend 契约
AI 查错时仍能定位到模型加载失败发生在 Model Runtime Backend，而不是资源系统其它层
```

失败策略：

```text
GLTFLoader 加载成功 -> 缓存 glTF scene，渲染时 clone
GLTFLoader 加载失败 -> 保留 primitive / fallbackPrimitive
错误进入 Model Runtime Backend report()
```

### AssetRef

AssetRef 是编译后的底层稳定引用。  
用户和 AI 不应在项目逻辑中散落式生成裸 AssetRef。

AssetRef 用于：

```text
编译后的 Scene / Prefab
编译后的 DSL / IR
Bundle Manifest
Runtime Asset Loading
```

AssetRef 的长期保存结构：

```json
{
  "assetId": "player_ship_texture",
  "guid": "8c2f2a6d-7c4d-4e10-89fd-4eae5f16f8a1",
  "type": "Texture"
}
```

带子资源时使用 `subAsset`：

```json
{
  "assetId": "enemy_model",
  "guid": "2a1f...",
  "type": "Mesh",
  "subAsset": {
    "id": "mesh_body",
    "kind": "Mesh"
  }
}
```

AssetRef 不保存：

```text
sourcePath
bundlePath
runtime handle
cooked asset path
GPU resource id
```

解析规则：

```text
优先用 guid 定位资源
assetId 用于 AI / 用户可读性和一致性校验
type 用于验证层快速检查
guid 找到但 assetId 不一致 -> warning
assetId 找到但 guid 不一致 -> conflict
二者都找不到 -> missing
```

AssetRef 不直接等于具体平台文件。  
运行时通过 Active Asset Version 解析：

```text
AssetRef(assetId="vfx_dash", guid="...")
  -> Active Asset Version
  -> vfx_dash@2026.06.15.android
  -> Bundle
  -> Cooked Asset
```

资源 meta 由引擎自动生成：

```text
用户拖入 / 复制资源文件 -> 自动生成 asset.meta.json
外部工具或 SVN 拉取资源 -> 扫描后自动生成缺失 meta
AI 生成资源文件 -> 生成资源文件后自动生成 meta
```

meta 是技术身份，不是设计决策。  
真正需要用户确认的是资源是否绑定到 AssetSlot、是否替换旧资源、是否删除引用。

### Source / Cooked / Runtime 三层

资源必须分三层：

```text
Source Asset
Cooked Asset
Runtime Instance
```

Source Asset：

```text
png / psd / gltf / fbx / wav / mp3 / effect graph / material graph / ui layout
```

用于编辑器和 AI 修改。

Cooked Asset：

```text
Windows: BC7 texture, desktop mesh, desktop shader variant
Android: ASTC texture, mobile mesh, mobile shader variant
iOS: ASTC texture, Metal-friendly variant
Web: BasisU / WebP / WebGPU-friendly asset
```

用于运行时加载。

Runtime Instance：

```text
ECS Entity
VFX Instance
UI Node
Audio Instance
Material Instance
Prefab Instance
```

Runtime Instance 可以销毁，但不等于删除资源。

### Bundle 规则

Bundle 是构建器根据 Asset Graph 和 Bundle Policy 生成的运行时加载单位。  
Bundle 不强制按资源类型划分。
Bundle 不作为用户主要编辑对象，也不作为项目源资源的组织方式。

区分：

```text
Asset = 单个资源对象
AssetSet = 资源集合
Bundle = 构建产物
```

正式规则：

```text
AssetSet 是语义集合，Bundle 是构建产物。
Bundle 分包由 Build Graph 自动生成。
用户只配置策略，不手动管理底层包。
AI 只能建议 Bundle Policy，不能直接手写最终 Bundle 内容。
```

一个 Bundle 可以对应：

```text
单个 Asset
一个 AssetSet
多个 AssetSet
一个场景
一个功能
一个热更差异包
```

不建议默认每个资源一个 Bundle。  
可以支持 single asset bundle，但主要用于：

```text
小热更
远程独立下载
用户生成内容
高频替换资源
```

Bundle Policy 可以由项目声明，AI 可以建议，构建器最终生成实际 Bundle：

```text
按功能聚合
按场景聚合
按热更频率聚合
按平台聚合
共享资源抽 common
大资源单独 bundle
高频热更资源单独 bundle
```

构建器必须输出 Bundle Build Report，说明：

```text
每个 Bundle 包含哪些 Asset
为什么这样分包
依赖哪些 Bundle
体积是多少
哪些资源导致体积增长
是否有循环依赖
是否有跨包异常依赖
```

### Bundle 依赖

Bundle 依赖采用类似 Unity AssetBundle 的依赖方式。  
资源依赖发生在 Asset 层：

```text
VFX -> Texture / Material
Material -> Texture / Shader
Prefab -> Mesh / Material / Animation / Audio / VFX
Scene -> Prefab / UI / Audio
DSL -> AssetSlot / AssetSet
IR Rule -> schema / config / rule backend manifest
```

Bundle 依赖由构建器根据 Asset 依赖自动推导：

```text
如果 Asset A 在 Bundle X
Asset A 依赖 Asset B
Asset B 在 Bundle Y
则 Bundle X dependsOn Bundle Y
```

如果 A 和 B 在同一个 Bundle：

```text
没有跨 Bundle 依赖
```

Bundle Dependency Graph 必须是有向无环图。  
循环依赖不能运行时解决，必须构建阶段处理。

遇到循环依赖时，构建器应报错并给出修复建议：

```text
合并循环 Bundle
抽出 common Bundle
移动共享 Asset
拆分 AssetSet
禁止某类反向引用
```

AI 可以根据构建错误生成修复 Patch Plan。

### 多平台 Cook

同一个 Asset ID 可以生成多个平台变体：

```text
Asset ID: tex_dash_trail
  source: dash_trail.png
  windows: BC7 2048
  android: ASTC 6x6 1024
  ios: ASTC 6x6 1024
  web: BasisU 1024
```

Cook Profile 示例：

```json
{
  "profile": "android_mobile",
  "texture": {
    "format": "ASTC_6x6",
    "maxSize": 1024
  },
  "mesh": {
    "generateLod": true,
    "maxBones": 64
  },
  "audio": {
    "format": "ogg",
    "quality": "medium"
  },
  "vfx": {
    "particleBudget": 400

```

流程是：

```text
修改 Source Asset / Graph
  -> 重新 Cook 受影响平台
  -> 更新 Bundle
  -> 更新 Hot Update Manifest
```

```text
项目定义版本域和版本策略

```

### 资源生命周期

资源加载接口由引擎控制，加载策略由项目侧控制，实际加载和卸载由 Runtime 执行。

正式边界：

```text
项目侧决定什么时候加载
项目侧决定加载什么语义资源
项目侧决定什么时候请求卸载
项目侧决定是否跨场景常驻
项目侧决定资源替换什么时候允许生效

引擎侧提供受控资源接口
引擎侧解析 AssetRef
引擎侧根据 Manifest 找到真实 Bundle
引擎侧执行 Bundle mount / unmount
引擎侧执行 Asset load / unload
引擎侧执行引用计数、依赖加载、安全点和内存预算
```

项目逻辑允许调用资源加载接口，但只能调用受控接口。  
项目逻辑不能直接依赖底层 Bundle 文件名、Bundle 路径或平台包内部结构。

允许：

```text
AssetModule.preloadAssetSet("battle_core_assets")
AssetModule.loadAsset("ui_shop_panel")
AssetModule.releaseScope("match")
AssetModule.keepAlive("lobby_common_assets")
AssetModule.requestRemoteAssetSet("skin_pack_01")
```

不允许：

```text
loadBundle("bundle_006")
unloadBundle("android_battle_vfx_20260617.bundle")
openFile("Project/Build/android/bundles/xxx")
freeTextureMemory(...)
```

原因：

```text
Bundle 是 Build Graph 自动生成的构建产物，不是稳定项目语义。
同一个 AssetSet 在不同平台、不同版本、不同热更策略下可能被拆分、合并或抽 common Bundle。
项目逻辑如果直接依赖 Bundle 名称，后期分包优化和热更会变得不可维护。
```

引擎负责机制：

```text
preload 执行
release 执行
引用计数
Bundle mount / unmount
Asset load / unload
Runtime Instance tracking
内存预算检查
安全点切换
热更版本切换
加载失败 fallback
```

项目负责策略：

```text
哪些资源什么时候 preload
什么时候 release
能不能常驻
能不能战斗中替换
哪些资源进入首包
哪些资源远程下载
哪些资源只能安全点替换
哪些资源必须 app 重启后替换
```

推荐策略值：

```text
preload:
  app_start
  project_load
  scene_enter
  before_match
  ui_open
  on_demand
  background_stream

release:
  never
  scene_exit
  after_match
  ui_close
  ref_count_zero
  memory_pressure
  manual_safe_point

scope:
  global
  session
  scene
  match
  ui_screen
  feature
  temporary

replace:
  immediate
  safe_point
  scene_reload
  between_matches
  requires_app_update
```

运行时加载流程：

```text
Load Project Manifest
Load Bundle Manifest
Resolve Active Asset Version
Resolve AssetRef
Mount Bundle
Load Asset Dependencies
Create Runtime Asset
Instantiate Runtime Object
Track Instance References
Despawn Runtime Object
Release Asset Handle
Garbage Collect Unused Assets
Unmount Bundle
```

运行时资源加载的核心原则：

```text
项目说“我要这些资源，在这个时机，用到这个范围”。
引擎决定“这些资源在哪些 Bundle 里，怎么加载，怎么释放，怎么保证安全”。
```

### 编辑器删除与运行时卸载

编辑器删除和运行时删除必须分开。

编辑器删除：

```text
允许物理删除资源
必须先做引用影响分析
必须弹出影响范围提示
必须让用户确认
必须更新 Asset DB / Asset Graph
必须记录 Patch History
```

如果资源被引用，用户必须选择：

```text
删除并移除引用
替换为其它资源
仅标记为不再使用
取消删除
```

运行时不做项目资源删除。  
运行时只做：

```text
Despawn Runtime Instance
Release Asset Handle
Unload Runtime Asset
Free GPU / Audio / CPU memory
Unmount Bundle
Evict cached cooked asset
```

运行时最多清理下载的热更缓存或旧版本 Bundle，这属于缓存清理，不是项目源资源删除。

### 热更方式

对用户只暴露两种热更方式：

```text
Delta Update：只热更修改的
Full Content Update：热更所有
```

Delta Update 对用户表示“只热更修改的”，但内部不是简单单文件替换。  
引擎实际处理：

```text
changed assets
affected bundles
updated manifest
dependency compatibility check
hash / signature
rollback metadata
```

Full Content Update 用于：

```text
大版本
赛季更新
资源结构变化
重大依赖重排
清理历史包
```

热更包必须包含：

```text
manifest
changed bundles
removed / deprecated assets
migration，可选
hash
signature
dependency list
safe apply time
rollback target
```

帧同步项目必须锁定：

```text
rulesetVersion
logicHash
assetHash
bundleHash
```

一局战斗中不能替换：

```text
project_rules.ir / rust_aot_rule_module
battle asset bundle
deterministic config
```

### Asset Reference Report v1

当前代码已经实现 `asset-reference-report.v1`。  
它是 Asset Report 内的派生报告，用来回答 AI 和用户最常问的资源维护问题：

```text
这个资源被谁引用？
为什么被引用？
来自哪个 Scene / Prefab / Entity / Component / Field？
删除或替换它会影响哪些地方？
```

Asset Reference Report 的规则：

```text
AI 不手写 referencedBy / reverseReferences
引擎从 Scene / Prefab / Entity Component 自动提取 AssetRef
输出必须确定性排序，方便 AI diff、回归测试和构建审计
每条引用必须包含 ownerAssetId、ownerType、entityId、component、field、reason、path
```

当前 v1 已覆盖：

```text
Mesh.assetRef -> model
Mesh.materialRef -> material
Mesh.textureRef -> texture
Audio.clipRef -> audio
PrefabInstance.prefab -> prefab
Scene Entity 引用
Prefab Root 引用
```

这条报告只是真相的索引，不是项目源数据。  
用户、AI、Patch Plan 修改的是项目资源绑定；Asset Reference Report 由引擎重新生成。

### Asset Impact Report v1

当前代码已经实现 `asset-impact-report.v1`。  
它建立在 Asset Reference Report 之上，用于资源删除 / 替换前的影响分析。

资源删除或替换的规则：

```text
AI 可以提出删除 / 替换资源意图
引擎必须先生成 Asset Impact Report
如果资源仍被引用，删除必须标记为 high risk
如果替换资源类型不一致，替换必须标记为 high risk
同类型替换可以进入后续 Patch Plan，但仍需要用户确认
影响报告必须列出所有受影响的 Scene / Prefab / Entity / Component / Field
```

Asset Impact Report 输出：

```text
action: delete / replace
assetId
replacementAssetId，可选
referenceCount
references
severity: none / low / medium / high
canAutoApply
requiresUserApproval
warnings
```

这条规则的目标不是增加用户负担，而是避免 AI 在不知道影响范围的情况下删除或替换资源。  
用户看到的是“会影响哪里、风险多高、是否允许继续”，不是底层引用图细节。

### Asset Patch Operation v1

当前代码已经把资源删除 / 替换接入 Patch Plan 验证链路：

```text
replaceAsset
deleteAsset
```

`replaceAsset` 规则：

```text
只能替换同类型 Asset
如果原资源存在引用，必须带 approvedImpact=true
approvedImpact 代表用户或上层流程已经看过 Asset Impact Report
replaceAsset 会更新 Scene Entity 和 Prefab Root 中的相关 AssetRef
removeOriginal=true 时会在引用替换后移除旧 Asset 记录
```

`deleteAsset` 规则：

```text
不能删除仍被引用的 Asset
approvedImpact 不能绕过悬空引用
要删除被引用资源，必须先通过 replaceAsset 或 updateEntity 移除所有引用
deleteAsset 只删除项目 Asset 记录，不直接物理删除硬盘源文件
物理删除仍属于编辑器资源管理 / 导入系统，并且必须弹出影响提示
```

这条规则把危险操作收束到 Patch 验证层。  
AI 可以提出资源修改意图，但不能直接制造悬空引用，也不能用用户授权绕过项目一致性。

项目定义 Policy Metadata：

```text
allowAiEdit
allowAiReplace
allowAiDelete
requiresUserApproval
hotUpdatePolicy
fallbackPolicy
```

禁止：

```text
字符串路径资源引用
未声明动态加载
AI 手写 referencedBy
AI 绕过影响分析直接删除资源
```

## Scene Unload 与资源释放边界

Scene unload 不等于资源 release。

正式规则：

```text
Scene unload 只负责销毁该 SceneInstance 拥有的 Entity / Component。
资源是否 release 由项目侧 Loading Rule / Scene Lifecycle 决定。
Runtime Asset Loader 只提供 release(handle) / ref_count / diagnostics 能力。
```

原因：

```text
同一资源可能被多个 Scene / Prefab / Persistent Entity 共用。
下一场景可能继续使用同一资源。
跨场景常驻对象可能仍持有资源。
热更和资源替换需要独立的安全生效点。
```

因此 Scene 生命周期和资源生命周期的关系是：

```text
SceneUnloadRequested
  -> Runtime 销毁 Entity / Component
  -> Loading Rule 判断哪些 AssetSet / handle 可以 release
  -> AssetRuntime 执行 release / unload
  -> RuntimeAssetReport 记录 loaded / released / retained / missing
```

SceneLifecyclePlan 中的资源字段：

```text
preload:
  表示生命周期进入前需要准备的 AssetSet / AssetRef。

release:
  表示生命周期退出后可以释放的 AssetSet / handle / scope。
```

资源系统边界：

```text
SceneLifecyclePlan 只能声明 preload / release 意图。
Runtime Asset Loader 负责真实 load / release。
SceneLifecyclePlan 不能直接调用 IO / decode / GPU upload。
SceneLifecyclePlan 不能用 release 绕过引用计数和资源安全检查。
SceneLifecyclePlan 不是新的资源规则系统。
```

## Runtime 资源加载同步 / 异步 / 分阶段规则

正式规则：

```text
Runtime Asset Loading 必须同时支持同步加载和异步加载。
异步加载是运行时默认推荐路径。
同步加载允许存在，但只能用于启动、编辑器、加载界面、小型必需资源和测试。
分阶段加载不是引擎底层固定模式，而是项目侧 Loading Rule / Scene Lifecycle 的编排。
```

成熟引擎参考：

```text
Unity:
  Resources.Load 是同步加载。
  Resources.LoadAsync 返回 ResourceRequest / AsyncOperation。
  AsyncOperation 提供 isDone / progress / priority / allowSceneActivation。
  场景激活控制属于加载流程编排，不代表所有资源都必须由底层 loader 固定分阶段。

Unreal:
  FStreamableManager 提供 RequestAsyncLoad / RequestSyncLoad / LoadSynchronous。
  FStreamableHandle 提供 WaitUntilComplete / CancelHandle / GetProgress / StartStalledHandle。
  UAssetManager 提供 LoadPrimaryAsset(s) / PreloadPrimaryAssets / UnloadPrimaryAsset(s) / ChangeBundleStateForPrimaryAssets。
  大项目主要用 async handle 和 AssetManager 编排加载、预加载、卸载和 bundle state。

Bevy:
  AssetServer / Handle<T> / LoadState / AssetEvent 形成异步 handle + 状态查询模型。
  适合 Rust / ECS，但同步加载不是主要表达方式。
```

我们的边界：

```text
Engine 负责能力：
  AssetRef 解析
  Active Asset Version 解析
  Bundle / Runtime Package 访问
  依赖解析
  IO / 解码 / GPU upload 调度
  资源缓存
  引用计数
  release / unload 执行
  progress / status / cancel / priority
  diagnostics / trace / report

Project 负责策略：
  什么时候 preload
  什么时候等待加载完成
  什么时候 instantiate
  什么时候 activate scene
  什么时候 release 旧资源
  加载界面如何表现
  是否拆成多个加载阶段
```

第一版 Runtime Asset Loading API 形态：

```text
load_sync(asset_ref) -> LoadedAssetHandle / Error
load_async(asset_ref | asset_set, options) -> AssetLoadRequest

poll_load(request_id) -> AssetLoadStatus
await_load(request_id) -> AssetLoadResult
cancel_load(request_id)
release(handle)
is_loaded(asset_ref)
get_loaded(asset_ref)
```

`AssetLoadRequest` 最小字段：

```text
request_id
asset_refs
status: Queued | Loading | Ready | Failed | Cancelled
progress
priority
loaded_handles
diagnostics
trace_source
```

同步加载限制：

```text
允许：
  启动期
  编辑器工具
  加载界面
  小型必需资源
  测试场景

不推荐：
  战斗中
  每帧逻辑里
  高频系统里
  大资源加载
```

如果运行时热路径调用 `load_sync`，引擎不直接禁止，但必须写入 RuntimeTrace / Console / Build Report warning。

项目侧分阶段示例：

```text
LoadingRule: EnterBattleScene

step 1: load_async(BattleSceneAssetSet)
step 2: wait until Ready
step 3: instantiate scene entities
step 4: activate scene
step 5: release previous scene assets
```

AI 生成规则：

```text
AI 默认生成项目侧 LoadPlan / Lifecycle Rule。
AI 不直接生成底层 IO / 解码 / GPU upload 调用。
AI 必须能从 AssetLoadRequest diagnostics 解释：
  哪个资源被请求
  为什么失败
  缺少哪个依赖
  哪个 bundle / cooked asset 未 mount
  是否在热路径使用了同步加载
  哪些资源已 loaded / released
```

## RuntimeAssetIndex / CookedAsset / RuntimeAssetHandle 规则

正式规则：

```text
Runtime 不读取完整编辑器 Asset DB。
Build / Cook 阶段生成 RuntimeAssetIndex。
RuntimeAssetIndex 是 Runtime 资源加载的唯一索引真相。
AssetRef 通过 RuntimeAssetIndex 解析到 cookedAssetId / bundleId / loader_kind。
依赖在 Build 阶段展开，Runtime 只校验和执行。
RuntimeAssetHandle 是运行时资源句柄，不包含 sourcePath / editor object / Asset DB 细节。
第一版只支持本地 Runtime Package + 本地 cooked asset + 本地 bundle mount。
diagnostics 必须能解释 resolve / dependency / bundle / read / decode / gpu_upload / apply 失败。
```

成熟引擎参考：

```text
Unity:
  Editor AssetDatabase 和 Player / AssetBundle runtime data 分离。
  BuildPipeline.BuildAssetBundles 生成 AssetBundleManifest。
  AssetBundleManifest 提供 bundle hash、direct dependencies、all dependencies。
  AssetBundle 提供 LoadFromFile / LoadFromFileAsync / LoadAsset / LoadAssetAsync / Unload。
  BuildReport / PackedAssetInfo 记录 packed object、type、sourceAssetGUID、sourceAssetPath 等构建期追踪信息。

Unreal:
  FSoftObjectPath / FPrimaryAssetId 进入 AssetRegistry / AssetManager。
  AssetRegistry 提供 GetAssetByObjectPath / TryGetAssetPackageData / GetDependencies / GetReferencers。
  AssetManager 使用 FStreamableManager / FStreamableHandle 执行 async/sync load。
  PackageStore 保存 PackageName、PackageId、ImportedPackageIds、SoftPackageReferences、HasCookError。
  IoStore TOC 保存 chunk id、offset/length、compression blocks、chunk metadata。

结论：
  成熟引擎都不会让 Runtime 直接消费完整编辑器 Asset DB。
  Runtime 消费 cooked 后的精简索引、包表、依赖表和加载句柄。
```

```text

  -> bundleId
```

```text

guid 找到但 type 不一致 -> type_mismatch
bundle 未 mount -> bundle_not_mounted
cooked 文件缺失 -> cooked_asset_missing
依赖不存在 -> dependency_missing
解码失败 -> decode_failed
GPU 上传失败 -> gpu_upload_failed
```


规则：

```text
RuntimeAssetHandle 不保存 sourcePath。
RuntimeAssetHandle 不保存 editor object。
RuntimeAssetHandle 不保存完整 Asset DB 数据。
generation 用于防止释放后的旧 handle 被误用。
runtime_resource_id 指向 decoded resource / gpu resource / audio buffer 等运行时资源。
```

依赖规则：

```text
Build Graph 负责扫描 Scene / Prefab / Material / DSL / IR / AssetSet。
Build Graph 生成 dependency_table 和 bundle/cooked 归属。
Runtime 不重新推导业务依赖。
Runtime 只按 RuntimeAssetIndex 的 dependencies 执行加载顺序和校验。
```

Runtime 仍必须做最低限度校验：

```text
依赖是否存在
依赖 bundle 是否 mounted
依赖 cooked asset 是否可读
依赖类型是否匹配
循环依赖是否已经在 build 阶段被禁止或标记
```
