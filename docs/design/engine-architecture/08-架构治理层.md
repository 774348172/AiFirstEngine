# 架构治理层

> 当前解释：根据 `195-Gameplay-Rule-Asset-Rust-Framework-IR-Redline-and-AUI-Logic-Boundary方案.md`，本文中的 Architecture Governance Layer 只按 AI Patch / Validation 流程能力理解，不新增 Logic Ownership Router / Architecture Guard 作为运行时层或新的项目架构层。复杂功能默认通过 Feature Asset / Feature Folder 聚合 `ui / rules / logic / tests`，Feature Folder 只作为编辑期组织、AI patch scope 和测试报告聚合。

## 架构治理层

Architecture Governance Layer 属于 Core Engine 提供的 AI Patch / Validation 治理能力。  
但它不是具体玩法功能实现层，也不是 runtime 层或新的项目架构层，而是 AI 原生引擎的规则流程能力。

它默认服务没有编程基础和只有少量编程基础的用户。治理结果必须转译成玩法影响、可见风险和可执行选择；依赖图、耦合指标和 Contract 细节只作为高级证据，不要求用户理解后才能继续。

它的定位是：

```text
规则框架
流程引擎
验证机制
决策门
```

它不应该变成：

```text
战斗系统
装备系统
技能系统
羁绊系统
任务系统
经济系统
商店系统
怪物 AI 系统
```

这些具体玩法能力仍然属于 Standard Module、Official Template 或 Project Layer。

### 为什么它属于引擎层

自然语言开发复杂项目时，用户通常只关心功能结果，不会主动处理：

```text
高耦合 / 低内聚
系统职责边界
跨层依赖
循环依赖
模块 API 边界
确定性风险
热更新边界
测试覆盖
长期维护成本
```

如果这些问题完全交给 AI 自由处理，项目越复杂，后期越容易出现：

```text
新功能引入大量隐藏 bug
系统之间互相直接调用
逻辑层和表现层混在一起
同类逻辑被复制到多个系统
Bug 无法定位到原始需求
修复一个问题破坏多个旧功能
```

因此架构治理能力必须由引擎核心提供。  
它解决的是 AI 原生工程的通用 Patch / Validation 问题，而不是某个具体游戏项目的业务问题，也不改变 RuntimePackage、ECS、AUI、Project Rule 或 Feature Folder 的运行时链路。

### 它在 Core 中提供什么

Core Engine 在 AI Patch / Validation 流程中提供治理框架和执行机制：

```text
System Registry
Module Contract Reader
Project Policy Reader
Dependency Graph Builder
Impact Analyzer
Layer Boundary Checker
Coupling Checker
Contract Checker
Architecture Rule Engine
Patch Risk Scorer
Scenario Test Mapper
Validation Reporter
Decision Gate
```

这些能力负责：

```text
读取系统声明
读取模块契约
读取模板策略
读取项目架构规则
生成依赖图
分析本次改动影响范围
检查跨层访问
检查循环依赖
检查模块边界
检查系统职责冲突
检查热更等级
检查确定性风险
检查测试覆盖缺口
输出架构验证报告
阻止高风险 Patch
要求用户确认架构性变更
```

### 它不负责什么

Architecture Governance Layer 不负责实现具体业务逻辑：

```text
伤害怎么算
商店怎么刷新
棋子怎么移动
技能怎么触发
装备怎么掉落
任务怎么完成
经验怎么升级
怪物怎么决策
```

这些由模块、模板和项目提供。

正式边界：

```text
引擎提供 Patch / Validation 治理执行器
模块声明能力边界
模板声明默认架构策略
项目声明业务约束
AI 在这些规则内生成 Patch Plan
不新增运行时 Logic Ownership Router / Architecture Guard
```

### 规则来源

Architecture Governance Layer 执行的规则来自四个层级：

```text
Core Architecture Rules
Module Contracts
Template Policies
Project Policies
```

Core Architecture Rules 是所有项目通用的底线规则：

```text
AI 不能直接改底层引擎实现
Patch 必须可审查
Patch 必须可回滚
项目层不能绕过模块公开 API
逻辑层不能依赖表现层的运行结果
热更新内容必须声明热更等级
帧同步逻辑必须通过确定性检查
```

Module Contracts 由标准模块声明：

```text
模块公开哪些 command / event / query
模块禁止哪些访问
模块是否确定性
模块是否支持热更
模块允许被哪些层调用
模块修改后需要跑哪些测试
```

Blueprint Policies 由系统蓝图或游戏蓝图提供默认架构规则。  
例如 Auto Chess Game Blueprint 可以声明：

```text
战斗逻辑层不能依赖 UI 层
表现层只能监听战斗事件
战斗中不能直接访问商店刷新逻辑
所有随机数必须来自 Deterministic RNG
技能、装备、羁绊不能各自复制伤害结算逻辑
```

Project Policies 由具体项目声明业务约束：

```text
本项目有哪些自定义系统
哪些系统可以互相访问
哪些系统只能通过事件通信
哪些功能允许热更
哪些逻辑必须保持帧同步确定性
哪些玩法规则属于项目核心规则
```

### 在 AI 流程中的位置

Architecture Governance Layer 位于 Patch Plan Draft 和 Validation Layer 之间，只影响 Patch 是否能进入后续验证 / 事务应用：

```text
User Intent
  -> Project Context Scan
  -> Feature Spec
  -> Patch Plan Draft
  -> Architecture Governance
  -> Validation Layer
  -> Patch Transaction
  -> Test / Build Check
  -> Result Report
```

Validation Layer 主要检查底层合法性：

```text
schema 是否合法
资源是否存在
脚本是否能编译
shader 是否能编译
平台是否支持
性能预算是否满足
```

Architecture Governance Layer 主要检查工程结构：

```text
这个改法是否破坏架构
这个系统是否职责过多
这个依赖是否不该存在
这个功能是否应该抽象成新系统
这个 Patch 是否让后续维护变难
```

### 示例

用户输入：

```text
让技能命中敌人后影响商店折扣
```

AI 不应直接让 CombatSystem 调用 ShopSystem。  
Architecture Governance Layer 应该检查：

```text
SkillSystem 是否允许直接依赖 ShopSystem
Combat Layer 是否允许访问 Economy Layer
这个 Patch 是否新增跨层依赖
是否存在更低耦合方案
是否需要新增事件或中间规则系统
```

如果当前方案违反规则，应输出治理报告：

```text
当前方案风险：CombatSystem 直接依赖 ShopSystem，违反层级规则。
建议方案：
1. CombatSystem 只发出 SkillHitEvent
2. ShopDiscountRule 监听 SkillHitEvent
3. EconomySystem 根据规则修改折扣
4. 新增对应场景测试和回归测试
```

用户不需要理解设计模式，但引擎必须把不可维护的方案挡在 Patch 应用之前。

### 最终定义

Architecture Governance Layer 的正式定义：

```text
Architecture Governance Layer 是 Core Engine 中的 AI 原生工程治理流程能力。
它不承载具体玩法实现，不新增运行时或项目架构层，只负责读取声明、分析影响、验证边界、评估风险、阻止错误 Patch，并把需要产品决策的问题交还给用户。
```

它的核心价值：

```text
防止 AI 把项目写成不可维护的代码堆
防止自然语言需求绕过工程边界
让复杂项目在用户不懂架构的情况下仍然保持可维护
```
