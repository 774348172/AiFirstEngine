# 热更新能力边界

> 当前实现基线见 `201-热更新方案收敛与当前实现基线.md`。本文定义长期热更新能力边界和产品承诺红线；其中 Level 1 / 2 / 3 / 3.5 的完整热更链路不代表当前代码已经实现。
> 项目逻辑边界以 `195` / `196` 为准：IR 只存在于 Contract-bound RuleSlot 中，是受限规则数据，不是 Lua / Blueprint 式脚本语言；复杂状态机、行为树、复杂 gameplay 流程、复杂算法和复杂 UI 工作流默认进入 Rust Project Module / Rust Framework，不作为默认热更 IR 职责。

## 热更新能力边界

本引擎不能承诺“用户自己生成的所有逻辑和资源都能热更”。  
正确承诺应该是：

```text
引擎不保证任意内容都能热更
引擎保证受控内容可验证热更
```

也就是说，只有当用户生成的内容被限制在引擎定义的 schema、Spec、DSL、IR、资源包、脚本沙箱和模块能力范围内，热更新才可以被强约束、强验证、可回滚地支持。  
如果用户生成内容触及原生 runtime、平台原生插件、底层渲染管线、底层网络协议或引擎核心模块实现，就不能承诺热更，需要走重新打包发布。

### 可强保证热更的内容

资源内容可以强支持热更：

```text
图片
模型
动画
音频
字体
特效预设
材质参数
UI 布局
关卡资源
表现绑定资源
```

这些内容应通过 Asset Bundle / Pak / Addressable Resource 系统管理，并具备：

```text
资源包版本号
资源 hash
依赖表
平台标记
签名校验
回滚信息
```

数据内容可以强支持热更：

```text
角色属性
技能数值
Buff 参数
关卡配置
掉落表
商店配置
AI 行为参数
渲染质量配置
UI 文案
本地化文本
```

受限 RuleSlot 规则可以强支持热更：

```text
技能数值条件
Buff 条件片段
触发器条件
任务条件
关卡条件片段
表现绑定参数
固定 Contract 内的受限业务交易编排
渲染 preset / material graph / postfx 配置数据
```

这些内容适合 AI 生成，因为它们结构化、可校验、可 diff、可回滚，也能被引擎做确定性检查和平台能力检查。

不属于默认规则热更职责：

```text
完整战斗流程
复杂状态机
行为树
A* 寻路
复杂数组 / map 算法
复杂 UI 交互流程
项目侧 Rust Module / Rust Framework
```

如果这些能力确实需要变更，默认走重新构建 / 重新发布。只有被 System Contract 明确限制为 Contract-bound RuleSlot 的轻量规则片段，才可以进入 Level 3 IR hotfix 路线；当前代码仍未实现 IR RuleSlot runtime hotfix。

### 可热更但需要限制的内容

Lua 不作为本引擎的核心逻辑热更路线。  
如果后期保留 Lua，应只作为可选开发工具或非发布调试能力。  
适用场景：

```text
编辑器调试脚本
临时实验插件
开发者工具自动化
非发布逻辑
```

限制要求：

```text
必须运行在脚本沙箱中
必须限制可调用 API
必须限制文件、网络、时间、随机数等非确定性能力
不得作为帧同步核心逻辑的权威来源
不得作为发布版 IR / Rust AOT 逻辑的预览替代语义
```

IR Rule Package 可以作为长期受控规则热更载体，但也不能被描述为任意 native 代码热更。  
适用场景：

```text
跨平台规则模块
规则执行模块
AI 从 DSL / Spec 编译生成的受控规则
由包内 IR Interpreter 执行的热更覆盖规则
```

限制要求：

```text
必须固定 IR 语义版本
必须限制可用 operation
必须签名校验
必须有版本和 hash
必须通过 deterministic test
必须通过 IR Static Validation
必须通过热更影响分析
必须符合移动平台政策
```

Project UI Hot Logic Module 是项目侧 UI 热逻辑的受控热更载体。  
它的推荐路线是：

```text
Rust 源码编写项目侧 UI 逻辑
  -> 编译为 WASM hot module
  -> 通过稳定 Host Interface 批量读取输入
  -> 输出 ProjectUiStateSnapshotPatch / ProjectCommand / Diagnostic
```

它解决的是“项目 UI 逻辑经常要热更”的问题，例如：

```text
复杂 tooltip 文本和属性差值生成
装备 / 商店 / 背包界面的展示数据转换
面板状态和简单 screen flow 计算
AuiAction 到 ProjectCommand 的受限映射
ProjectUiStateSnapshot 的局部 patch 生成
```

它不是：

```text
AUI Core 热更
Rust native dylib 热更
Lua 式任意脚本层
HybridCLR 式托管运行时热更
引擎 UI framework 替换机制
```

允许能力：

```text
读取 ProjectUiStateInput / compact read model
输出 ProjectUiStateSnapshotPatch
把 AuiAction 转成 ProjectCommand
输出 validation diagnostic / trace
使用 Host 提供的受控纯函数和确定性辅助函数
```

禁止能力：

```text
直接访问 ECS storage / 指针 / renderer / RHI
直接访问文件、网络、平台 API
直接创建、删除或移动 AUI node
实现 layout / hit test / drag/drop framework
跨热更保留长期 unmanaged state
绕过 Project Command / Transaction primitive 修改项目状态
```

生效点必须显式声明：

```text
启动时
登录前
大厅
screen transition
panel reopen
战斗结束后
玩家确认重载时
```

不允许在 mid-frame、mid-drag transaction、正在运行的对局中静默替换。

验证要求：

```text
WIT / Host Interface schema version
module manifest / hash / signature
Host import whitelist
deterministic test
dependency validation
performance budget
rollback target
source map / diagnostic map
```

性能规则：

```text
必须批量输入 / 批量输出。
不得逐 UI node 高频跨 Host 调用。
复杂装备 UI 的目标是把热逻辑控制在毫秒级预算内，具体数值以项目 perf gate 实测为准。
```

移动端尤其是 iOS 对“下载并执行动态代码”敏感。  
因此移动端热更策略应优先使用：

```text
数据热更
DSL 规则热更
资源热更
受控 IR / 规则字节码热更
受控 Project UI Hot Logic Module，但必须通过平台政策检查
```

不应把移动端能力宣传成“任意代码热更”。

### Lua / HybridCLR / Rust WASM 对比

本项目不把 Lua 或 HybridCLR 作为主路线，但需要明确它们和 Project UI Hot Logic Module 的区别。

| 路线 | 适用生态 | 优点 | 风险 | 本项目结论 |
|---|---|---|---|---|
| Lua 热更 | Unity / C++ 项目常见 | 成熟、灵活、UI 业务热更经验多 | 自由代码边界容易漂移，AI 审查难，类型与宿主桥接成本高 | 可作为开发工具参考，不作为核心发布路线 |
| HybridCLR | Unity C# / IL2CPP 生态 | C# 心智统一，热更能力强，业务侧成熟 | 依赖 CLR / IL2CPP 生态，不适用于 Rust ABI 和本引擎主线 | 不采用 |
| Rust -> WASM UI Hot Logic | 本项目项目侧 UI 热逻辑 | Rust authoring，沙箱隔离，Host import 显式，跨平台边界稳定，适合 AI-first 验证 | 需要接口 schema、批量数据协议和性能预算治理 | 采用为受控项目 UI 热逻辑路线 |

性能判断：

```text
Lua / C# managed / WASM 在复杂 UI 上的差异主要不来自语言本身，
而来自是否频繁跨宿主边界、是否逐控件调用、是否复制大对象。

Project UI Hot Logic Module 必须用 batch input/output，
避免每个 item cell / tooltip 字段都跨 Host 调一次。
```

### 不应承诺热更的内容

Rust 原生引擎代码不支持热更：

```text
Renderer 底层实现
ECS 核心实现
物理核心
资源系统
网络底层
平台适配层
导出器
原生插件
```

项目侧 Rust native dylib 热更也不作为正式产品承诺。  
Windows/editor 可以后期评估 dev-only fast path，但跨平台发布路线以受控 WASM hot module 为准。

这些内容需要重新构建和发布：

```text
Windows -> 重新导出 EXE
Android -> 重新构建 APK / AAB
iOS -> 重新构建 IPA 并走平台发布流程
Web -> 重新发布 Web 包
```

底层渲染管线结构也不应承诺热更：

```text
新增底层 Render Pass 类型
修改 wgpu 后端逻辑
修改 shader 编译器
修改材质系统核心
修改底层资源生命周期管理
```

可以热更的是：

```text
材质参数
Material Graph
Lighting Preset
PostFX Preset
Quality Profile
Visual Style Patch
```

平台原生能力也不应承诺热更：

```text
支付 SDK
登录 SDK
广告 SDK
推送 SDK
文件权限
系统通知
平台手柄支持
平台商店能力
```

这些能力应随 App 包版本发布。

### 热更新分层

正式分层定义：

```text
Level 1: 数据热更，强支持
Level 2: 资源热更，强支持
Level 3: DSL / Graph / IR 规则热更，强支持，但由 IR Interpreter 执行
Level 3.5: Project UI Hot Logic Module，受限支持，Rust-authored WASM
Level 4: Rust AOT 规则变更，不支持热更，需要重新打包
Level 5: Rust 原生引擎模块热更，不支持，需要重新打包
```

AI 生成内容默认应该落在 Level 1 到 Level 3。  
如果是项目侧 UI 热逻辑，且 IR RuleSlot 表达力不合适，可以落在 Level 3.5。  
Level 3.5 只服务项目 UI 热逻辑，不是默认 gameplay 主路线，也不是 AUI Core 热更。  
Level 4 是正式发布性能路径，不属于热更路径。  
Level 5 属于引擎版本升级，不属于项目热更新。

### 规则热更生效时间点

规则热更必须在专门时间点生效，不允许任意帧直接覆盖正在运行的逻辑。

标准流程：

```text
下载热更文件
校验签名 / hash / 版本 / 依赖
构建或读取 IR Rule Package
执行 Schema Validation
执行 IR Static Validation
执行 Determinism Validation
执行 Platform Policy Validation
挂载到 Hot Update Staging Area
在允许的 Apply Point 切换 Rule Registry
新规则调用走 IR Interpreter 热更覆盖
```

允许的 Apply Point 由项目和运行场景声明，例如：

```text
启动时
登录前
大厅
关卡加载前
战斗开始前
对局结束后
切换场景时
玩家确认重载时
```

不允许：

```text
任意 frame_update 中途替换
正在运行的 State Rule 实例中途替换
正在进行的对局中静默替换规则
未验证直接覆盖线上文件
```

### State Rule 热更规则

State Rule / Lifecycle Rule 不能在运行中热更。

正式规则：

```text
State Rule 实例启动时绑定 rule version。
实例运行期间继续使用该版本。
热更生效后，新启动的 State Rule 实例使用新版本。
旧实例直到 exit / destroy 前不被替换。
```

原因：

```text
State Rule 有 runtime schema
State Rule 有 event binding
State Rule 有 cleanup / exit 责任
State Rule 可能持有表现锁、移动状态、碰撞状态、计时状态
中途替换会造成状态迁移、事件解绑、表现恢复和 determinism 风险
```

如果项目确实需要改变正在运行中的状态，不能用“热更替换规则”处理，而应走显式游戏逻辑：

```text
发出 Command
结束旧 State
执行旧 State exit cleanup
按新规则重新启动 State
或等待下一个安全 Apply Point
```

### 帧同步项目的热更新规则

如果项目是帧同步游戏，例如自走棋，不能允许对局中随意热更逻辑。  
正确规则是：

```text
大厅可以热更
匹配前锁定规则版本
对局中使用固定 logicHash / dataHash / assetHash
对局结束后才能切换新规则版本
```

示例版本信息：

```json
{
  "gameVersion": "1.3.0",
  "rulesetVersion": "2026.06.15.001",
  "assetVersion": "2026.06.15.003",
  "logicHash": "abc123",
  "dataHash": "def456",
  "assetHash": "ghi789"
}
```

同一场对局中，所有客户端必须使用完全一致的：

```text
rulesetVersion
logicHash
dataHash
assetHash
deterministic module version
```

否则帧同步会出现分歧。

### AI 生成热更的标准流程

AI 生成可热更内容时，也不能直接覆盖线上文件。  
标准流程：

```text
User Intent
  -> Project Context Scan
  -> Feature Spec
  -> Hot Update Patch Plan
  -> Schema Validation
  -> Dependency Validation
  -> Deterministic Validation
  -> Platform Policy Validation
  -> Package / Bundle Build
  -> Signature / Hash
  -> Staged Rollout
  -> Runtime Version Lock
  -> Rollback Plan
```

失败处理：

```text
可确定错误 -> AI 自动修复并重新验证
产品性决策 -> 交给用户确认
平台政策或原生能力限制 -> 明确提示必须重新发包
```

### 对外产品表述

对用户和开发者的正确表述应该是：

```text
AI 生成的资源、数据、规则、技能、关卡、UI、表现绑定，默认支持可验证热更。
项目侧 UI 热逻辑可以通过受控 Rust -> WASM hot module 热更。
底层引擎能力、原生平台能力、底层渲染和网络实现，通过版本发布升级。
```

不建议宣传：

```text
所有 AI 生成内容都能热更
所有逻辑都能多端完全热更
无需重新发包即可修改任何能力
```

这个边界更符合真实平台限制，也更适合长期商业化。
