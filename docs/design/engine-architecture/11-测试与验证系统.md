# 测试与验证系统

测试系统正式方案：

```text
AI-native Validation & Test Graph
```

测试系统不是只证明代码能跑，而是证明 AI 生成的需求、规则、资源、构建和运行结果没有偏离用户意图。

默认用户没有编程基础或只有少量编程基础。测试系统必须先给出功能是否成立、玩家能观察到什么、失败影响什么和下一步怎么处理；底层断言、trace 和编译日志放在可展开证据中。

核心目标：

```text
AI 友好
高效率
支持多平台测试
长期可维护
可修改
避免最终逻辑沦为玩具
```

## 基本原则

测试不是普通代码文件，而是项目工程对象。  
测试必须和以下内容建立追踪关系：

```text
Feature Spec
DSL / Graph
Project System IR
IR Interpreter Result
Rust AOT Result
Asset Graph
Build Graph
Runtime Trace
```

完整链路：

```text
Feature Spec
  -> Test Intent
  -> Test Graph
  -> DSL / IR Test
  -> IR Interpreter Test
  -> Rust AOT Equivalence Test
  -> Scenario Test
  -> Simulation Consistency Test
  -> Platform Test
  -> Test Report
  -> AI Fix Plan
```

每个测试都应能追踪：

```text
Test Case
  -> Requirement ID
  -> DSL node
  -> IR node
  -> IR Interpreter step / Rust AOT function
  -> Runtime Trace
  -> Build / Platform Result
```

## 测试分层

最终测试系统分为七层：

```text
1. Static Validation
2. Logic Test
3. Contract Test
4. Scenario Test
5. Simulation Consistency Test
6. Asset / Render / Performance Test
7. Build / Platform Test
```

## 1. Static Validation

不运行游戏，速度最快。  
每次 AI Patch 必跑。

验证对象：

```text
Schema
Feature Spec
Patch Plan
DSL
IR
AssetRef
AssetSet
Bundle Dependency
Module Contract
Architecture Governance
Hot Update Policy
Build Profile
```

作用：

```text
防止 AI 生成非法项目结构
防止资源引用缺失
防止 DSL 越权
防止 Bundle 循环依赖
防止 Patch 破坏架构边界
```

## 2. Logic Test

Logic Test 针对项目规则。

测试对象：

```text
DSL
IR
IR Interpreter
Rust AOT
Command
Query
Rule
Modifier
```

示例：

```text
背包满了不能 AddItem
火球命中后必须 ApplyBuff burning
机械族 3 个单位上阵触发护盾
商店刷新必须遵守稀有度权重
```

特点：

```text
快
可自动生成
适合 AI 修复
不依赖完整场景
```

### Rust AOT Equivalence Test

IR Interpreter 和 Rust AOT 必须执行同一份 IR 语义。  
因此每个进入发布包的规则都必须通过 IR 语义一致性测试。

注意：

```text
这里的等价测试只针对 Canonical Rule IR 的解释执行与 Rust AOT 语义一致性。
它不是 TypeScript Runtime vs Rust Runtime 等价测试。
Rust Native Runtime 的整体正确性由 Golden Scenario Test 验证。
```

测试方式：

```text
同一份 IR
  -> 用 IR Interpreter 执行测试输入
  -> 用 Rust AOT 执行测试输入
  -> 对比输出、事件、错误、deterministic hash
```

必须一致：

```text
输出字段
事件列表
错误类型
确定性随机结果
边界条件
溢出 / 除零 / 非法输入处理
```

如果不一致：

```text
禁止发布
标记为 BackendMismatch
回指 IR node / DSL node / Requirement ID
由 AI 生成修复 Patch Plan
```

这层测试解决：

```text
开发期解释执行通过，但发布版 Rust AOT 行为不同
热更 IR 覆盖和下个版本 AOT 合并后行为不同
不同平台 Rust AOT 输出不一致
```

## 3. Contract Test

Contract Test 验证系统边界。

示例：

```text
UI 不能直接写 InventoryContainer
Presentation Event 不能影响战斗逻辑
IR Rule 不能调用未授权 Native Module / operation
Shop System 不能直接修改 Combat State
项目层不能绕过 Module Contract
```

这层用于防止项目越做越乱，是 Architecture Governance 的测试化落地。

## 4. Scenario Test

Scenario Test 从用户需求生成可运行场景。

示例需求：

```text
玩家获得装备后，局内背包新增装备，UI 显示图标。
```

生成测试：

```text
加载测试场景
创建玩家
执行 AddItem Command
检查 InventoryContainer
检查 UI Query
检查 InventoryItemAdded Event
```

Scenario Test 类似传统引擎的 Play Mode / Functional Test，但必须绑定 Feature Spec 和 Requirement ID。

## 5. Simulation Consistency Test

不是所有游戏都是帧同步游戏。  
因此不应把 Replay / Determinism Test 作为所有项目的固定测试层。

正式测试层为：

```text
Simulation Consistency Test
```

它根据 Project Simulation Profile 展开不同一致性测试。

项目声明：

```json
{
  "simulationProfile": "lockstep_deterministic"
}
```

或：

```json
{
  "simulationProfile": "single_player"
}
```

引擎根据 Profile 决定测试矩阵。

### single_player

适合：

```text
单机动作
打飞机
平台跳跃
RPG
解谜
```

测试重点：

```text
同一场景能否稳定运行
核心规则是否正确
存档 / 读档是否一致
关键事件是否触发
崩溃 / 卡死检查
```

不要求：

```text
跨设备逐帧 hash 一致
严格 deterministic replay
```

### lockstep_deterministic

适合：

```text
帧同步自走棋
帧同步 RTS
确定性战棋
```

测试重点：

```text
同一输入 -> 同一结果
跨平台 hash 一致
Replay 一致
确定性 RNG
禁止系统时间 / 本地随机 / 非确定浮点
```

Replay / Determinism Test 只属于这个 Profile，不属于所有项目。

### server_authoritative

适合：

```text
MMO
竞技游戏
在线 RPG
服务端权威卡牌
```

测试重点：

```text
客户端预测是否能回滚
服务端结果是否权威
客户端不能越权修改状态
网络延迟下状态是否收敛
作弊敏感逻辑是否只在服务端执行
```

不要求客户端和服务端完全执行同一份逻辑。

### turn_based

适合：

```text
回合制 RPG
卡牌
战棋
桌游
```

测试重点：

```text
同一操作序列结果一致
回合状态机合法
撤销 / 重做合法
存档恢复后继续一致
```

### async_multiplayer

适合：

```text
异步 PvP
排行榜挑战
离线结算
邮件战报
```

测试重点：

```text
服务端结算一致
战报可复现
版本锁定
过期规则处理
```

### presentation_only

适合：

```text
纯 UI
展示工具
非逻辑交互
视觉编辑器
```

测试重点：

```text
渲染正确
交互不崩
资源加载正确
性能预算
```

### 一致性测试边界

正式规则：

```text
测试系统不强制所有项目确定性。
测试系统根据 Project Simulation Profile 选择一致性测试。
Replay / Determinism 是帧同步 Profile 的要求，不是所有项目的要求。
```

权责：

```text
引擎提供 Simulation Consistency Test 框架
项目选择 Simulation Profile
System Blueprint / Game Blueprint 提供默认 Profile
AI 根据项目类型建议 Profile
用户确认
```

## 6. Asset / Render / Performance Test

验证资源、渲染和性能预算。

包括：

```text
AssetRef 是否缺失
AssetSet 是否过大
Bundle 是否循环依赖
移动端贴图是否超预算
VFX 粒子数是否超预算
Shader / Material 是否能编译
场景加载内存是否超预算
帧率是否低于目标
```

渲染测试早期可以先做：

```text
非空画面检查
截图对比
关键对象可见性
性能预算检查
```

## 7. Build / Platform Test

构建后真实运行。

包括：

```text
Windows EXE 启动测试
Android APK / AAB 安装启动测试
iOS 构建 / 启动测试
Web 加载测试
热更包下载 / 校验 / mount 测试
崩溃和日志收集
```

这层较慢，但正式发布前必须跑。

## AI 在测试中的职责

AI 不直接说“我觉得没问题”。  
AI 负责：

```text
从 Feature Spec 生成 Test Intent
从 DSL / IR 生成测试用例
根据失败报告生成修复 Patch Plan
补齐缺失测试
解释测试失败
建议哪些测试必须跑
```

引擎负责：

```text
执行测试
记录结果
生成结构化报告
阻止未通过 Patch
阻止高风险发布
```

用户负责：

```text
确认产品性测试结果
决定是否接受性能降级
决定是否发布
决定是否回滚
```

## 用户可理解的测试报告

用户不应该看到一堆底层日志。  
测试报告应显示功能级失败：

```text
功能：局内背包
状态：失败
原因：背包容量规则未阻止第 7 个物品
来源：Requirement R4
影响：局内战斗、移动端 UI
建议：
1. 修复 capacity_rule
2. 禁用局内 AddItem 超容量
3. 添加回归测试
```

用户没有编程基础或只有少量编程基础也能判断问题。

## 权责边界

引擎负责：

```text
Validation Runner
Test Graph
Test Execution
Simulation Consistency
Platform Test Runner
Report
Coverage
Blocking Rules
```

项目负责：

```text
Test Policy
Performance Budget
Required Test Suites
Platform Matrix
Simulation Profile
Release Gate
```

System Blueprint 负责：

```text
默认测试模板
默认契约测试
默认场景测试
默认 Simulation Profile 建议
```

AI 负责：

```text
生成测试
解释失败
生成修复计划
补齐覆盖
建议测试范围
```

用户负责：

```text
审批高风险修复
判断产品性结果
发布 / 回滚决策
确认 Simulation Profile
```

## 最终原则

```text
1. 每个 Feature Spec 必须生成测试意图。
2. 每个可执行需求必须有测试覆盖或明确豁免。
3. 每个 DSL / IR / Interpreter / Rust AOT 错误必须能追踪回 Requirement。
4. 每个 System Blueprint 必须提供默认契约测试。
5. 测试系统根据 Project Simulation Profile 选择一致性测试。
6. Replay / Determinism 只属于 lockstep_deterministic Profile。
7. 发布前必须跑 Build / Platform Test。
8. 用户看到的是功能级失败报告，不是底层日志。
```
