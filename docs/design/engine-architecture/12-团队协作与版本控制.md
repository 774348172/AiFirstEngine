# 团队协作与版本控制

本引擎不能采用传统模式：

```text
多人同时改
  -> Git 冲突
  -> 用户手动解决代码冲突
```

因为本项目正式面向没有编程基础和只有少量编程基础的游戏创作爱好者，用户主要通过自然语言、AI 和编辑器修改项目，不能把手动解决代码冲突作为协作前提。

正式方案：

```text
AI-native Project Versioning & Collaboration
```

核心目标：

```text
冲突提前发现
可自动合并的自动合并
不可自动合并的转成产品决策
AI 解释冲突和生成合并方案
引擎验证后事务应用
用户不需要手动 merge 代码
```

## 基本原则

团队协作不能依赖大文件锁。  
如果 AI-native Patch Version Control 仍然依赖大文件锁，它会失败。

正式原则：

```text
1. 项目源数据采用 One File Per Stable Object。
2. 协作锁定采用 Semantic Lock，而不是文件锁。
3. Patch 冲突按语义路径判断，而不是按文件行判断。
4. 可结构化对象优先走 Patch Merge，不强制锁。
5. 非结构化二进制资源才使用 Asset Lock。
6. 大型索引文件和图文件只作为 Derived Cache，不作为手工编辑真相。
```

## One File Per Stable Object

项目不应把大量对象挤在少数大文件里。  
应采用稳定对象拆分：

```text
project/
  scenes/
    battle/
      scene.meta.json
      entities/
        player.entity.json
        enemy_001.entity.json
        camera.entity.json

  prefabs/
    player/
      prefab.meta.json
      components/
        transform.component.json
        movement.component.json
        dash_ability.component.json
        render.component.json

  features/
    player_dash/
      feature.spec.json
      patch_history.json
      tests.json

  logic/
    skills/
      player_dash.skill.dsl
      fireball.skill.dsl

  assets/
    vfx_dash/
      asset.meta.json
      source.effect

  asset_slots/
    player_dash.trail_vfx.json
```

这样：

```text
改移动速度 -> movement.component.json
改材质 -> render.component.json
改冲刺技能 -> dash_ability.component.json / player_dash.skill.dsl
改拖尾资源 -> player_dash.trail_vfx.json
```

冲突会明显减少。

## Semantic Lock

锁定对象不应该主要是文件，而应该是语义对象。

可锁对象：

```text
Feature
Component
AssetSlot
AssetSet
DSL Rule
Scene Entity
System Blueprint
Build Profile
Version Domain
Release Profile
```

示例：

```text
lock Feature.player_dash
lock Component.player.DashAbility
lock AssetSlot.player_dash.trail_vfx
lock DSLRule.skill.player_dash
```

AI 生成 Patch 前必须先做：

```text
Impact Analysis
  -> 需要锁哪些语义对象
  -> 检查是否有人正在改
  -> 检查是否有 pending Patch
```

## Asset Lock

非结构化二进制资源仍然需要锁。

例如：

```text
psd
fbx
wav
mp4
手工编辑图片
手工编辑模型
```

锁定对象应是 Asset ID，而不是文件路径：

```text
lock Asset.source.boss_model
```

这样资源移动路径时，锁仍然有效。

## Patch Plan 作为版本控制一等公民

每次修改都必须记录：

```text
谁发起
用户意图
AI 生成的 Feature Spec
Patch Plan
影响范围
验证结果
测试结果
实际文件变更
回滚点
```

示例：

```json
{
  "changeId": "change_player_dash_001",
  "author": "user_or_ai",
  "intent": "把玩家冲刺拖尾改成红色闪电",
  "feature": "player_dash",
  "patchPlan": "patch_player_dash_vfx_001",
  "affectedObjects": [
    "AssetSlot.player_dash.trail_vfx",
    "Asset.vfx_dash_red_lightning",
    "Bundle.battle_vfx"
  ],
  "validation": "passed",
  "tests": ["dash_vfx_binding_test"],
  "rollback": "snapshot_2026_06_16_001"
}
```

版本控制管理的不只是文件 diff，而是：

```text
Feature Spec
Patch Plan
Asset Graph
DSL
IR
Build Graph
Validation Report
Test Report
```

## Patch Queue

AI Patch 不能直接进入主线。

正式流程：

```text
用户需求
  -> AI Draft Patch
  -> 私有 Workspace 预览
  -> Validation / Test
  -> Submit Patch
  -> Patch Queue
  -> Conflict Check
  -> Review
  -> Merge to Main
```

Patch Queue 状态：

```text
draft
validating
waiting_review
conflict
approved
rejected
applied
rolled_back
```

团队里 AI 生成的大量修改不能直接进主线，而是排队进入：

```text
待验证
待合并
待审批
已拒绝
已应用
```

## 语义冲突检测

传统冲突是：

```text
同一个文件同一行冲突
```

本引擎需要语义冲突：

```text
两个 Patch 都修改同一个 AssetSlot
两个 Patch 都修改同一个 DSL Rule
一个 Patch 删除资源，另一个 Patch 引用它
一个 Patch 改 Build Profile，另一个 Patch 依赖旧 Profile
一个 Patch 修改背包容量规则，另一个 Patch 修改对应测试
```

冲突判断按语义路径：

```text
scene.battle.entity.player.component.Movement.speed
prefab.player.component.Render.material
feature.player_dash.requirement.R3
assetSlot.player_dash.trail_vfx.current
dsl.skill.fireball.effect.damage_formula
```

如果两个 Patch 改同一个语义路径，就是冲突。  
如果改不同语义路径，就可以自动合并。

## 冲突分类

不是所有冲突都需要人处理。

### 自动可合并冲突

示例：

```text
A 改火球 VFX
B 改火球音效
```

不同语义路径，可自动合并：

```text
AssetSlot.fireball.hit_vfx
AssetSlot.fireball.cast_audio
```

### 规则性冲突

示例：

```text
A 增加背包容量到 30
B 限制移动端背包容量为 20
```

可以由 Profile 合并：

```text
desktop: 30
mobile: 20
```

AI 可以建议，用户确认。

### 产品性冲突

示例：

```text
A 想让火球术变强
B 想削弱火球术
```

这不是技术冲突，而是设计决策冲突。  
必须交给负责人或用户决定。

## Merge Plan

合并不能是手工改文件，而应由引擎生成 Merge Plan。

示例：

```json
{
  "mergePlanId": "merge_fireball_001",
  "patches": ["patch_A", "patch_B"],
  "autoMerged": [
    "AssetSlot.fireball.hit_vfx",
    "Test.fireball_vfx"
  ],
  "conflicts": [
    {
      "path": "dsl.skill.fireball.damage_rule",
      "type": "product_decision",
      "options": [
        "use_patch_A",
        "use_patch_B",
        "combine_formula",
        "ask_ai_rebalance"
      ]
    }
  ]
}
```

用户只需要做产品决策，不需要手动解决代码冲突。

## Semantic Ownership

团队项目必须有语义所有权。

示例：

```text
战斗系统负责人
经济系统负责人
UI 负责人
资源负责人
构建负责人
```

对象可以声明 owner：

```text
Feature.fireball -> combat_team
Blueprint.shop -> economy_team
AssetSet.battle_vfx -> art_team
BuildProfile.android_release -> release_manager
```

如果 AI Patch 修改高风险对象，必须由对应 owner 审批。

## 用户如何处理冲突

用户不需要解决代码冲突。  
系统应该把冲突翻译成自然语言和可选方案。

示例：

```text
冲突：两个修改都改变了火球术的伤害规则。

修改 A：
- 固定伤害从 100 改为 150
- 目标：增强早期战斗爽感

修改 B：
- 伤害改为法强 * 1.2
- 目标：让技能随成长变强

可选方案：
1. 使用 A
2. 使用 B
3. 合并为基础 80 + 法强 * 0.8
4. 让 AI 生成平衡方案并重新测试
```

用户没有编程基础或只有少量编程基础也能处理，因为他面对的是产品决策，而不是代码 merge。

## 派生文件规则

大型索引和图文件不应作为手工编辑真相：

```text
asset_graph.json
dependency_graph.json
bundle_manifest.json
build_graph.json
```

它们应该是：

```text
Derived Cache
Build Output
Generated Index
```

可以重新生成，不需要多人手动 merge，不应该成为冲突源。

真正可编辑源应该是：

```text
Feature Spec
DSL
Scene Entity
Prefab Component
Asset Metadata
AssetSlot
AssetSet
Policy
```

## 权责边界

引擎负责：

```text
Patch History
Semantic Lock
Conflict Detection
Version Snapshot
Rollback
Merge Plan
File Layout
Asset Lock
VCS Adapter
Change Report
Patch Queue
Review Gate
```

项目负责：

```text
Branch Policy
Review Policy
Lock Policy
Release Policy
Semantic Ownership
谁能改哪些系统
哪些资源必须锁
哪些 Patch 必须审核
```

AI 负责：

```text
生成 Patch Plan
解释冲突
建议合并
补测试
生成变更说明
协助回滚
```

用户负责：

```text
审批 AI Patch
解决产品性冲突
确认合并
确认回滚
确认发布
```

## 最终原则

团队协作不能是：

```text
AI 写文件
  -> Git 冲突
  -> 用户手动 merge
```

而必须是：

```text
AI 生成 Patch Plan
  -> Impact Analysis
  -> Semantic Conflict Detection
  -> Patch Queue
  -> Merge Plan
  -> User / Owner Decision
  -> Validation / Test
  -> Transaction Apply
```

一句话：

```text
本引擎必须把冲突从代码合并问题变成结构化产品决策问题。
```
