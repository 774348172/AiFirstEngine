# 库系统与项目资源归属

本文档定义 AI 原生游戏引擎中的库系统边界，以及项目资源应该归属的位置。

## 核心结论

项目里的资源文件全部放在：

```text
Project Library
```

也就是：

```text
Project Library = 当前项目的主资源库
```

它对应 Unity 的：

```text
Assets / Project Window
```

对应 Unreal 的：

```text
Content Browser
```

Project Library 是用户看到和管理资源的地方。  
Asset Graph 是引擎内部记录引用关系、依赖关系、分包和热更关系的底层结构。

```text
用户看到：Project Library
引擎内部：Asset Graph
```

用户不应该直接面对 Asset Graph。

## 为什么需要内部数据层

如果只是普通手动资源编辑器，直接使用文件系统也许可以工作。  
但本引擎的目标是 AI 原生游戏生产，因此不能只依赖文件名和文件夹。

文件系统只能告诉引擎：

```text
这里有一个 enemy.png
这个文件叫 enemy.png
它在 Assets/Sprites/
它什么时候修改过
它多大
```

但 AI 和引擎真正需要知道：

```text
这个资源是什么用途
谁生成的
生成它的需求是什么
能不能商用
被哪些 Prefab / Scene / DSL 引用
它属于哪个 AssetSet
能不能热更
适合哪个平台
移动端贴图预算是否通过
有没有低配版本
碰撞体怎么来的
能不能安全删除
修改后影响哪些 Build Bundle
和哪个 Style Bible 匹配
当前是第几个版本
能不能回滚
```

这些信息不能靠文件系统自然表达。  
如果没有内部数据层，AI 只能：

```text
猜文件名
扫文件夹
读散乱文件
凭感觉修改
```

这会让后期项目越来越不可维护。

因此引擎必须维护内部数据层：

```text
Asset Metadata
Asset Database
Asset Graph
AI Source Graph
Asset Revision
Validation Report
Build / Bundle Relation
```

这些不是给用户手动维护的项目文件，而是引擎自动维护的索引、历史和依赖关系。

## 内部数据层的收益

### 引用稳定

资源引用不能只依赖路径。

如果 Prefab 引用：

```text
Assets/Enemies/enemy.png
```

用户改名为：

```text
Assets/Enemies/enemy_red.png
```

路径引用就会断。

正式规则：

```text
资源身份使用 GUID
用户路径可以变化
引用关系不能因为移动 / 改名轻易断裂
```

这和 Unity `.meta` 的核心价值一致。

### AI 理解上下文

AI 生成或修改资源时，需要知道：

```text
这是敌机
属于红色阵营
用于 enemy_medium_sprite
被 Enemy_Medium.prefab 使用
移动端最大 512px
由哪张参考图生成
用户上次要求“更有压迫感”
```

这些必须来自 Asset Metadata / Asset Graph / AI Source Graph。  
不能只靠文件名推断。

### 删除和修改安全

用户删除或替换资源时，引擎要知道：

```text
这个资源被哪些地方引用
删除是否会导致 Prefab 缺失
是否有替代资源
是否需要同步更新 Bundle
是否需要提示用户确认
```

这必须依赖 Asset Graph。

### Build / 热更可计算

Build 和热更不能简单复制所有文件。

Build Graph 需要知道：

```text
哪些资源被当前场景使用
哪些资源属于同一个 Bundle
哪些资源发生了变化
哪些依赖也要带上
哪些资源只需要热更
```

因此 Asset Graph 和 Build / Bundle Relation 是必要的。

### 版本和回滚

AI 会连续生成和修改资源。  
没有内部版本记录，就无法可靠支持：

```text
回到上一个敌机版本
撤销这次 AI 生成
查看 AI 改了哪些资源
恢复误删资源
```

因此 AI 操作必须进入：

```text
Asset Revision
AI Operation History
Patch Transaction
```

### 验证和质量门禁

AI 生成资源后需要检查：

```text
尺寸
格式
透明
碰撞
LOD
授权
平台预算
风格一致性
引用完整
```

验证结果必须保存为 Validation Report，避免每次全项目重复扫描。

## 内部复杂度控制原则

内部数据层会增加同步和维护成本。  
因此必须遵守以下原则：

```text
1. 文件系统仍然是用户可见来源
2. GUID + meta 是最小必需层
3. Asset Database 必须可重建
4. Cache 必须可删除
5. Asset Graph 必须可从资源和引用重新计算
6. AI 生成历史和版本是增量记录
7. 用户不直接编辑内部数据库
8. 内部数据必须可校验、可修复
```

内部数据不是另一个用户要维护的项目。  
它是引擎自动维护的索引和历史。

最终收益：

```text
让 AI 不靠猜
让引用不靠路径
让删除可检查
让打包可增量
让热更可计算
让回滚可实现
让验证可缓存
让项目可长期维护
```

最终代价：

```text
需要同步系统
需要元数据
需要状态管理
```

但只要内部数据层做到：

```text
可重建
可校验
可修复
用户不可见
```

这个代价就是可控的，也是 AI 原生引擎必须承担的地基成本。

## 库的定义

库不是简单文件夹，也不是运行时系统。  
库是：

```text
一组可被用户和 AI 检索、复用、安装、验证的结构化内容集合
```

它可以包含：

```text
资源
Prefab
Scene
AssetSet
Style Bible
System Blueprint
AI Workflow
DSL 模板
材质 / Shader Preset
VFX Preset
Build Profile
Validation Rule
```

库的重点不是“放文件”，而是：

```text
这个内容能被 AI 理解
知道用途
知道依赖
知道适用范围
知道怎么安装到项目
知道怎么验证
知道怎么撤销
```

因此库的定位是：

```text
内容管理
复用入口
AI 检索上下文
安装来源
```

## 库的类型

库系统只保留四类：

```text
1. Project Library
2. Built-in Library
3. Imported Library Package
4. Marketplace Source
```

不单独提供自动跨项目的 Personal Library。

个人常用资源、个人偏好、个人模板，如果用于某个项目，就属于该项目的 Project Library。  
如果要复用到另一个项目，必须显式导出和导入。

```text
Project A -> Export Package
Project B -> Import Package
```

不允许项目之间自动引用个人库。

## Project Library

Project Library 是当前项目的主资源库。

项目自己的内容全部放在 Project Library：

```text
图片
Sprite
音频
3D 模型
材质
Shader Preset
VFX
Prefab
Scene
UI
DSL
IR Rule
AssetSet
Style Bible
AI 生成历史
参考图 / 参考视频 / 参考音频
Build Profile
Validation Report
```

建议项目结构：

```text
MyGameProject/
  Library/
    Assets/
    Prefabs/
    Scenes/
    UI/
    Audio/
    Materials/
    VFX/
    Logic/
    Blueprints/
    References/
    Generated/
    Packages/
  ProjectSettings/
  BuildProfiles/
  Cache/
  Temp/
```

其中：

```text
Library/
```

就是当前项目的 Project Library。

## AI 生成资源归属

AI 生成资源必须进入 Project Library。

默认位置：

```text
MyGameProject/
  Library/
    Generated/
      enemy_red_set/
        enemy_small.sprite
        enemy_medium.sprite
        enemy_boss.sprite
        generation_graph.json
        asset_spec.json
```

用户确认使用后，可以归档到正式分类：

```text
Library/
  Assets/
  Prefabs/
  VFX/
  Audio/
  UI/
```

但无论处于 Generated 还是正式分类，本质都属于：

```text
Project Library
```

AI 生成资源必须保留：

```text
Asset Spec
Generation Graph
Asset Revision
Reference Asset
Provider / Model / Prompt / Seed
License / Source
Validation Report
```

## Imported Library Package

用户从市场、团队、另一个项目或第三方来源导入的包，进入：

```text
Project Library / Packages
```

示例：

```text
MyGameProject/
  Library/
    Packages/
      red_enemy_pack/
      sci_fi_ui_kit/
      inventory_blueprint_pack/
```

关键规则：

```text
导入前是外部包
导入后属于当前项目上下文
不和原来源保持强耦合
更新必须显式进行
删除必须显式进行
```

项目不能偷偷依赖外部个人库、云端库或市场资源。  
这样项目才能完整迁移、构建和归档。

## Built-in Library

Built-in Library 是引擎内置库。

它只提供只读默认能力和标准起点，不存放项目私有资源。

Built-in Library 中的所有引擎提供能力必须保持项目无关。

正式规则：

```text
引擎库不能依赖某个具体项目规则
引擎库不能理解某个具体项目语义
引擎库不能反向引用 Project Library
引擎库不能和项目库形成耦合
```

也就是说，引擎库可以提供：

```text
通用计算
通用算法
通用资源处理
通用渲染能力
通用音频能力
通用物理能力
通用平台能力
通用验证能力
```

但不能提供带项目语义的能力：

```text
查找敌人
释放技能
商店刷新
怪物掉落
任务完成
阵营敌对
装备穿戴规则
卡牌结算规则
```

这些属于 Project Rule，应该由 Schema / DSL / Blueprint 在项目层表达。

包含：

```text
基础材质
基础 Shader Preset
基础 UI 控件
基础输入模板
基础 System Blueprint
基础 Validation Rule
基础 Build Profile
Core Compute Module 说明
Engine Capability Module 说明
```

关系是单向的：

```text
Project Library 可以使用 Built-in Library
Built-in Library 不能反向引用 Project Library
```

建议规则：

```text
通用运行时能力可以引用 Built-in Library
会被用户修改的内容必须复制 / 安装到 Project Library
```

原因：

```text
避免用户修改内置资源污染全局引擎
避免项目迁移时缺失可修改内容
避免 AI 修改引擎默认资源
```

## 引擎提供模块边界

早期讨论中的 `Standard Module` 容易被误解为“标准玩法模块”。  
因此正式拆成两类：

```text
Core Compute Module
Engine Capability Module
```

### Core Compute Module

Core Compute Module 是引擎提供的通用计算能力库。

它类似 Unity 中的 Mathf / Mathematics / Random 等能力，但更适配本引擎的 Schema / DSL / IR / Rust AOT 路线。

它负责：

```text
给定输入
执行确定性计算 / 查询 / 转换
返回输出
```

它不负责：

```text
决定什么时候调用
决定数据从哪个 Component 来
决定结果写到哪里
决定是否触发事件
理解敌人 / 玩家 / 技能 / 商店 / 任务等项目语义
```

可提供能力：

```text
MathModule
CurveModule
RandomModule
CollectionModule
GeometryModule
SpatialComputeModule
PathComputeModule
FormulaModule
WeightedRandomModule
DeterministicHashModule
```

示例：

```text
Math.add(a, b) -> number
Curve.evaluate(curve_id, t) -> number
Random.next(seed) -> number
WeightedRandom.sample(table, count, seed) -> index[]
Geometry.distance(a, b) -> number
SpatialCompute.query_radius(space_index, center, radius) -> EntityId[]
PathCompute.find_path(graph, start, end, options) -> NodePath
Formula.evaluate(formula, typed_inputs) -> number
```

注意：

```text
SpatialCompute.query_radius 只返回空间范围内的候选 Entity
它不知道谁是敌人

PathCompute.find_path 只计算路径
它不知道目标是不是敌人

WeightedRandom.sample 只执行权重抽样
它不知道抽出来的是商店商品还是怪物掉落
```

### Engine Capability Module

Engine Capability Module 是引擎提供的通用运行时能力。

它可以有副作用，因此权限高于 Core Compute Module。

可提供能力：

```text
AssetModule
VfxModule
AudioModule
AnimationModule
PhysicsModule
RenderModule
NavigationModule
NetworkModule
SaveModule
PlatformModule
```

示例：

```text
AssetModule.load(asset_ref)
AssetModule.instantiate(prefab_ref, transform)
VfxModule.spawn(asset_ref, transform, parameters)
AudioModule.play(asset_ref, position, parameters)
AnimationModule.play(entity_id, clip_ref, options)
PhysicsModule.apply_force(entity_id, vector)
```

它同样不能理解项目语义。

不允许：

```text
VfxModule.play_skill_vfx(skill_id, target)
AssetModule.load_enemy_asset(enemy_type)
AudioModule.play_boss_death_sound(boss_id)
NavigationModule.find_path_to_enemy(entity_id)
```

正确方式：

```text
DSL / Project Rule 决定：
什么时候播放
播放哪个资源
目标 Entity 是谁
资源 AssetRef 从哪里来
结果如何写回项目状态

Engine Capability Module 只执行通用能力。
```

## 引擎库与项目规则边界

正式边界：

```text
Schema 提供项目数据字段
DSL 组织项目规则
Core Compute Module 提供通用计算能力
Engine Capability Module 提供通用引擎能力
Project Library 保存项目资源和规则
Built-in Library 保存只读引擎默认能力
```

一句话：

```text
引擎库不理解游戏，只提供能力。
项目规则理解游戏，通过 Schema / DSL 调用能力。
```

例如，不允许：

```text
find_enemies_in_radius(center, radius)
```

因为 `enemy` 是项目语义。

应拆成：

```text
候选 = SpatialCompute.query_radius(space_index, center, radius)
敌人 = DSL 根据 Faction / Health / TeamRule 过滤候选集合
```

再例如，不允许：

```text
refresh_shop_items(shop_id)
```

应拆成：

```text
候选 = Project Rule 根据商品池和条件生成权重表
结果 = WeightedRandom.sample(weight_table, count, seed)
Project Rule 将结果写回 Shop Component
```

最终规则：

```text
所有引擎提供的库都必须是项目无关能力。
所有项目语义必须留在 Project Library 的 Schema / DSL / Blueprint 中。
引擎库不能依赖项目库。
项目库可以通过受控 Contract 调用引擎库。
```

## Marketplace Source

Marketplace Source 是外部发现和下载来源。

它负责：

```text
发现
搜索
下载
购买
安装
更新来源
```

它不作为项目运行时库，也不作为项目直接依赖。

项目真正使用市场内容时，必须进入：

```text
Project Library
```

或者安装为：

```text
Imported Library Package
```

不允许运行时直接依赖 Marketplace Source。

## 库与库之间的解耦

库之间默认无依赖。

正式规则：

```text
库不能自动引用另一个库
库不能隐式读取另一个库
跨库使用必须显式安装 / 导入 / 复制
```

允许的关系：

```text
Project Library -> 使用 Built-in Library
Project Library -> 安装 Imported Library Package
Project Library -> 从 Marketplace Source 下载包
Imported Library Package -> 声明自己的依赖
```

不允许：

```text
Project A 自动引用 Project B 的个人库
Project Library 自动引用云端个人库
Marketplace 资源被运行时直接引用
Imported Package 偷偷引用用户本地路径
Built-in Library 反向引用项目内容
```

## AI 如何使用库

AI 可以搜索多个来源，但不能让库自动耦合。

AI 搜索顺序：

```text
1. 当前 Project Library
2. 当前项目已安装的 Imported Library Package
3. Built-in Library
4. Marketplace Source
```

如果 AI 想使用 Marketplace Source 里的内容，必须生成：

```text
Install Plan
```

用户确认后才导入项目。

如果 AI 想复用另一个项目的内容，必须走：

```text
Export Package -> Import Package
```

不能直接跨项目引用。

## 库的能力边界

库负责：

```text
收纳内容
检索内容
描述内容
显示引用
导入 / 导出
安装 / 卸载
版本
兼容性
许可证
AI 可检索元数据
```

库不负责：

```text
运行时加载
热更新执行
打包构建
AI 推理
游戏逻辑执行
资源生成本身
```

对应关系：

```text
库负责管理内容
Asset Graph 负责引用关系
Build Graph 负责打包
Runtime 负责加载
AI Pipeline 负责生成
Validation 负责验证
```

## 用户可见文件模型

Project Library 是用户经常面对的路径，因此用户可见层必须简单。

正式规则：

```text
Project Library 中用户可见资源只允许两种形态：
1. 普通文件
2. 普通文件夹
```

不采用用户可见的目录式资源：

```text
enemy_medium.asset/
  source.png
  cooked.ktx2
  asset.json
  spec.json
  generation_graph.json
```

原因：

```text
用户很难理解什么时候资源是文件，什么时候资源是目录
用户会困惑应该修改哪个内部文件
外部工具处理目录式资源会更复杂
版本控制和人工排查成本更高
AI 的复杂性不应该转嫁给用户
```

用户看到的应该接近 Unity：

```text
Project Library/
  Assets/
    enemy_medium.png
    player_ship.png
  Prefabs/
    enemy_medium.prefab
  Scenes/
    level_01.scene
  Audio/
    explosion.wav
  Generated/
    red_enemy_set/
      enemy_small.png
      enemy_medium.png
      enemy_boss.png
```

用户理解模型：

```text
资源就是文件
一组资源就是文件夹
```

复杂 AI 数据、生成图、版本、验证报告放到引擎内部管理位置：

```text
ProjectSettings/
  AssetDatabase/
  AIHistory/

Cache/
  Imported/
  Cooked/
  Thumbnails/
```

或者隐藏元数据目录：

```text
.asset-meta/
  <asset_guid>/
    asset.json
    spec.json
    generation_graph.json
    revisions.json
    validation_report.json
```

这些目录由引擎维护，用户不需要理解和手动修改。

最终原则：

```text
用户看到：Unity-like 普通文件和文件夹
AI / 引擎看到：GUID、Metadata、Asset Graph、Generation Graph、Revision、Validation Report
```

这符合：

```text
Unity-like Editor Shell
+
AI-native Internal Data Model
```

## GUID 与 Meta 规则

每个用户可见资源都必须有稳定身份。

正式规则：

```text
资源身份使用 GUID
资源路径只作为当前位置
引用关系不能只依赖路径
```

最小 meta 文件：

```text
enemy_medium.png
enemy_medium.png.meta.json
```

meta 至少包含：

```json
{
  "guid": "asset_7f3a...",
  "type": "sprite",
  "importer": "sprite_importer",
  "import_settings": {},
  "last_known_hash": "..."
}
```

复杂数据不堆在资源旁边，而由 GUID 关联到内部数据层：

```text
enemy_medium.png
  -> enemy_medium.png.meta.json
  -> AssetDatabase / asset_7f3a / ...
```

如果用户移动或改名资源，只要 meta 跟随移动：

```text
GUID 不变
引用不变
Asset Graph 更新路径
```

如果 meta 丢失，引擎尝试从 Asset Database 根据 path / hash 找回 GUID。  
不能确认时，生成新 GUID，并提示可能存在引用风险。

## 外部文件变更支持

引擎必须支持用户在引擎外部增删改查 Project Library 文件。

正式原则：

```text
Project Library 是普通文件夹
用户可以在引擎内外修改
引擎负责同步、识别、修复和提示
```

但边界是：

```text
外部修改可以支持
但不是所有外部修改都能静默自动修好
```

能高置信修复的自动修复。  
不能高置信修复的标记 Conflict 并询问用户。

### 外部新增文件

用户在文件夹中新增：

```text
enemy.png
```

如果没有 meta：

```text
生成 meta
分配 GUID
导入资源
创建 Asset Database 记录
Project 面板显示新资源
```

### 外部修改文件

用户使用 Photoshop / Blender / Audacity 等工具修改文件。

引擎检测：

```text
hash 变化
mtime 变化
```

处理：

```text
标记 Dirty
重新导入
重新生成缩略图
重新跑基础 Validation
刷新引用处显示
```

### 外部删除文件

用户删除资源文件后，不立即硬删内部记录。

处理：

```text
资源标记 Missing / Tombstone
保留 GUID 和历史
查询引用
提示恢复 / 替换 / 确认删除引用
```

Tombstone 的作用：

```text
保留资源身份
保留引用关系
保留 AI 历史
允许恢复或替换
```

### 外部改名 / 移动

理想情况：

```text
enemy.png
enemy.png.meta.json
```

一起移动。  
这时 GUID 不变，引用不变。

如果只移动文件，没有移动 meta：

```text
引擎根据 hash / 文件大小 / 修改时间 / 文件名相似度尝试匹配
```

高置信匹配时：

```text
自动修复或提示用户确认
```

无法确认时：

```text
新位置当作新资源导入
旧资源标记 Missing
```

### 外部删除 meta

如果资源文件存在，但 meta 缺失：

```text
尝试从 Asset Database 根据 path / hash 找回 GUID
能恢复则重建 meta
不能恢复则生成新 GUID
如果存在引用风险则提示用户
```

### 外部同时修改文件和 meta

这是高风险情况：

```text
文件 hash 变了
meta GUID 也变了
```

可能原因：

```text
用户复制其它资源覆盖
SVN / Git 合并冲突
手动乱改 meta
```

处理：

```text
标记 Conflict
禁止 Build
提示用户选择：
  保留旧 GUID
  使用新 GUID
  当作新资源
  恢复上一次记录
```

## 资源状态

每个资源必须有明确状态：

```text
Ready
Dirty
Pending
Importing
Missing
Tombstone
Broken
Conflict
Stale
```

状态含义：

```text
Ready = 资源可用
Dirty = 文件已变化，等待导入
Pending = 等待同步队列处理
Importing = 正在导入
Missing = 文件缺失但内部记录仍存在
Tombstone = 删除后的保留记录，可恢复或替换
Broken = 导入失败或格式非法
Conflict = GUID / meta / 文件状态冲突，需要用户处理
Stale = 当前显示的是旧缓存或旧导入结果
```

状态规则：

```text
Build 不能使用 Dirty / Pending / Importing / Broken / Conflict 资源
AI 不能基于 Dirty / Pending / Importing 数据做最终写入
Scene / Game 可以临时显示 Stale 资源，但必须标记
Validation 必须等待相关资源 Ready
```

## 资源同步与导入锁定

Project Library 是普通文件夹，用户可以在引擎内外增删改查文件。  
外部变化包括：

```text
资源管理器复制 / 删除 / 改名 / 移动
Photoshop / Blender / Audacity 等外部工具修改
SVN / Git 拉取和合并
脚本批量生成资源
AI 写入资源文件
```

这些变化必须统一进入：

```text
Asset Sync Pipeline
```

基础流程：

```text
File Watcher / Project Rescan
  -> Change Queue
  -> Scanner
  -> Meta Resolver
  -> Import Pipeline
  -> Asset Database Update
  -> Asset Graph Update
  -> Cache Invalidate / Rebuild
  -> Editor Refresh
```

### 大量资源变更

大项目下，SVN / Git 一次拉取大量资源是必须支持的场景。

例如：

```text
新增 5000 个文件
修改 2000 个文件
删除 300 个文件
移动 100 个文件
meta 冲突 20 个
```

这种情况不能按单个文件事件逐个导入，必须进入：

```text
Bulk Sync Mode
```

Bulk Sync Mode 规则：

```text
1. 检测到大量变化后暂停细粒度实时导入
2. 扫描文件清单
3. 和 Asset Database 做差异对比
4. 生成 Change Manifest
5. 执行 Index Sync
6. 执行 Import / Validate
7. 更新 Asset Graph
8. 生成 Sync Report
```

Bulk Sync 触发条件：

```text
短时间内文件事件超过阈值
检测到 .svn / .git 更新
用户点击 Reimport / Resync
项目重新获得焦点后发现大量差异
打开项目时 Full Scan
```

同步不能全量重导。  
必须使用增量判断：

```text
path
mtime
file size
hash
meta GUID
import settings hash
dependency hash
```

如果：

```text
文件 hash 没变
import settings 没变
importer version 没变
platform profile 没变
```

则复用缓存，不重新导入。

缓存 key：

```text
asset_guid
source_hash
import_settings_hash
importer_version
platform_profile
```

缓存包括：

```text
Imported Cache
Cooked Cache
Thumbnail Cache
Validation Cache
Dependency Cache
```

### 导入期间项目锁定

正式设定：

```text
导入资源 / 同步资源期间，用户不能操作项目。
```

原因：

```text
导入期间 Asset Database 可能正在更新
Asset Graph 可能正在重算
资源状态可能处于 Dirty / Importing / Pending
Prefab / Scene / DSL 的引用可能暂时不完整
此时继续编辑可能造成不可预料的问题
```

因此进入 Asset Sync Pipeline 后，编辑器进入：

```text
Project Import Lock
```

锁定期间禁止：

```text
编辑 Scene
编辑 Prefab
编辑 Inspector 字段
拖拽 / 删除 / 移动 Project Library 资源
AI 写操作
AI Patch Apply
Build / Export
Hot Update 发布
运行 Validation
保存项目修改
```

锁定期间允许：

```text
查看导入进度
查看同步日志
查看冲突列表
取消 / 暂停导入
打开 Sync Report
关闭项目
```

UI 显示：

```text
正在同步项目资源
新增：5000
修改：2000
删除：300
冲突：20
进度：1300 / 7400

项目已锁定，导入完成前不可编辑。
```

AI Tab 显示：

```text
项目资源正在同步，AI 写操作已暂停。
导入完成后可继续执行任务。
```

### 两阶段同步

虽然用户操作被锁定，但内部仍然分两阶段：

```text
阶段 1：Index Sync
阶段 2：Import / Validate
```

Index Sync：

```text
快速建立文件和 GUID 状态
识别新增 / 修改 / 删除 / 移动 / 冲突
生成 Change Manifest
```

Import / Validate：

```text
重新导入变更资源
重建必要缓存
更新缩略图
更新 Asset Graph
生成 Validation Report
```

只有两阶段都完成，项目才解除锁定。

### 可中断恢复

资源导入必须可中断、可恢复。

引擎保存：

```text
SyncState
ImportQueue
FailedJobs
ConflictList
Change Manifest
```

如果编辑器关闭：

```text
下次打开继续同步
```

如果单个资源导入失败：

```text
标记 Broken
继续处理其它资源
最终在 Sync Report 中展示
```

### AI 写入资源规则

AI 生成或修改资源时，不能绕过 Asset Sync Pipeline。

AI 写入必须走：

```text
Asset Write Transaction
  -> 写入资源文件
  -> 写入 / 更新 meta
  -> 更新 Asset Database
  -> 更新 Asset Graph
  -> 触发 Import / Validation
  -> 生成 AI Operation History
```

禁止：

```text
AI 直接往 Project Library 乱塞文件
AI 直接修改内部 Asset Database
AI 在资源 Dirty / Importing / Conflict 时继续写入相关资源
AI 绕过 meta 创建资源
```

原因：

```text
AI 写入和用户外部写入都必须进入同一套同步机制
否则 Asset Database / Asset Graph / Cache 会不一致
```

### 最终规则

```text
文件监听只负责小规模实时变化入口。
Bulk Sync Mode 负责大规模外部变化。
导入 / 同步期间进入 Project Import Lock。
锁定期间用户不能编辑项目，AI 不能写入，Build 不能启动。
导入完成并生成 Sync Report 后才能恢复操作。
用户外部增删改移动资源必须支持，但不能高置信修复时必须进入 Conflict。
AI 写入资源也必须走 Asset Write Transaction。
```

## 最终规则

```text
所有项目资源都归 Project Library 管理。
所有项目可修改资源必须存在于 Project Library。
外部包导入后进入 Project Library / Packages。
AI 生成资源进入 Project Library / Generated，确认后可归档到正式分类。
Built-in Library 只提供只读默认能力，不存放项目私有资源。
Marketplace Source 只作为下载来源，不作为项目资源位置。
```

一句话：

```text
库是项目内可复用内容的结构化管理入口，不是跨项目自动共享的依赖系统。
```
