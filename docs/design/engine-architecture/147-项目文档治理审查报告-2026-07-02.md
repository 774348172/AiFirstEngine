## 3. 当前文档结构判断

当前文档结构已经比早期清楚很多，主线入口基本成立：

```text
README.md
  -> 框架设计/引擎总体架构/00-文档地图.md
  -> 49-当前状态与下一步入口.md
  -> 54-当前可自动化施工总入口.md
```

当前正式工程入口已经明确为：

```text
rust/                         正式 Rust workspace
框架设计/引擎总体架构/          架构、规则、施工文档入口
legacy/typescript-prototype/  已退役 TypeScript / Electron 原型，仅历史参考
```

施工和阶段记录也已经有正确归口：

```text
框架设计/引擎总体架构/施工文档/
框架设计/引擎总体架构/阶段完成记录/
```

结论：

```text
文档主结构可继续使用。
不需要再次大规模重建文档目录。
需要修的是入口同步、路径表达、当前规则收敛，而不是推倒重来。
```

## 4. 发现的问题

### 4.1 当前状态入口有轻微滞后

`49-当前状态与下一步入口.md` 的“当前最近完成”仍写 M11：

```text
144-M11-Physics2D-Collider-Authoring-Visualization-C-min方案.md
```

但 `54-当前可自动化施工总入口.md` 和 `施工文档/README.md` 已经记录最近完成是：

```text
146-Historical-Docs-Legacy-Annotation-and-Archive-Governance
```

影响：

```text
后续 AI 或人类从 49 进入时，会误以为最近状态停在 M11。
```

治理建议：

```text
每次施工完成后，49/54/施工文档README/阶段完成记录README 必须同步更新同一个最近完成项。
```

### 4.2 路径表达存在相对路径歧义

`00-文档地图.md` 中写：

```text
施工文档/README.md
阶段完成记录/README.md
```

这些路径相对 `框架设计/引擎总体架构/` 是正确的，但如果从仓库根目录理解，会误以为根目录下也存在 `施工文档/` 和 `阶段完成记录/`。

影响：

```text
搜索或自动化脚本容易从根目录找错路径。
```

治理建议：

```text
入口文档中第一次出现施工和阶段路径时，写完整相对路径：
框架设计/引擎总体架构/施工文档/README.md
框架设计/引擎总体架构/阶段完成记录/README.md
后续在同目录文档中可继续简称。
```

### 4.3 当前有效规则列表不够完整

`00-文档地图.md` 的“当前有效规则”列出了近期规则和部分主线规则，但没有完整覆盖 `131-M1` 到 `139-M6 / Sprite2D / RenderAsset` 等已经写入的当前方案。

影响：

```text
从“当前有效规则”列表看，会低估 M1-M6 等系统的当前有效性。
```

治理建议：

```text
“当前有效规则”不再试图手写全量清单。
改成两层：
1. 当前最高优先级规则。
2. 当前主线索引按 Runtime / Render / Editor / Build / Validation 分类。
```

这样能减少每次新增文档后都要手动维护一个巨大列表。

### 4.4 历史关键词仍然很多，但不应继续大规模清洗

搜索结果显示，历史文档和阶段记录中仍有大量：

```text
TypeScript
Electron
npm.cmd
Bridge
Hydration
RenderAssetBridge
```

这不是错误。它们大量存在于：

```text
阶段完成记录
历史施工文档
带 current status notice 的旧架构文档
兼容旧命名的代码或报告
```

当前治理规则已经说明：

```text
TypeScript / Electron 是 legacy reference。
Bridge / Extract / Hydration 旧命名统一按 Projection / ProjectionAdapter 理解。
```

判断：

```text
不建议继续逐行重写所有历史文档。
继续清洗会消耗大量时间，并可能破坏历史追溯。
```

真正需要做的是：

```text
入口处强约束。
当前方案文档顶部有状态说明。
新增方案不得继续扩展旧命名。
```

### 4.5 施工完成记录已经很多，不能再把它当作当前入口

`施工文档/已完成/` 和 `阶段完成记录/` 数量已经很大。

风险：

```text
如果后续讨论直接从已完成施工文档检索结论，容易读到过期中间态。
```

治理规则应保持：

```text
施工文档/已完成/ 只用于复盘。
阶段完成记录/ 只用于事实追溯。
当前正式规则只能看正式方案文档和 00/49/54 入口。
```

## 5. 是否存在文档已经难以为继

当前没有到“难以为继”的程度，但有两个趋势需要压住：

```text
1. 当前有效规则列表如果继续手写全量，会越来越难维护。
2. 历史关键词如果不靠入口状态约束，AI 检索会继续被旧路线干扰。
```

建议的长期治理方式：

```text
保持少数入口文档强同步。
正式方案文档只追加大系统规则，不为小问题不断生成微文档。
已完成施工文档和阶段记录不参与当前决策。
历史文档只加状态说明，不再大搬家。
```

## 6. 后续文档治理规则建议

### 6.1 固定五个当前入口

后续任何讨论或施工前，只把下面五个作为当前入口：

```text
README.md
框架设计/引擎总体架构/00-文档地图.md
框架设计/引擎总体架构/49-当前状态与下一步入口.md
框架设计/引擎总体架构/54-当前可自动化施工总入口.md
框架设计/引擎总体架构/130-复杂打飞机编辑到Windows可玩项目缺失能力当前基线.md
```

施工时再读：

```text
框架设计/引擎总体架构/施工文档/README.md
框架设计/引擎总体架构/施工文档/当前/
```

完成后再写：

```text
框架设计/引擎总体架构/阶段完成记录/
```

### 6.2 每次施工完成的最小同步动作

每次施工完成后只做这些固定动作：

```text
1. 施工文档从 当前/ 移动到 已完成/。
2. 新增 阶段完成记录/YYYY-MM-DD-系统名/00-总览.md。
3. 更新 54 的当前可施工状态和最近完成。
4. 更新 49 的当前真实状态和最近完成。
5. 如果新增正式规则，更新 00-文档地图.md 对应分类。
```

不再每次施工后全仓库重整文档。

### 6.3 当前规则和历史规则分层

文档判断优先级应固定为：

```text
1. 00 / 49 / 54 / 130 当前入口
2. 当前正式方案文档
3. 施工文档/当前
4. 阶段完成记录
5. 施工文档/已完成
6. 历史文档 / 其它AI审查目录 / legacy/typescript-prototype
```

低层文档不得覆盖高层当前规则。

## 7. 本次自审结论

```text
Specification fit: 本报告只做文档治理审查，符合用户要求。
Rule fit: 没有重开已确认系统，没有把历史 TS/Electron 当作当前方案。
Textual consistency: 区分了当前入口、正式规则、施工记录、历史记录。
Design fit: 有利于 AI 检索和长期维护，减少每轮施工后的文档重整成本。
Implementation feasibility: 建议都是文档入口和流程治理，不依赖代码改造。
Practical reasonableness: 不做大规模历史清洗，避免新的文档灾难。
```

最终判断：

```text
当前文档体系可以继续使用。
主要问题是入口同步和当前/历史边界表达，不是目录体系本身失败。
```
