## 6. 是否实现走偏

### 6.1 没有明显走偏的部分

```text
TypeScript / Electron 主动入口已退役，Rust 是正式主线。
Runtime 没有把打飞机玩法概念做成引擎 API。
ECS 写入、Project Rule、CommandBuffer、Trace 等仍保持通用底座边界。
RHI / WgpuBackend 分层已经存在，wgpu 没有成为所有层的直接真相。
Projection 统一规则已经写入文档，并在 report summary 中有所体现。
```

### 6.2 有偏移风险但尚未失控的部分

#### Editor UI 层级偏多

当前存在：

```text
editor_ui_model
editor_ui_renderer
editor_input
editor_wgpu_renderer
editor_window_winit
editor_ui_backend_egui
editor_host
```

风险：

```text
如果每个 UI 功能都在多层重复注册 command / hit / payload / render / test fixture，后续会变得难维护。
```

当前缓解：

```text
UiDrawList / HitRegion / UiCommand / EditorSession transaction 已经形成主线。
```

建议：

```text
后续新增 UI 能力必须先确认归属：
EditorUiModel 真相数据
SelfUiRenderer 生成 draw / hit
editor_input 只路由输入
EditorSession 执行业务命令
editor_wgpu_renderer 只 present
不要让 panel 自己绕过这条链。
```

#### 旧 Bridge 命名仍在代码里

代码仍有：

```text
Physics2DBridge
AuiRendererBridge
RenderAssetBridge
RenderSnapshot
```

这不等于当前架构走偏，因为文档已规定它们是历史实现名或兼容入口，统一按 Projection 理解。

风险：

```text
如果后续继续新增 XxxBridge，会重新走向无数桥的复杂路线。
```

建议：

```text
新增同步类型只新增 ProjectionAdapter。
旧 Bridge 名可以保留到自然重构，但不得继续作为新系统命名。
```

#### RenderSnapshot 仍在 FrameLoop 兼容路径中

代码中仍有：

```text
render_snapshot.rs
FrameOutput.snapshot
FrameOutput.snapshot_compat
```

风险：

```text
如果 Snapshot 再次被当作长期渲染真相层，会和 RenderCommand / RenderSceneState / RHI 主线冲突。
```

当前判断：

```text
它目前更像兼容和 hash / golden support，不是主要渲染通道。
```

建议：

```text
后续不要基于 RenderSnapshot 扩展新渲染能力。
新渲染能力继续走 RenderCommand / RenderSceneState / RuntimeRenderer / RHI。
```

#### editor_ui_backend_egui 仍存在

当前 `editor_ui_backend_egui` 只有约 125 行，主要用于 headless summary。

判断：

```text
它目前不像正式 UI 路线核心，也没有阻塞当前自研 UI / WGPU 路线。
```

风险：

```text
如果后续继续把 egui 当正式控件承载，会和自研 UI renderer 长期路线冲突。
```

建议：

```text
保持为历史/兼容/测试辅助，不扩展为正式编辑器 UI backend。
```

## 7. 是否有实现已经难以为继

当前没有发现必须立即推翻的实现。

但有三个需要优先收敛的维护风险：

```text
1. editor_core 已经 1.6 万行，EditorSession 聚合了很多领域状态。
2. editor_window_winit 承担 application shell、dock、input route、real window、runtime viewport 等多种职责。
3. engine_runtime 已经 3 万行，模块很多，但 lib.rs 仍是平铺导出，长期需要更清晰的 domain grouping。
```

这些不是本轮要立刻拆的施工任务，但后续每做一个大系统时都应避免继续把职责塞进单一文件。

## 8. 距离复杂打飞机 Windows 可玩项目的真实距离

根据 `130-复杂打飞机编辑到Windows可玩项目缺失能力当前基线.md`，M1-M11 多数已经有 C-min / v1 实现或阶段完成记录。

当前最大的差距已经从“底层没有能力”转为：

```text
真实用户级闭环没有被稳定验收。
编辑器真实窗口可用性还没有达到 Unity-like 创作体验。
复杂样例项目还没有成为长期回归资产。
导出 exe 的真实运行、截图、输入、渲染、报告闭环还不够常规化。
```

换句话说：

```text
底层能力已经搭出很多段。
最缺的是把这些段用一个真实项目串起来，并用真实窗口 / 真实导出产物验收。
```

## 9. 推荐下一步方向

不建议继续随机补单点系统。

推荐下一步只围绕一个大目标：

```text
复杂打飞机最小真实项目闭环验收
```

该闭环不应新增打飞机专用引擎 API，只用项目侧数据验证：

```text
Project Authoring Workspace
Project Rule IR -> Rust AOT
Prefab / Scene / Asset / Input / AUI
RuntimePackageBuilder
Windowed Player
RuntimeRenderer / RHI / WgpuBackend
Trace / Report
```

验收方式建议分三层：

```text
1. headless golden：证明数据链和规则链正确。
2. native window smoke：证明真实窗口可打开、可输入、可 present。
3. exported package gate：证明导出目录可独立运行，并产生可读 report。
```

## 10. 本次自审结论

```text
Specification fit: 覆盖了当前实现、走偏风险、难以维护风险和复杂打飞机缺口。
Rule fit: 没有加入项目玩法 API，没有重开已确认系统。
Textual consistency: 明确区分已实现、风险、缺口、建议。
Design fit: 继续坚持 Rust 主线、Projection、RHI、Project Rule、AI 友好和复杂项目能力。
Implementation feasibility: 结论来自现有源码和测试，不依赖未验证假设。
Practical reasonableness: 没有建议推倒重来，重点放在闭环验收和边界收敛。
```

最终判断：

```text
当前工程主线没有明显走偏。
底层实现没有到难以为继。
最大风险是编辑器/UI/真实导出闭环的产品化不足，以及文档入口不同步导致后续讨论被旧路线带偏。
```
