## 1. 归档规则

本文只记录已经发生并有现存证据支持的事实：

1. `failed`、`blocked` 与随后修复后的 `passed` 是不同历史终态，不互相覆盖。
2. 预期红测试与意外失败分开记录；预期红测试不计为产品回归。
3. 原始 artifact 缺失时只记录 `evidence gap`，不得根据后续代码反推或补造原始失败原因。
4. 历史 R2-N6/N7/N7V/N7W/R2-G 与 R2-FC6 的授权已经消费，不得重跑、改写或复用其 candidate、activation、attempt、root 或 evidence。
5. 本文中的“公共 Module 设计未被推翻”只表示现有证据没有证明两个公共 Interface 的目标分割错误，不表示其内部 Implementation 已通过 production 验证。

## 2. 公共 Module 结论

公共 Interface 始终保持：

```text
ProductionCandidateModule::produce(request)
  -> CandidateDisposition

CodexOutcomeEvaluationModule::evaluate(candidate, goal, riskEnvelope)
  -> EvaluationOperation
```

历次失败没有证明需要把 prepare/conformance/seal/activate/finalize/rollback 重新公开为 caller 菜谱，也没有证明应把 candidate production 与真实环境 evaluation 合并。已经确认的系统性缺口集中在 `ProductionCandidateModule` 的内部语义角色、production composition 测试 seam 和施工验证设施。

`CodexOutcomeEvaluationModule` 的 observer/composition 已完成非 production 回归，但因为 R2-FC6 未产生 candidate，真实 production `evaluate` 尚未执行。不得把“尚未执行”写成“设计失败”或“production acceptance passed”。

## 5. R2-FC6 已确认根因

冻结事实：

```text
outer commit: 35e88d3f3a6e888d8db3b79606ea161f7de07ff8
outer tree:   2f2e6d2063e1fcefbf38cb3bd64aec5e0e259feb
gitlink OID:  e332e0ba6d5c1b7772de57ef69804eebe28ea415
owner invocation count:  1
module invocation count: 1
retry count:             0
candidateId created:     false
diagnostic:              source_snapshot.file_set_mismatch
cleanup:                 complete
```

后验代码与定向测试审查确认的因果链：

```text
SourceSnapshotProducer::produce
-> snapshot exact reopen passes
-> ProductionConformanceModule receives fixture_root inside snapshot
-> released editor_host --gateway-process-preflight opens that project
-> ProjectIntentWorkflow attaches project binding
-> writes Library/ProjectIntent/journal.json inside snapshot
-> SourceSnapshotProducer::reopen compares exact file set
-> extra generated file causes source_snapshot.file_set_mismatch
```

这暴露的是正式合同中的矛盾：同一目录同时承担 immutable source truth 与 writable Editor project。修复不得把 `Library/**` 简单加入 caller exclude list，也不得弱化 snapshot exact reopen。

## 6. 重复失败的共同原因

### 6.1 语义角色退化为弱类型原语

```text
Git regular file / gitlink             -> 都退化为 Path
immutable snapshot / writable project -> 都退化为 &Path
owned process / reused PID            -> 都退化为 raw PID
completed / unknown exit              -> 都退化为 nullable exit code
```

正式方案要求强身份和强 ownership，但内部 seam 没有把这些角色编码为不同的 capability/value type，导致错误只能在昂贵组合运行中出现。

### 6.2 精确 production composition 太晚执行

组件测试分别证明 snapshot 会拒绝 extra file、Editor 能打开项目，却没有组合证明：

```text
Editor opens conformance project
-> generated state remains outside immutable snapshot
-> snapshot still reopens exactly
```

R2-FC4 的 name-filtered production tests 没有执行 ignored N6/N8 preflight；`ProductionConformanceModule::run_with_evidence` 也没有真实端到端测试。R2-FC5 的 1600+ default/all-features tests 因此不能覆盖 R2-FC6 的实际路径。

### 6.3 施工验证设施自身变成第二套复杂产品

PowerShell Runner 先后承担 timeout、exit code、incremental output、process tree、PID residual、stage logging 与 cleanup authority，产生了多次与目标产品无关的失败。后续不得继续用新增 Runner 状态机补偿产品 Module 内部 seam 缺失。

### 6.4 昂贵大矩阵制造了错误信心

full workspace 回归能发现共享回归，但不能替代目标级 exact composition test。正确顺序应是快速精确组合红/绿测试、受影响域回归、一次 exact production-composition preflight，最后才是一次权威 workspace 矩阵。

## 9. 采用的纠偏方案

采用方案 2：

1. 保留两个公共目标级 Module，不新增第三个 public lifecycle Interface。
2. 在 `ProductionCandidateModule` 内部显式区分 `ImmutableSourceSnapshot` 与 `DisposableConformanceWorkspace`。
3. 任何会创建 journal、cache、Library、Build、Temp 或其它生成状态的 Editor/fixture action 只能获得 writable workspace，不能获得 snapshot project root。
4. workspace 由 Module 从 snapshot 物化并生成 receipt；caller 不提供 exclude list、copy recipe、stage order 或 generated-path 菜谱。
5. candidate identity 继续绑定 immutable snapshot、release inventory 与 conformance evidence；不绑定 disposable workspace 的运行时生成字节。
6. 增加穿过 `ProductionCandidateModule::produce` orchestration 的快速组合测试，以及最终权威回归前的 exact released-Editor composition preflight。
7. full workspace 矩阵不能再冒充 exact production composition coverage。

本文确认设计方向，不构成代码施工、Fresh Candidate 重跑、FC7、activation 或 Real Evaluation 授权。
