## 1. 目标与已确认原因

让同一次 Windows dev 导出的 Game.exe、Engine DLL、Project DLL、RuntimePackage、清单和验收结果对应同一份产物。以现有 DesktopExport / Compiler / runtime_cli 为 owner，不增加 Agent 工具或调用前置步骤。

327-R3 的 `.artifacts/327-r3-formal-delivery` 混合了两次测试输出：原始 `aife-dx-4936-1789234860639364900` 的 RuntimePackage manifest SHA-256 为 `42E69452BBB217A052D46FD2438D5A325D114485955179CBB62C9648B687BBD6`，对应混合目录的 `data/data/runtime_package/manifest.json`；原始 `aife-dx-5868-1789234358713626300` 的 manifest SHA-256 为 `9CD1E3B7CEA5ACE9B1FD6F6B79EA6EF97B33F628BCFA5367B5A5A9EA04477695`，对应混合目录的顶层 RuntimePackage。两份原始目录没有重复嵌套；后者还执行了故意复制失败的测试。具体人工复制命令未保留。

因此不能认定正常导出器自动制造重复目录；旧混合证据包不能再证明单次正式成功导出。DLL execution owner 的独立运行事实不因此抹除。

已确认的产品缺口：`runtime_cli::exported_player_verification::resolve_package_contract` 只正式识别 release manifest，dev manifest 回退 `legacy-dev`，仅检查必要文件存在而未核对 dev 清单中的模块摘要。现有 `ProjectPlayerArtifact` 已核对 module ID/interface/AOT，RuntimePackageBuilder 已有 staging/publish；无需重做这两个 owner。

## 3. 方案 B 的实现合同

### 3.1 同源交付清单

继续使用 `desktop-package-manifest.v1`，保留 `playerArtifactHash`，只补 `engineRuntimeHash`、`projectRuntimeModuleHash`、`runtimePackageDigest` 三个摘要字段。不另建文件清单、路径配置、注册表、crate 或发布状态机。三个运行文件为 Game.exe、engine_runtime.dll、data/bin/<规范化 moduleId>.dll；固定相对路径规则由现有 owner 产生，不能由 AI 手写。

新增字段可反序列化旧数据，但当前 dev 交付验收遇到缺失身份必须给出“重新导出”的结构化失败，不能静默当成已校验的当前包。release 格式沿用既有合同；不以夹具为理由保留当前 dev 绕过校验的分支。

模块 moduleId/interfaceVersion/aotContentDigest 必须与 RuntimePackage 的 runtimeModule 相同；Game.exe 摘要与既有 playerArtifactHash 对齐。DLL 摘要来自此次选择并复制的文件；复制前后的摘要不一致或必要清单写入失败时导出失败。

清单中的旧绝对目录字段是来源信息，包可整体移动；运行载荷使用 package root 下的固定相对布局。完整复制无需修改原始清单或原始导出报告。

### 3.2 现有 build / verify 内的共享检查

在既有依赖方向允许的位置（runtime_cli 的交付校验代码）共享 dev 清单类型/纯文件校验；project_authoring_execution 复用并维持现有公开 re-export。不把任何检查变成新增工具。

检查本轮运行载荷是否完整、摘要是否匹配、module identity 是否一致，以及引擎管理的目录是否含重复运行载荷/多余项目 DLL。`data/data`、`reports/reports` 这类已观测到的重复布局应失败；README、许可证和报告输出不作为任意附加文件禁令的对象。复用既有安全相对路径、摘要和 RuntimePackage 校验基础，不引入整仓扫描或全资源二次编译。

实现复核补充：既有 Loader 还识别 `data/project_runtime.dll` 与 `data/runtime_package/project_runtime.dll`；正式 dev 布局须拒绝这些旧项目 DLL 位置，防止绕过本次清单绑定的 `data/bin/<moduleId>.dll`。不调整 Loader ABI 或引入新的路径配置。

导出完成前执行静态一致性检查；显式 verify 在启动 Player 前复用检查。Compiler 在已有内部 DeliveryRef 中增加本次 package-manifest 字节摘要，在 verify/playtest 与当前文件核对；既有 EXE/RuntimePackage 摘要继续保留。即使 DLL 与清单被一起替换得相互自洽，也不能冒认原 DeliveryRef。该字段不增加工具参数或外部 schema。playtest 的原有 lineage/摘要语义保留，并消费需要的 DLL 身份检查。

开发构建不强制启动游戏，326 的 build/verify 解耦与 334 缓存均保留。检查失败返回已有结构化诊断（code/path/message），不回退旧 dev 验收分支。

### 3.3 证据保留

验收一个成功导出的原始目录，或把这一整份包逐相对路径复制到一个全新的保留目录。复制前后比较运行载荷/清单摘要；不合并不同输出、不改写旧报告冒充新产物。原始导出报告原样保留，移动后的运行报告单独记录新的实际位置。

测试故意修改/损坏输出前先保留成功交付；完成记录只引用成功快照。旧混合目录保留供追溯，并在 327-R3 记录注明不再作为单次正式交付资格证据。

## 5. 验收

1. 同源 dev 包静态检查及有界正式 Player 运行通过；完整移动/复制后的同一包仍通过。
2. 旧 module 摘要、缺失文件、替换 Engine/Project DLL、RuntimePackage 内容变化、重复运行目录被拒绝，拒绝发生在进程启动前。
3. manifest 缺失必要身份或格式错误不能以 legacy-dev 成功；原有 release 合同不退化。
4. 必要清单/报告写入失败返回失败；build-without-verify 保持无 Player 运行。
5. 保留一次成功交付的同源证据与原始报告，纠正旧混合证据引用；完成记录明确源码集成、正式包运行和安装态的不同范围。

## 6. 风险与控制

摘要检查增加顺序文件读取，优先复用已有摘要，避免重复扫描相同文件；不借此做新的性能优化。增加字段可能暴露旧夹具/旧 dev 包身份不足，修正夹具或明确要求重新导出，不能削弱检查。只对引擎拥有的载荷布局建立约束，不建立任意目录白名单。
