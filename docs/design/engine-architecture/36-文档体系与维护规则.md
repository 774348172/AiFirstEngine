# 文档体系与维护规则

本文档定义当前架构文档和执行需求文档的分层规则。

它的目标不是新增引擎能力，而是避免文档越写越乱，尤其避免三类内容混在一起：

```text
架构规则
施工计划
执行记录
```

## 新需求进入文档体系的流程

新需求进入时，先判断它属于哪一类。

```text
如果是在讨论引擎应该怎么设计：
  -> 更新核心架构规则。

如果是在讨论某个模块怎么落地：
  -> 更新长期实现路线。

如果是现在可以直接做：
  -> 在 施工文档/当前 新增施工文档。
  -> 更新 49-当前状态与下一步入口.md。
  -> 更新 54-当前可自动化施工总入口.md。

如果已经做完：
  -> 写入阶段完成记录。
  -> 同步 49-当前状态与下一步入口.md。
  -> 同步 54-当前可自动化施工总入口.md。
  -> 施工文档从 施工文档/当前 移到 施工文档/已完成。
  -> 如果执行中验证出新规则，回填架构文档。

如果被新路线替代：
  -> 移入或标记为历史文档。
```

## 架构方案讨论标准

后续每个重要架构方案都必须包含市场对比。

### 已确认系统不重复讨论规则

后续每次讨论一个系统前，必须先查已有文档，而不是直接重新出方案。

必须先搜索：

```text
框架设计/引擎总体架构/00-文档地图.md
框架设计/引擎总体架构/
框架设计/引擎总体架构/施工文档/当前/
框架设计/引擎总体架构/施工文档/已完成/
框架设计/引擎总体架构/阶段完成记录/
框架设计/UE源码参考/
框架设计/Unity源码参考/
框架设计/Bevy源码参考/
框架设计/Godot源码参考/
```

如果已经存在当前有效方案：

```text
不从零重新讨论同一个系统。
先说明“该系统已讨论过”。
列出对应方案文档 / 施工文档 / 完成记录。
只讨论缺口、冲突、新证据、实现落地或下一个未确认系统。
```

只有以下情况允许重新打开已确认系统：

```text
用户明确要求推翻或重审旧方案。
实现时发现旧方案无法施工。
新源码参考或测试结果证明旧方案存在重大缺陷。
旧方案与后续更高优先级规则冲突。
```

如果只是用户问“继续讨论下一个系统”：

```text
必须先排除已经有正式方案的系统。
优先选择当前文档中标记为缺口、阻塞、未确认或需要施工的系统。
```

这条规则优先级高于“先调研其它引擎再出方案”。  
原因是：已经确认的系统不应该因为每次重新调研而反复打开，否则文档会膨胀，施工入口会漂移，AI 和人都会被重复方案拖慢。

### Projection 统一命名规则

后续所有引擎内部跨域同步都必须优先使用：

```text
World Projection
Projection Boundary
Projection Adapter
Projection Report
```

禁止为了单个类型或单个系统继续新增独立：

```text
xxxBridge
xxx桥
xxx独立同步器
```

例外只限真实外部边界：

```text
进程通信
网络通信
第三方工具通信
外部 SDK / OS API 适配
```

当前有效归属以 `110-World-Projection-Adapter统一跨域同步规则.md` 为准：

```text
RuntimeScene Hydration = HydrationProjection
RenderExtract = RenderProjection
SpriteRenderer2D ECS-to-RenderProxy Bridge = RenderProjectionAdapter<SpriteRenderer2D>
RenderAssetBridge = AssetProjection
Physics2DBridge = Physics2DProjection
AuiRenderExtract / AuiRendererBridge = UiProjection
```

如果历史文档、施工记录或旧代码类型名继续出现 `Bridge / Extract / Hydration`：

```text
可以作为历史命名保留。
不能作为新增系统命名依据。
新增方案必须先说明它归属于哪个 Projection Boundary。
新增类型只增加 ProjectionAdapter，不增加独立跨域流程。
```

这条规则的目标是减少隐性规则和无数局部桥，保证 AI 和人类工程师排查问题时只沿着：

```text
source domain -> projection kind -> adapter -> target domain -> report
```

进行定位。

### 系统级讨论门控

后续讨论默认按“系统”推进，不按孤立细节点无限下钻。

一个系统进入讨论时，必须先完成系统级框架，再进入细节：

```text
1. 系统目标：
   这个系统解决什么问题，不解决什么问题。

2. 市场对比：
   Unity / Unreal / Bevy / Godot 等成熟方案如何划分该系统。

3. 本项目系统边界：
   哪些属于引擎层，哪些属于项目层，哪些属于编辑器层，哪些属于构建层。

4. 核心数据模型：
   只定义能支撑系统闭环的核心结构，不先拆无限字段。

5. 核心流程：
   画出从输入到输出的主流程。

6. 关键细节：
   只挑会影响长期架构、AI 友好、复杂项目维护、性能的关键细节讨论。

7. 方案收敛：
   形成一份系统方案文档。

8. 施工方案：
   方案确认后再拆自动化施工文档。
```

禁止的讨论方式：

```text
不在没有系统总览的情况下逐字段讨论。
不因为发现一个边界问题就新增一套规则系统。
不把第一版细节讨论扩张成长期必须实现的完整系统。
不让连续小问题替代系统方案文档。
```

允许的细节讨论条件：

```text
该细节会影响系统边界。
该细节会影响数据模型稳定性。
该细节会影响 AI 是否能生成 / 修改 / 查 Bug。
该细节会影响复杂项目后期维护。
该细节会影响施工能否开始。
```

如果连续讨论超过三个细节点，必须暂停并回到系统级文档，重新判断：

```text
当前是不是缺系统总览。
当前是不是已经可以写方案。
当前是不是应该生成施工文档。
当前是不是在讨论第一版不需要的细节。
```

固定讨论顺序：

```text
1. 简明说明这个问题是什么。
2. 说明为什么现在需要讨论。
3. 列出用户需要确认的点。
4. 调研并对比市场成熟方案。
5. 根据本项目优先级给出推荐方案。
6. 明确哪些能力第一版做，哪些能力暂不做。
7. 用户确认后再写入对应架构文档。
```

市场对比至少包含：

```text
Unity 对应方案
Unreal 对应方案
Godot / Bevy / Cocos / O3DE 等相关方案
Rust / Web / Native 生态中可参考的底层库
```

如果某个领域没有完全对应方案，也要说明：

```text
没有直接对应。
只能参考其中某一层。
本项目为什么不能照搬。
```

推荐方案必须按本项目优先级判断：

```text
第一优先级：AI 友好。
第二优先级：复杂项目可维护。
第三优先级：后期可修改。
第四优先级：规则简单，不制造隐性复杂度。
第五优先级：性能。
第六优先级：多平台成本。
```

文档写入前必须明确：

```text
这个方案更像市场上的哪一个。
和 Unity / Unreal / Godot / Rust 生态方案相比，我们保留什么、舍弃什么。
第一版边界是什么。
长期演进路径是什么。
```
