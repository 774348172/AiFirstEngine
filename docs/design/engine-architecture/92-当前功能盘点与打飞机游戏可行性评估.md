```text

```

```text

```

这些名称可以作为历史实现名保留，但不再作为新增架构概念扩展。后续新增类型只新增对应 `ProjectionAdapter`，不新增独立 Bridge。

## 1. 本文目的

本文基于当前 Rust 代码和测试结果，盘点 AI First Engine 已经实现的功能，并判断当前能力是否足以制作一个“稍微复杂的打飞机游戏”。

这里的“稍微复杂的打飞机游戏”不是只播放一个移动方块，而是至少包含：

```text
玩家飞机移动
玩家发射子弹
敌机生成与移动
子弹击中敌机
碰撞检测
敌机扣血 / 死亡
得分
资源图片进入项目并显示
可编辑 Scene
可 Play / Run
可测试 / 可追踪
```

## 6. 结论：现在能不能做稍微复杂的打飞机游戏？

### 6.1 可以做什么

当前可以做一个“技术验证版打飞机”：

```text
一个玩家飞机 Entity
按 Space 或 WASD 触发规则
玩家飞机移动
RenderExtract 产生 RenderCommand
RenderThread / RuntimeRenderer 生成 headless report
AI mock 生成飞机图片并进入项目资源
资源通过 PlaceAssetIntoScene 放入 Scene
保存并 Play
```

这个版本更像：

```text
打飞机游戏的引擎技术切片
```

它可以验证：

```text
输入能进 Runtime
规则能改 ECS
ECS dirty 能进入渲染
资源能进入 Scene
编辑器能保存和 Play
Trace / Report 能记录过程
```

### 6.2 现在还不能自然完成什么

当前还不能自然完成一个“稍微复杂、可玩、可编辑”的打飞机游戏，因为缺少：

```text
1. Gameplay Query API
2. Spawn / Despawn 暴露给 LogicContext
3. 标准 Velocity / Lifetime / Health / Damage / Score 组件
4. 2D Collider / AABB / Overlap Query
5. Bullet / Enemy / Player 的标准 gameplay archetype
6. Timer / Cooldown / Wave Spawner
7. SpriteRenderer / 2D 排序 / 透明渲染的完整闭环
8. Input Mapping 项目资产化
9. Prefab Authoring 到 Runtime Instantiate 的完整编辑器闭环
10. 一个可重复运行的 Shooter Golden Scenario
```

## 7. 推荐下一步

## 8. 推荐判断

```text
当前引擎已经具备“做游戏闭环”的底座。
当前引擎还不具备“自然制作稍微复杂打飞机游戏”的 gameplay 标准模块。
```

所以结论是：

```text
现在可以做打飞机技术 demo。
但如果要做稍微复杂的打飞机游戏，应该先实现 Shooter Gameplay C-min。
```

这一步非常值得做，因为它会直接暴露：

```text
ECS Query 是否够用
LogicContext API 是否合理
FrameLoop 顺序是否够简单
Gameplay 模块是否会把规则重新搞复杂
AI 是否能按自然语言生成可维护规则
```

## 9. 后续边界修正

本文第 7 节提到的 `Shooter Gameplay C-min` 容易被误解为“引擎内置打飞机玩法模块”。后续正式讨论中应修正为：

```text
Engine Gameplay Foundation C-min
```

打飞机只作为验证场景，不作为引擎内置玩法方向。

边界如下：

```text
引擎侧：
ECS Query
Generic Component Read / Write
CommandBuffer
Spawn / Despawn
2D Collision Query
Sprite2D Rendering
Prefab Instantiate
Time / Timer
Input Mapping Asset
Trace / Replay

项目侧：
Player
Enemy
Bullet
Health
Damage
Score
WaveSpawner
WeaponLevel
```

后续以 `93-复杂打飞机验证所需引擎侧缺失能力清单.md` 为准。
