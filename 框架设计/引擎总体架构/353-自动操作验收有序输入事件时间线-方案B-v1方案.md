## 1. 目标与权威边界

在现有Semantic Playtest中增加按tick组织、tick内严格有序的输入事件，使AI能通过现有工具重复执行鼠标移动、点击、拖动、持续射击和必要组合键，并使用既有Observation Contract、断言与截图验证结果。

继承顶层产品/架构v1.1、[312语义运行验收](312-Semantic-Runtime-Observation-Outcome-Acceptance-v1方案.md)、现有Native输入回放及[352已接入基线](阶段完成记录/2026-09-17-352-Toolchain-Installation/00-总览.md)。本方案只扩展312的输入合同及其直接执行消费者，不重开Observation、Compiler、Provider或Runtime架构。312中仅键盘的v1合同作为兼容输入继续成立；新增有序事件使用明确版本区分。

九项公开Engine tools保持不变。AI继续编写项目测试场景，通过engine_runtime_playtest执行、按需engine_runtime_observe回读。Provider不成为Agent，也不新增逐事件MCP工具。

## 2. 确认的缺口与改动规模

当前PlaytestInput仅包含simulationTick、keyDown/keyUp，校验拒绝同tick同键的多次转换；NativePlayerInputScriptFrame另有pointerPosition，但没有鼠标按钮事件。SemanticPlaytestController::input_script只转换键盘字段，scripted_input_events按键盘按下、键盘松开、最后鼠标移动的固定分组顺序生成事件。

底层InputDeviceState已经顺序处理RawInputEvent，PointerDown/Up使用事件发生时的指针位置，frame_events保留运行输入事件。可复用这条公共路径，无需建立新的设备系统。

范围评估为中等：修改集中于输入DTO、校验、适配、计数及直接消费者；公开JSON输入合同发生扩展，需要跨Compiler、Player、Engine DLL传输验证。代码主owner仍为runtime_player_winit，不以此新增crate、长驻服务或通用脚本语言。

## 5. 版本与唯一输入合同

### 5.1 语义场景

新增`playtest-scenario.v2`。除inputs内容外，其余字段、限制和结果聚合沿用312；seed仍保持当前不支持边界。

```json
{
  "schemaVersion": "playtest-scenario.v2",
  "scenarioId": "input.ordered-example",
  "initialSceneId": "scene-main",
  "target": "windows-headless",
  "maxSimulationTicks": 60,
  "maxPresentationFrames": 120,
  "timeoutMs": 10000,
  "inputs": [
    {
      "simulationTick": 1,
      "events": [
        {"type": "pointerMove", "position": [320, 180]},
        {"type": "mouseDown", "button": "Left"},
        {"type": "pointerMove", "position": [360, 180]},
        {"type": "mouseUp", "button": "Left"}
      ]
    },
    {
      "simulationTick": 10,
      "events": [
        {"type": "keyDown", "key": "ShiftLeft"},
        {"type": "keyDown", "key": "D"},
        {"type": "mouseDown", "button": "Left"}
      ]
    },
    {
      "simulationTick": 20,
      "events": [
        {"type": "mouseUp", "button": "Left"},
        {"type": "keyUp", "key": "D"},
        {"type": "keyUp", "key": "ShiftLeft"}
      ]
    }
  ],
  "assertions": [],
  "captures": []
}
```

这是输入格式示例，scene-main须存在于实际项目；空assertions不构成功能验收。施工验收场景必须添加能捕获实际错误的项目断言。

v2输入点只接受simulationTick和events；不允许同点或同场景混用v1的keyDown/keyUp字段。events为有序数组，不增加eventId、浮点时间戳、优先级或另一套序号；定位使用数组索引。

### 5.2 事件类型

| type | 必需字段 | 含义 |
| --- | --- | --- |
| keyDown | key: string | 按下指定逻辑键，保持到keyUp |
| keyUp | key: string | 释放已按下键 |
| pointerMove | position: [i32, i32] | 更新目标画布像素位置 |
| mouseDown | button: Left / Right / Middle | 按下鼠标按钮，使用当时的指针位置 |
| mouseUp | button: Left / Right / Middle | 释放鼠标按钮，使用当时的指针位置 |

鼠标枚举映射到既有RuntimePointerButton的Primary/Secondary/Middle；不接受任意device path。枚举封闭，未知type、未知字段、缺失字段、类型错误均拒绝，不静默忽略。

v2键名接受原v1逻辑名A–Z、0–9、Space、Enter、Escape、ArrowUp/Down/Left/Right，增加Tab及ShiftLeft/ShiftRight、ControlLeft/ControlRight、AltLeft/AltRight。不引入KeyA与A双重写法，不模拟OS快捷键；大小写遵守此白名单。新增键必须走现有键/修饰键识别路径，不能靠项目特殊处理字符串。

修饰键必须作为明确keyDown/keyUp输入；没有单独modifiers字段。跨tick保持的组合键为本轮必须验证的用法。同tick释放修饰键后的动作判定，继续服从现有公共Input Mapping快照语义，不承诺逐事件重新执行玩法映射。

### 5.3 原生回放与唯一事件定义

新增`native-player-input-script.v2`，顶层保持scriptId/frames，frame点采用frameIndex/events；复用与语义场景相同的事件DTO，不复制两个不同的键/按钮枚举。

统一事件类型归runtime_player_winit，邻近现有输入DTO实现；可抽取一个小的replay_input模块，避免新增crate。语义场景负责模拟tick校验，原生脚本保留呈现frame语义；两者共用事件到RawInputEvent转换，不能共享或混淆计时器。

## 6. 时间、顺序与状态语义

1. inputs的simulationTick一基且严格递增，同tick所有事件放在一个events数组。数组顺序即执行顺序；不得按事件类型重新分组、排序或合并。
2. 输入在目标模拟tick的既有注入点处理一次，随后执行该tick的正常逻辑提交，再采样Observation并计算断言。没有输入的tick不补发动作。
3. 同tick内可出现down→up、up→down（前提是此前处于按下状态）、多次pointerMove。状态校验逐事件进行，而不是按“本tick出现过该键”一律拒绝。
4. 同tick的pointerMove(A)→mouseDown→pointerMove(B)→mouseUp，必须生成位置分别为A和B的按下/释放事件；不能统一使用最后指针位置。
5. 同tick多个事件不创建额外fixed tick、不多调用一次项目FixedUpdate、不在事件间渲染。事件消费者可看到边沿；轮询最终状态的项目只能看到tick结束时的状态。
6. 因此同tick按下再释放不等于持续射击一个tick。需要持续动作时跨tick保持按钮；事件列表保证输入次序，不重新定义公共Input Mapping的Down/Pressed/Up等语义。
7. 事件送入AUI/项目的公共处理链，尊重AUI消费、焦点、捕获和按下/释放行为；不得为测试额外直调按钮动作。若真实路径本身不支持某种拖拽，不得把可表达拖拽输入写成该控件已支持拖拽。
8. Surface等待或呈现重试不得重放同一模拟tick输入。不同窗口/无窗口驱动必须保持模拟tick与呈现帧各自身份。

## 7. 校验、限额与隔离

沿用每场景最多4096个输入点、64断言、16捕获、JSON 1 MiB、两类帧各不超过36000、timeout不超过120000ms。v2每输入点1–32个事件；总事件数量自然受4096×32及JSON字节上限约束，不再增加额外全局预算协议。

校验维护pressedKeys、pressedMouseButtons及是否已有显式pointerPosition：

- 重复按下尚未释放的键/按钮拒绝；释放未按下的键/按钮拒绝。
- 在同一tick先按下再释放合法，其间顺序必须保留。
- 首次mouseDown前必须有显式pointerMove，可来自此前tick；避免依赖系统当前鼠标或隐含(0,0)。
- 没有输入点、纯pointerMove输入点均可表达；输入点内空events拒绝。纯指针移动不能被旧“至少一个键转换”校验误拒。
- 场景的声明时间线结束时，所有按键/按钮应释放；退出等提前终态的实际清理由既有宿主执行，不注入虚构尾部动作补齐成功结果。
- 源数据逐字段严格校验。错误指出schema版本、/inputs/i/events/j及具体字段，并给出允许值或当前状态，沿351首因链返回。

每次运行从隔离的脚本输入状态开始，不承接上次run的按键、鼠标位置或未完成捕获。成功、失败、超时和取消都使用已有Runner进程/会话清理；清理不触发额外项目点击、不写伪造输入事件计数。

不修改真实InputDeviceState对OS事件的既有宽容行为来实现场景严格校验；格式/时间线校验属于回放输入owner。

## 8. 坐标与窗口前提

position沿用Native回放的目标画布像素：原点左上，X向右，Y向下；不使用屏幕坐标、DPI坐标或归一化坐标。允许画布外坐标交由既有公共命中测试处理，不自动夹到边缘冒充点击；类型范围保持i32，转换沿用现有数值路径。

明确记录/说明这是synthetic engine replay。既有报告的窗口模式、实际焦点、尺寸与捕获信息继续使用，不制造第二份焦点真相。引擎输入状态可能因模拟按键变化，不能将其等同为OS窗口确已获焦。

有窗口运行不叠加用户现场键鼠；真实窗口焦点事件仍按既有生命周期处理。若失焦导致项目按策略拒绝动作，应保留实际焦点与断言结果，不自动伪造FocusChanged(true)、抢焦点或改项目暂停逻辑。需要真实OS焦点控制的资格属于后续窗口环境工作；本轮窗口验证只在已成立的前提下作对应声明。

## 9. 兼容与传输

版本划分必要性：B允许同tick同键多次合法转换，已与312的v1键状态限制不同；只增加events而沿用原schemaVersion会混淆旧合同。仅这两个输入JSON合同增加v2，不顺带升级RuntimePackage、Observation、Project SDK、工具schema或全局engineVersion。

| 消费关系 | 行为 |
| --- | --- |
| 新实现读取playtest v1 | 先按原v1严格校验，再转换为内部有序事件；keyDown数组顺序在前，keyUp数组顺序在后 |
| 新实现读取native script v1 | 保持原v1校验和旧回放顺序：keyDown→keyUp→pointerPosition；不偷偷改为鼠标优先 |
| 新实现读取v2 | 按本方案逐事件校验，完全保留events顺序 |
| 旧实现读取v2 | 明确不支持/反序列化拒绝；不得丢弃新事件后继续运行 |
| v1混入events，或v2混入旧字段 | 严格拒绝，给出相应格式建议 |

兼容适配仅发生在读取边界；内部执行最终共用有序事件到RawInputEvent路径。保留原场景sourcePath/sourceDigest及原始版本身份，不把内部转换后的数据冒充用户原文件。为旧场景重新编码、批量改项目或重算所有历史delivery不是本轮要求。

EngineRuntimeExecutionRequest已有JSON字节传输可携带更新后的场景/脚本；首选沿用该传输，不增加事件专用DLL调用或新的执行owner。需要验证完整roundtrip及实际导出消费。新场景须由匹配新Player/Engine DLL消费；旧delivery不支持v2时明确失败，不静默重建旧交付或降级丢输入。

Provider保持独立九工具及现有deliveryRef/runRef语义；普通项目build不强制新增playtest配置。
