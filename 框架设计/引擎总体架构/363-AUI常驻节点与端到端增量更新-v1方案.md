本文承接 [361 AUI R2](361-AUI表现逻辑分离与常驻节点运行时-v1方案.md)，将常驻节点、分类失效和局部消费落实到真实项目的完整更新链。保留 361 已完成能力与历史验收身份，不另建一套 UI 引擎。当前实现和安装见 [49](49-当前状态与下一步入口.md)，唯一施工入口见 [54](54-当前可自动化施工总入口.md)。

## 1. 目标与已确认选择

AUI 负责让项目描述界面、处理交互，并把变化高效地显示出来。本方案对标成熟引擎的常驻 UI 树、失效调度、布局依赖和保留绘制数据；公开使用继续保持控件引用、属性设置、事件与模板实例化的简单方式。

确认采用：**常驻节点作为属性真相，节点属性变化作为更新输入，按真实依赖传播，持续保留布局与绘制结果；Canvas、布局依赖范围、绘制缓存范围和 GPU 合批范围各司其职。**

| 研究过的路线 | 决定 | 原因 |
| --- | --- | --- |
| 按更新频率拆少量 Canvas，以 Canvas 为主要重建单位 | 作为组织和辅助优化手段 | 能隔离区域，但无法独自消除完整快照、属性扫描和布局重建 |
| 节点级分类失效，按布局依赖传播，复用绘制片段与批次 | 主方案 | 同时满足 AI 接口简单、正确依赖传播和低更新成本 |
| 每节点 Canvas，或普遍把子树缓存为离屏纹理 | 不作为默认架构 | 增加管理、内存、合成与批处理限制；离屏策略只适用于特定复杂低频界面 |

默认一个 Canvas 也必须能高效更新单节点。额外 Canvas 按坐标、排序、合成和输入组织需要创建；节点数量或屏幕面积不是唯一划分依据。普通项目作者不需要为了获得局部更新而手工拆 Canvas。

本轮正式范围包括引擎更新链收敛、旧绑定兼容、普通项目接口保持、塔防项目迁移及完整真实交付验收。GPU 共享变换是可按瓶颈选择的后端优化；Retainer 式离屏缓存、通用渲染线程重构和任意世界空间 UI 不扩入必做范围。

## 3. 成熟实现的采用与不采用

### 3.1 横向结论

| 参考体系 | 关键机制 | 采用 | 限制与不照搬部分 |
| --- | --- | --- | --- |
| Unity UGUI | `CanvasUpdateRegistry` 分布局/图形去重队列；`LayoutRebuilder` 查找布局根；Canvas 隔离批处理 | 分类调度、按频率合理分组 | Canvas 不是所有依赖的统一边界；不复制 GameObject/全局 registry 体系 |
| Unity UI Toolkit | `VersionChangeType`；动态变换数据；常驻渲染结果 | 按属性分类，局部变换与几何复用 | `GroupTransform` 可打断批次并增加 draw call，不默认逐节点使用 |
| UE Slate/UMG | `SWidget::Invalidate`、`FSlateInvalidationRoot`、widget 绘制缓存、Global Invalidation | 节点原因合并、阶段队列、快慢路径及缓存根 | CanvasPanel 是布局容器；Retainer 有额外纹理/重绘成本；不能承诺其 RenderTransform 完全免布局 |
| Godot | `Control` 分位置/尺寸变化；`CanvasItem` 保留绘制命令；Container 单独排队布局 | 平移、内容重绘和容器布局分开 | CanvasItem 不是每节点离屏纹理；最小尺寸变化仍可能向祖先传播 |
| Flutter | `parentUsesSize`、紧约束等决定 relayout boundary；repaint boundary 独立 | 按真实尺寸依赖确定布局范围，独立评估重绘隔离价值 | 隔离边界不能截断真实依赖；RepaintBoundary 不保证光栅缓存 |
| Qt Quick | 常驻 QSGNode/GPU 几何；部分 batch root 仅更新矩阵 | 持久渲染数据、必要时共享变换，合批与节点失效分离 | 分组变化本身可能重建；不复制其经验阈值，不改变透明顺序换合批 |

## 4. 目标链路与所有权

```text
AUI 源资产、主题、模板
  -> 正式构建/加载：验证、稳定索引、绑定目标与依赖信息
  -> 常驻 AuiInstance（已提交属性真相）
       <- typed setter / 控件行为 / 动画 / 可选绑定适配
  -> 唯一更新协调器：合并已知变化，按阶段产生工作集
       -> 样式与必要布局
       -> 变换、裁剪及命中索引
       -> 持久绘制片段、顺序和批次
  -> 既有 UiProjection -> Renderer -> RHI/GPU -> Present
```

| 所有者 | 持有内容 | 明确职责 |
| --- | --- | --- |
| AUI 资产/编译结果 | 不可变结构、初始属性、资源引用、可编译索引 | 作者侧真相；不保存逐帧游戏状态 |
| 常驻实例 | 有效句柄、当前属性、owner、生命周期及提交信息 | 唯一运行属性真相；任何写入须经过相同校验 |
| 共用更新协调器与布局 owner | 阶段工作集、布局树/测量缓存及有效几何版本 | 统一执行依赖更新，供 Player、Editor 和输入消费者使用 |
| UiProjection/Renderer | 派生的绘制片段、批次和有界 GPU 资源 | 不反查玩法、binding path 或源文档，不回写属性 |

当前 AuiInstance 与 C2 的相关状态须按上述职责收敛，不能新增第三份属性镜像或独立布局执行器。只读发布结果和有明确失效规则的缓存允许存在；它们不成为另一份可写真相。共享不可变结果保留跨帧读者安全，不能为避免复制而修改仍被消费者持有的数据。

## 5. 已知变化的直接传递

### 5.1 提交与合并

1. 属性事务先校验句柄 generation、类型、所有权、容量和阶段，再执行同值消除；失败不能安装半份属性。
2. 成功提交产生内部变化记录，至少可确定实例身份、结构代次、提交序号、节点 slot、属性或失效类别。正式字段名属于后续实现合同，不成为项目手写接口。
3. 一个协调器从实例收集变化并分发各阶段工作，不能让 style/layout/hit/paint 分别争抢 `drain_invalidations`。跨发布消费者使用各自的已消费版本或有界 journal cursor；不要求每个阶段都建立独立 journal。
4. 同一安全阶段内合并重复工作，祖先任务覆盖后代时去重；输入、结构事务和生命周期屏障之间保持必要顺序。不能以“只取最后状态”吞掉 down/up、交互通知或中间必须命中的几何。
5. 基础属性、绑定、控件反馈、动画覆盖和 custom 输出进入同一依赖调度；派生反馈保留其 owner，不覆盖项目基础值。

### 5.2 版本、失败和容量

- 消费者成功安装对应缓存后才能推进 cursor；失败不能把变化标为已处理。绘制与命中共同采用一致的有效几何版本。
- 初次挂载/新增消费者以一致基线和 cursor 开始；package reload、实例重建使用新身份。删除后旧句柄失效，slot 复用须换 generation，revision 溢出禁止回绕误命中。
- journal、交换缓冲、脏队列和缓存均有硬容量。落后消费者超出 journal 历史时，从当前已提交实例重建必要基线并报告原因，不能丢变化或无限保留历史。
- 重建是明确的恢复路径，不得成为正常单节点更新的默认路径。输入超预算应有序延期或明确失败，不能静默丢弃。
- 沿用 361 单根每轮帧内稳定化最多 8 轮的保护；持续非法输出不无限重入，保持最近有效几何的一致绘制/命中，首次没有有效几何时隔离故障子树并诊断。

## 6. 可选绑定与旧快照兼容

构建/挂载阶段建立 path 到类型化字段及目标 slot/property 的反向索引。项目可使用直接 setter，也可使用已有字段通知或 typed 数据源；普通项目不必生成全 UI 快照、维护 revision 或编写内部变化记录。任意 Rust 变量写入并不会自动可观察；可选绑定必须通过有明确通知语义的数据源或现有通知接口更新。

旧 `Replace` 表示绑定输入的完整替换，不表示整份 Document、布局或绘制结果必须重建：

1. 按现有协议验证字段集合、类型、fallback、binding set 与身份。
2. 与最近成功绑定值比较，通过预编译映射将真实变化转换成统一属性更新。
3. 校验及应用成功后，原子安装新的输入基线和已接受身份。失败保留最后成功状态，不得先记住新 revision，再因后续 Reuse 永远漏掉失败变化。
4. 缺字段仍按完整 Replace 的既有缺失/fallback/错误规则处理，不能擅自当作“该字段未变化”。解绑、属性所有权转移、删除节点和恢复显示有明确状态转换。
5. 普通字段变化不复制整份源文档、不清空所有 solver；结构、主题、字体和 viewport 变化另带真实原因。

完整 Replace 的传输、解码及入口比较仍随全部输入字段数 B 增长；本方案仅保证它后续的更新按变化与依赖执行。现有 [C6 UiBindingStore](361-C6-绑定字段通知与按需刷新实际合同.md)可减少字段生产，但有可见变化时 wire 仍为完整 Replace，不能把它称作已实现端到端稀疏传输。

高频更新优先使用已有 typed 属性批次；若后续实现确需新增稀疏绑定 wire，须在施工合同中独立说明 ABI/schema 版本、旧读者拒绝和迁移方式，不能静默修改旧协议。本方案不预先以新增 ABI 作为局部更新的前置条件。

## 7. 分类失效与布局依赖

| 变化 | 必须考虑的更新 | 应保留的内容 |
| --- | --- | --- |
| 同值 setter、无变化 | 必要事件/呈现提交 | 样式、测量、布局、文字、绘制和索引 |
| 布局后纯平移 | 本节点及实际受影响后代的变换、裁剪、命中、渲染数据 | 原始尺寸测量、排列、文字整形与未变绘制内容 |
| 颜色、非尺寸 paint 属性 | 相应绘制/材质数据；主题状态按声明依赖处理 | 布局及不相关字形 |
| 文本变化 | 该文字整形、段落/绘制；尺寸贡献、基线或其它父布局读取的输出变化时传播布局 | 无关文字和独立布局区域 |
| 宽高、字体、自动尺寸或布局约束变化 | 必要测量与排列，受影响祖先、兄弟和后代 | 无关布局根和有效缓存 |
| Hidden/Visible | 绘制、命中及相关样式 | 保留空间时的有效布局 |
| Collapsed/Active、插删、重排 | 生命周期、结构索引、布局、绘制顺序、命中 | 不受影响的稳定子树 |
| 主题/DPI/字体/viewport 改变 | 依赖索引所确定的范围，可扩大至全根 | 未依赖该变化的资源和缓存 |

布局根由父子尺寸依赖与约束决定。固定约束且父布局不读取内容尺寸的独立子树，可以阻断部分向上传播；自动内容尺寸、Grid/Flex 的尺寸分配、baseline 和换行依赖必须正确传播。父级约束、继承字体、transform 或 clip 改变仍可能进入子树，不能用一个“隔离”标记无条件截断。

扩展现有布局输入更新能力，使合法 rect/style/约束修改能够更新必要节点和依赖；不能以整个文档不再逐字段相等为理由清空所有 solver。结构性改变只重建受影响根/范围；真正全局资源、viewport 或无法安全复用的结构变化允许有原因的较大重建。

已有 Taffy owner、文本测量与段落缓存继续使用。custom 布局对尺寸依赖的声明必须可验证；未声明且无法推断的自定义依赖保守扩展到相关根，不能漏更新以获得漂亮计数。

## 8. 持久绘制与 GPU 合批

绘制片段使用稳定 slot/句柄关联；保留节点到片段、字形数据、绘制顺序与批次范围的索引。变化直接更新对应片段，不能先遍历全树筛选变化，再重新汇总整份命令作为正常更新方式。

节点更新粒度与 draw call 粒度分离。多个兼容节点继续形成有序 batch；沿用 B16–B18 的不可变 payload、分段顶点和真实 GPU 部分上传。插删、排序、材质、裁剪或 chunk 形状改变时，重新处理必要绘制范围，不为合批改变透明混合结果。

纯平移尽量复用局部空间的绘制内容。第一优先级是把现有变化范围贯通到投影/上传；大量共同移动的子树若仍存在显著顶点处理成本，可以采用共享变换数据。是否启用、容量与回退条件由测量决定，不把新增离屏目标或每节点 draw call 当作实现前提。

有界驻留、资源身份和已发布数据 lineage 沿用现有正确性约束。丢帧/跳版本、GPU 资源淘汰、设备重建、未知外部数据等情况下允许完整上传，但须保持可见结果正确并区分回退原因。

每个呈现帧仍需提交和绘制可见 UI。允许必要的可见批次遍历，不允许将全树字符串解析、发现变化、克隆文档或重建命令伪装成“提交开销”。

## 9. Canvas、布局根与缓存分区

- Canvas 负责坐标映射、排序/合成阶段及相关输入组织，保持现有作者心智。
- 布局根由真实尺寸依赖决定；绘制缓存默认可细到节点/片段，其分区不自动创建 Render Pass 或离屏纹理。
- 合批由实际材质、字体、裁剪与顺序兼容性决定，不得默认强制一节点一批次；不兼容时允许必要的独立批次。
- 共享不可变节点源和索引，每个 Canvas/布局根只维护自己实际需要的布局/投影状态。源树被多个 Canvas 使用时，必要的每画布几何独立存在；不得为互不相关的根重复复制整份节点数组。
- HUD、战场、模态窗可以是清晰的粗分组。进一步建立变换/缓存组须有收益证据和稳定策略，不能每帧根据瞬时指标反复拆组并组。
- Retainer 式纹理缓存仅作为将来有明确绘制瓶颈的策略；不通过降低字牌移动或交互刷新率达到本方案目标。

## 10. 输入、生命周期与扩展正确性

沿用 361 的有序事件、capture/cancel、模态与焦点、IME、控件内部反馈、Active/Visibility、模板结构事务、属性 owner 与卸载清理合同。它们不是本方案可删减的性能成本。

下一输入依赖变更后几何时，协调器先补齐相关布局/变换/命中，再处理该事件。绘制与命中使用同一有效几何与坐标转换，覆盖同帧 down/move/up、父子平移、滚动、裁剪、节点销毁与 slot 复用。

扩展的 measure/layout/paint 仍只读输入、返回受验证结果。自定义控件可请求明确类别的局部失效；普通控件使用者由 setter 自动处理。布局和绘制回调不能任意重入修改 UI，也不能通过全树轮询弥补未声明的依赖。

## 11. AI 友好的公开体验

1. 保留 schema-first 资产、稳定 ID、模板、生成式命名 View、typed 引用与普通 Rust Controller；简单界面不强制拆成多个空壳类。
2. 现有 `set_translation`、`set_text`、显隐、值与事件接口继续是常用入口；同一回调内由已有传输/事务机制合并，避免每个节点一次独立跨 DLL 调用。
3. 内部 slot、脏队列、journal、依赖传播、几何和 GPU 缓存都由引擎管理。项目不必手写这些数据，AI 不必猜测 Canvas 划分才可获得正常性能。
4. 编译/检查通过现有工具报告源文件、节点、属性、期望类型及 owner 冲突；不新增强制通用 UI DSL、第二套节点对象模型或 AI 专用渲染接口。
5. 调试时可解释“属性变化 → 失效类别 → 受影响节点/根 → 扩大原因”。源 ID 与运行 slot 有稳定映射，日常热路径不反复解析字符串生成解释。

复杂结构、虚拟列表、自定义控件和多实例能力继承 361；不以删除扩展性、退回只支持固定塔防界面的方式达标。

## 12. 工作量、诊断与容量合同

令 k 为实际变化输入数，D 为真实依赖传播范围，V 为可见绘制/提交规模，B 为旧完整快照字段数。目标是常规更新主要随 k 与 D 增长，允许必要索引维护的对数成本；可见提交/GPU 工作可随 V 增长，旧 Replace 的入口成本仍随 B 增长。不得宣称整个 UI 每帧恒定 O(1) 或严格 O(k)。

测量模式必须区分：输入生产/交换、绑定差分/属性应用、样式、测量/排列、变换/裁剪/命中、绘制/投影/合批、CPU 提交/上传及 GPU 工作。分段边界不可重复计入总耗时；记录原始逐帧对应关系，不把各段 P95 相加冒充整帧 P95。

计数至少覆盖 visited、compared、built、copied、allocated、uploaded，以及 dirty 数量、solver 重建原因、journal 回退、缓存驻留和命中索引更新量。`drawingNodesCompared` 很小不能证明没遍历全树；已跟踪的缓存分配计数也不能冒充全进程分配总数。

Off 保留功能必需紧凑状态；Summary 提供有界计数，详细节点传播原因仅在 Trace/显式诊断启用。分配测量可用专门诊断配置，需报告自身开销；不得让正常 Release 每帧输出 JSON、长字符串或文件。

施工前冻结 journal、提交缓冲、队列、缓存及扩展输出的具体容量与溢出策略，优先继承有效的 361 预算。索引和缓存随实例释放，停滞消费者不能阻止无限历史回收。高频动态内容可跳过无收益的缓存层，但不能因此重算无关静态内容。

## 13. 塔防迁移与普通项目边界

项目侧将单位 ID 映射到稳定 UI 实例/句柄，出生/销毁可采用受控创建/删除，也可使用有明确绑定、解绑与复用规则的对象池；不能串用单位身份或旧句柄。移动使用布局后 translation。血量、文字、状态与显隐按实际变化提交，保留全部真实 UI、战斗与交互。

战场表现数据集中计算，同一帧不为 x、y、glyph、hp 等每个字段重复筛选和排序。若需要排序，明确它是绘制顺序需求还是数据查找；不能因为位置排序改变就无故交换节点所代表的单位身份。

低频 HUD 可以使用已有可选绑定，与高频单位 translation 同帧发生时也不能触发全 UI prepare。商店/布阵/战场/弹窗分组服务于项目组织，不给引擎 Core 增加兵种、合成或波次语义。

引擎修改与项目迁移分别标明 owner，通过普通 Project Game SDK、Compiler/Glue 和正式导出链消费；允许正式 Player 的确定性输入脚本，不使用绕开生产调用链的测试专用入口或直接访问引擎内部来证明项目性能。

## 14. 兼容与交付

保持单一 AUI 运行实现；旧源资产通过构建/加载适配进入同一常驻实例，旧 Snapshot 只作为可选绑定输入。不能长期维持“新项目快、旧项目永远整树重建”的两套引擎。

内部变化记录默认不进入公共 schema、Serde 语义或项目 ABI。若公开数据、缓存产物或 wire 不兼容，必须独立版本化并在构建/加载时明确拒绝旧读者，不能以文档编号代替协议版本。资源与编译缓存摘要覆盖实际影响范围。

保存既有可运行包和来源身份，候选交付使用独立输出；实施、Release 资格、安装接入和真实宿主激活分别声明。源码或文档完成不等于默认 Provider 已更新，也不等于塔防已使用新候选。

## 15. 验收矩阵与性能目标

### 15.1 正确性与机制验收

| 场景 | 必须成立的结果 |
| --- | --- |
| 正常 typed / Reuse 清洁帧、同值 setter | 无字段重新生产、全树发现变化、文档克隆、非必要布局/整形/几何重建；可见提交正常 |
| 完整但同值的兼容 Replace | 允许入口传输、解码和 O(B) 比较并单列成本；下游零失效、零重建 |
| 400/1k/10k 总节点，各仅 1 个独立叶节点移动 | 资源稳定、持续可见、已预热且文本不变时，measure、reshape、solver rebuild 为零；无关节点不被更新阶段全量访问或复制；首次进入可见区所需文字准备另设正确性样本 |
| 父节点平移 | 正确更新受影响后代、clip 和 hit；计数允许随真实后代范围增长 |
| 固定布局 A/B 子树 | A 变化不触发 B 的 measure/paint；自适应父级正例必须更新必要祖先和兄弟 |
| 同 Canvas 与多 Canvas 对照 | 单 Canvas 也能局部更新；多 Canvas 不复制每根都不需要的全部节点状态 |
| Replace 与 Translation 混合 | HUD 完整输入只做入口差分；未变节点不重建；移动和文本同时正确显示 |
| 解绑、缺值、fallback、非法类型、重复身份 | 符合原协议与 owner 合同；失败不推进成功身份或安装半份结果 |
| journal 超容量、消费落后、跳版本 | 有原因的安全恢复，状态与命中不遗漏、不无限保留历史 |
| 插删、排序、dispose、slot 复用 | 无旧句柄误用；正确绘制/命中顺序；资源及订阅释放 |
| 文字、主题、DPI、字体及 viewport 改变 | 更新真实依赖；必要的大范围变化能正确执行，不靠漏更新过关 |
| 连续拖动、合成、cancel、失焦、模态与 IME | 保留既有交互语义与即时反馈，同一有效几何被绘制和命中消费 |
| GPU 常驻、部分上传与回退 | 局部更新画面正确；资源淘汰/设备重建/lineage 缺失仍能完整恢复 |

计数断言与 fresh/full 路径的结果对照共同证明正确性；不能让增量路径通过少画、漏布局、延迟输入取得低耗时。400/1k/10k 固定单变化用于观察更新成本斜率，提交与 GPU 规模成本单独报告。

### 15.2 完整游戏资格

冻结同一机器、分辨率、显示同步、硬件/驱动、包身份、输入时间线和测量边界。保留现有 120 预热 + 240 第一波脚本作历史对照；正式资格对每一关分别预热至少 120 帧，并收集至少 600 个有效交战样本帧。交战阶段判定规则在采样前冻结，保存所有原始帧和阶段标签，准备/过渡帧另报。若波次提前结束，按预先固定的继续开波或分轮脚本采集，A/B 使用相同输入，不用准备期稀释交战分布，也不事后挑选有利帧；三关分别满足样本量和性能门槛。

目标：**Windows Release、1280×720、完整约 400 节点塔防界面，真实交战 AUI CPU P95 ≤ 2 ms，完整 CPU P95 ≤ 16.67 ms。** 当前 415 节点界面应完整保留，不能为凑 400 删除内容。相同总计时口径须覆盖既有 AUI 输入/反馈区间；新增分段计时不得通过缩小范围“达到”目标。

报告 P50/P95/P99、最大帧、各阶段工作量、CPU/GPU、上传、缓存和生命周期内存；可获得时另报真实呈现间隔与输入响应，不把 CPU 时间倒数称为显示 FPS。比较前后收益必须同条件；至少提供可复现重复采样，不能仅保留最好一次。未达标必须报告首因和残余项。

真实项目验收覆盖三关、部署、合成与失败反馈、连续拖动、单位移动、暂停/继续、弹窗和重复开关界面，并由正常 SDK/Glue、实际 Engine DLL 和独立 Release 包执行。微基准、静止命中和单帧截图不能替代此资格；三关样本不可混合成一个 P95 掩盖慢关卡。
