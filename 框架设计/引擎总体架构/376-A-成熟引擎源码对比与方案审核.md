## 4. 关键调用链与采纳理由

### 4.1 网格提交与更新

Godot G1：`add_surface_from_arrays → mesh_create_surface_data_from_arrays → add_surface`，而`surface_update_vertex_region → RenderingServer::mesh_surface_update_vertex_region → emit_changed`。创建和更新是分开的；后者源码本身不重算ArrayMesh表面边界，不能把emit_changed等同于完整几何派生数据重建。

Bevy B1/B4：`Mesh::new / insert_attribute / insert_indices → Assets中的变更 → AssetEvent::Modified → extract_render_asset → prepare_assets → RenderAssets`。值得学的是主世界数据与GPU准备分离，及修改只进入相关提取链。不可照搬其在新提取后先移除旧GPU资产的策略，因为376明确要求失败时继续使用旧有效版本。

UE U1/U2：`CreateMeshSection → UpdateLocalBounds / UpdateCollision / MarkRenderStateDirty`；`UpdateMeshSection`检查相同顶点数；`FastNotifyPositionsUpdated`显式安排边界计算并更新渲染数据。376采用同样的操作区分，但不复制FDynamicMesh3的全套拓扑编辑能力。

### 4.2 必须以实现纠正旧注释

Bevy B1中仍有“新网格才自动计算Aabb，修改后手工更新”的说明；但同一参考树B2的`calculate_bounds`实际查询`AssetChanged<Mesh3d>`或`Changed<Mesh3d>`并更新已有Aabb。两者不一致。

因此审核不能只引用一段API注释。376明确采用“位置变化自动更新边界”的合同，依据是实际消费链；不再给AI增加必须记住的刷新步骤。该选择不声称所有历史Bevy版本都有同一行为。

### 4.3 异步碰撞与同目标组合替换

Godot G1/G2：`create_trimesh_shape → ConcavePolygonShape3D::set_faces → _update_shape → PhysicsServer3D::shape_set_data`。这些入口证明几何与形状分离；不能从中推出和UE相同的异步cook回执或渲染/物理原子更新保证。

UE U1：`RebuildPhysicsData → AbortPhysicsMeshAsyncCreation（旧工作）→ CreatePhysicsMeshesAsync → FinishPhysicsAsyncCook → RecreatePhysicsState`。完成结果在AsyncBodySetupQueue中查找，成功后清掉较旧项；较新的请求仍可在队列中。因此它是“采用较新可用结果”的具体实现，不能直接说成“始终只提交最后请求”。

376更保守：最新已接纳候选才允许生效；渲染与碰撞需要配套时，按我方原prepared/activate合同一起切换逻辑绑定。该差异增加的是必要的可验证合同，不新增世界或事务平台。还要区分逻辑提交与首次实际呈现，不能向AI报告尚未出现的像素结果。

### 4.4 字节存储：分层可借鉴，保证不能照抄

Bevy B5明确把asset-agnostic字节I/O与每类AssetSaver/Loader分开；B6普通write使用File::create，不能以“有AssetWriter”为由声称有运行时存档事务或崩溃保护。Godot G4/G5的safe-save分支采用平台替换/rename，值得学的是把完整临时文件准备和目标替换分开；其选项、错误和平台实现仍需逐项核对。UE U3/U4进一步说明项目定义保存信息，引擎/平台执行字节保存。

我方O8已有文件替换owner，应该复用，但源码先rename旧目标至backup，且cleanup可在新数据已提交后返回错误。这两点与376需要的运行时回执有差异，必须修改合同及原owner中的适配，不能仅换函数名就宣称可靠。

376最终仅承诺已验证平台上的单key完整替换和明确提交状态，不承诺掉电事务、数据库或多key一致性。三层概念分别是：正常读者原子可见、进程中断后的目标可见、掉电后的耐久性。只验证前两层不能授第三层。

### 5.1 已由现有架构吸收的约束

- World/Projection/native renderer各自保留原owner；新增类型不建立第二Bridge或第二资源库。
- 普通Project Rust Module和结构化资产仍是一等输入；不扩Rule IR表达任意算法。
- Compiler/Assembler/Generated Glue保持唯一制作与注册链；不让AI同步多份派生文件。
- Off/Summary/Trace沿用既有规则，详细报告不进入发布热路径。

这些是继承约束，不重复建设新治理模块。

### 5.2 不适用或明确不采纳

- UE的UObject/GC、Godot的Resource/Callable、Bevy的全量Assets/ECS API不作为我方项目ABI。
- Godot/Bevy的通用任务池不在本轮重建；其存在不能反推用户授权了通用Job平台。
- 不引入体素容器、Marching Cubes、贪心合面、区块缓存或PCG生成图；这些即使可复用也归项目。
- 不照搬Bevy软上传预算或先移除旧资源的替换策略；采用符合我方已确认合同的严格预算和失败保留旧版本。
- 不从文件write/flush或进程重启测试推断掉电耐久性，不从headless状态推断GPU显示成功。

## 6. AI优化审核

| AI使用问题 | 方案处理 | 仍由项目决定 |
| --- | --- | --- |
| 容易写错stride/offset/附件长度 | 类型化builder生成编码，入口继续严格校验，错误落到field_path | 顶点和索引算法 |

| 迟到结果覆盖新修改 | 代次、基础修订、最新已接纳候选复核 | 哪些生成结果值得提交 |
| 重试导致副作用重复 | 查询请求/Applied修订；存储CommitUnknown先核对；不自动盲重放 | 业务重试和恢复策略 |
| 需要读大量日志才能定位 | 精简code、field_path、expected/actual与按需source mapping | 项目语义观察项 |
| 每帧报告拖慢运行 | Off保留必要状态，Summary/Trace按需；无顶点JSON或全场景扫描 | 主动诊断时机 |
| 不同消费端结果不一致 | 同一SDK/RuntimePackage/Compiler链；真实DLL与独立Player验收 | 游戏内容与玩法验证 |

这些优化减少的是AI要手写和记住的机械步骤，不替项目决定游戏设计，也不增加专门的Engine Agent、新DSL或新MCP工具。
