## 1. 结果

252 已完成。编辑器现在以 `ProjectIntentWorkflow` 承接不完整、矛盾、零散和跨会话的用户表达，并把它们整理为可独立推进的 WorkItem；只有选中且 ready 的 WorkItem revision 才能进入 ChangeSetProposal、一次明确批准和既有 ProjectCandidateEntry 执行链。

```text
capture -> observe -> prepare_change -> authorize -> dispatch
IntentEvent：append-only、schema-versioned、command-id 幂等
WorkItem：Park / Resume / Reopen / Merge / Split / Cancel 与 lineage
Diagnosis：只读 evidence；instrumentation 必须进入 ChangeSet
Approval：绑定 proposal、selected revision、target identity、base、风险和费用
ProductionRun：复用 ProjectCandidateEntry；同一 target 只有一条 active mutation lane
ProjectGoalSnapshot：可丢弃派生视图，不再是全局 FeatureSpec 前门
```

Launcher 支持无项目时先保存本地 Intent 草稿，正式 CreateProject 成功后再按 project identity、canonical root、initial digest 和 creation receipt 接管 journal。已有项目从 `Library/ProjectIntent` 恢复自己的 journal；Intent、Diagnosis、Proposal 和 Run 不进入 RuntimePackage。

产品入口包含 Launcher `Create with AI`、EditorSession attach/load、Project Intent Dock、Change Review 与 Production view model。严格 imported Codex normalization/change-plan Adapter 只导入结构化候选，不自行授权；Candidate/Apply/rollback 真相仍属于 250 已有模块。

E2E 兼容修复集中在 `project_e2e_gate`：临时样例不继承其它项目的私有 journal；fake Provider 与 lifecycle loopback accept 有 5 秒上限；accepted socket 恢复 blocking read；需要 Provider 的场景先附着唯一临时项目，再发起请求。

## 4. 无效运行与诊断

第一次完整 workspace 尝试异常等待，没有形成有效权威结果。根因是 252 把“无项目自然语言输入”改为仅保存本地 Intent 草稿、不启动 Provider，而旧 lifecycle fixture 仍让 loopback server 无限等待连接。修复为先创建并附着唯一临时项目，并给 fake server accept 增加 5 秒上限；accepted stream 改回 blocking read，避免 Windows `WouldBlock`。修复后先跑累计失败集和受影响域，再重跑权威矩阵。

第一次 all-features 在编译阶段以 `rustc-LLVM ERROR: no space on device` / OS error 112 退出，耗时 117.583 秒，未进入测试，因此记为环境无效而不是代码失败。审计确认 G 盘为 0 字节可用，且 `G:\gameEngin-targets\252\debug\incremental` 占 11.974 GiB；只删除该专用 target 的可再生 incremental 后释放约 10.97 GiB，最终矩阵通过。另有一次在仓库根而非 `rust` workspace 执行的 0.173 秒命令因找不到 `Cargo.toml` 立即退出，同样不计权威 run。
