# 371 3D方案、执行成本与施工过程复审

日期：2026-10-19。请求：重新审核为什么施工时间长、性能仍超预算，区分设计、施工和未完成工作。本报告是审核结论，不是新方案批准、施工激活或完成记录。原371方案B、§0.25、49/54的功能/性能/安装状态保持。

## 1. 结论

三种因素同时存在，但承担不同责任：

| 问题 | 审核判断 | 证据强度 |
| --- | --- | --- |
| 设计有问题吗 | 原持久资源、实例/view分层方向合理；执行成本、失效粒度和跨层消费合同细化得太晚，早期功能贯通不足以证明大型场景执行效率 | 原方案与后续整改合同可直接对照 |
| 施工有问题吗 | 有。既有原则曾只在局部兑现；发生过实际复杂度错误、过早终验与重复构建，部分局部修改没有整帧收益 | 原始失败、旧DLL反事实、确定性红例、timing收据直接证明 |
| 施工没做完吗 | 是。当前CPU渲染执行链效率确实未完成；S3–S5及部分实际配方也未完成，但后者并不解释当前52ms渲染提交成本 | 当前源码、最新运行与延期登记一致 |

没有证据要求推翻整个方案B或立即更换渲染后端；也不能承诺继续增加局部缓存就必然达标。应先在当前最终源码上确定剩余成本，再收敛同一条执行链。设计与施工之间不能给出可信的百分比分摊。

## 3. 运行慢的实际位置

最新一次原规模12帧、4预热/8采样无probe结果：

| 项目 | 当前结果 |
| --- | ---: |
| CPU mean / P95 | 53.3039 / 61.6049ms |
| renderSubmit mean | 52.0240ms |
| update mean | 1.2510ms |
| GPU mean / P95 | 9.9647 / 10.7622ms |
| CPU/GPU冻结门槛 | P95≤13.3ms，P99≤16.67ms |

约97.6%的CPU帧成本位于渲染提交链。它包括生产准备、图、后端准备和提交，并非只有GPU draw调用。CPU已排除present wait，不能把这52ms解释为显示等待、测试未做完或缺少物理/动画。

GPU短窗数值在预算内，CPU显著失败。8样本不能授持续P95/P99资格、实际显示FPS或可重复因果收益；没有用CPU倒数推导显示FPS。依据：[10记录:45–56](10-动态多视图与native参数消费.md)、[31-comparison.json](../../../../.artifacts/371/s2-dynamic-20261019/31-comparison.json)。

历史短窗CPU均值约280.19→158.61→110.50→75.38→53.09ms，说明已有实质改进；中间04、06及最新10均未证明整帧收益。最新53.09→53.30ms应报告“没有证明新的性能改善”，不把0.22ms短窗差异当作确定退化机制。不同源的轨迹不能拆成每项优化的精确收益。

S1静态配方已经有历史通过证据：BM03/BM02各三轮、每轮3661样本，六轮最差CPU P95/P99为12.1931/15.0395ms。它使用10000 unique mesh/256材质/64纹理；当前S2是10000实例/100驻留mesh/128材质/96张2k BC3 mip纹理/10M三角形/145灯/4级联+8spot/运动相机。不能将两个配方合成“一直未达标”，也不能用旧静态通过授予当前光照阴影资格。见[静态记录](../2026-10-13-371-S1-Static-CPU-Continuation/00-总览.md)。

## 4. 设计与实际实现的差别

原[371-B](../../371-B-基础贯通设计.md)第89、117、150行已分别要求稳定关联、相机移动不重准备mesh/material、稳定图只patch帧参数；[总方案](../../371-大型游戏级AI原生3D平台-方案B-v1方案.md)第185行已区分长期资源、dirty实例和每帧view。问题不是这些概念完全缺失，而是没有及早对Production→Graph→RHI→native每个消费者约束实际扫描、分配、校验和失效次数。

[整链整改方案](../../371-S2-整条渲染执行链整改方案.md)第11行记录过真实落差：共享表/batch命令已接通，但多层仍检查selection、native仍全展开后才减少上传、完整plan复用包含动态view。后来常驻工作集和准备证明合同已经修复其中一部分；本次不能沿用旧诊断把它们重新列成缺失。

当前源码复核：

| 路径 | 当前实际工作 | 分类与边界 |
| --- | --- | --- |
| `render_geometry/commands.rs:1707`、`proof.rs:48`、`graph.rs:265`、`rhi_command_plan.rs:343`、`engine_rhi.rs:100` | 同一不可变batch成功证明沿消费者传递，命中直接返回 | 已实现。当前inline路径不能再说四层都完整扫描tail；线程切换/容量清除可miss属于已声明边界 |
| `render_geometry.rs:816/868`、`commands.rs:1672/1682`、`shadow/planning.rs:573` | 每view候选扫描、当前深度、排序、组批和新selection验证 | 实际动态工作。相机/阴影/透明顺序需要更新，不能把所有O(view×候选)都判为错误；最终各段占比未知 |
| `wgpu_backend/real/geometry.rs:2530`、`geometry/parameters.rs:269/281/334` | 全部选中项展开临时tuple Vec，再处理instance、view映射，最后组索引 | 原owner内仍有实现收敛空间。纯派生缓存、dirty上传已生效，但不等于CPU只处理dirty |
| `geometry/parameters.rs:79/92/102` | 分配active位图/keys，遍历retained slots，比较真实已上传content | slot/content/重试正确性必须保留；临时集合和多遍处理不是产品语义本身 |
| `wgpu_backend/real/geometry.rs:1899/1930/1938` | 完整plan快路包含动态view全等，miss后重走准备和全plan检查 | 稳定执行结构与动态参数分离尚未覆盖全部准备；但2665处可按完整recipe恢复bundle，不能声称所有GPU命令必重录 |
| `render_geometry/production.rs:931/984`、`commands.rs:1888` | 实例集合未变时复用完整表/worksets；实例内容变化可能使新表和phase缓存失效 | 一般动态场景的扩展边界。当前K1主要相机运动，不能据此解释全部现有超预算 |

上述源码路径均相对`rust/crates/engine_runtime/src/`。另需区分两类验证：新batch动态tail验证，与native全plan跨batch的`(view,id)`唯一性不是同一事实；不能为提速直接删后者。实时资源准入、generation、旧packet及GPU完成点退休继续需要保留。

本审核支持先完成既有owner内临时数据/遍历/索引消费的收敛。若未来要跨动态plan复用稳定拓扑或准入事实，需先明确失效依赖与寿命证明；目前没有证据要求新建资源owner、BVH或GPU-driven管线。也尚不能从静态代码宣称任何一项能节省多少毫秒。

## 5. 与成熟引擎对照

本次重新读取本地源码，采用机制对照，不授同机性能结论：

- UE：`PrimitiveSceneInfo.cpp:638`在支持缓存的pass建立命令；`SceneVisibility.cpp:1286`的动态可见阶段引用缓存命令，不可缓存时才发动态构造请求。稳定命令和本帧可见工作分开。
- Unity：`BatchRendererGroup.bindings.cs:281/436`公开合同将mesh/material/batch与visibleOffset/count、drawCommands与visibleInstances分开。C# binding不足以证明完整native内部算法。
- Bevy：`render_phase/mod.rs:161/1309`保留entity→bin并清理本帧临时batch；`batching/no_gpu_preprocessing.rs:119`的CPU路径仍逐实体生成buffer数据，成熟引擎也不是全链O(dirty)。
- Godot：`renderer_scene_cull.cpp:992/4362`跳过不变transform并消费dirty队列，动态可见性和绘制列表仍有本帧成本。

源码根和版本限制见[371-C](../../371-C-成熟引擎源码依据.md)：UE5.8-dev、Unity公开C#6000.6.0a7、Bevy0.20-dev、Godot4.8-dev，本地没有可追溯commit。此次官方网页读取工具连接失败，未将未读网页当新证据。没有Unity/UE同机同场景对照，不能说相同配方在它们上必然满足13.3ms。

60Hz及13.3ms工作预算属于正常实时游戏目标；10000实例/10M三角形/多阴影是具体且较重的负载，其可行性还依赖实际可见工作量、材质和硬件。冻结主机为i5-12490F/RTX3070/约16GiB RAM，见[预算实际合同](../../371-S0-B-规模配方与测量预算实际合同.md)。当前有明确CPU执行与返工证据，不能先把超预算解释为标准不合理；也不能把设计目标当成已被外部引擎证明的承诺。

明确的施工问题：

1. 08阶段在产品实现尚未收敛时开始整套consumer构建，用985.14秒；随后补索引消费又付出11阶段621.76秒。不能说两次全部可省，但过早终验使证据立即失效是可避免成本。
2. 新receiver使用`iter().nth(index)`造成平方级行投影：32个selected投影528行。新DLL CPU升至422.6873ms，同环境旧DLL为55.4920ms，诊断receiver为362.2697ms。直接slice get修复后回到53.30ms。这是本轮引入的实现错误，不是预算或机器的必然问题。
3. 原测试只覆盖局部比较/派生次数，没有提前覆盖新索引实现的真实行访问复杂度。大量正确性测试通过不代表复杂度和原规模性能已合格。
4. 早期将S1全资格当S2功能前置，已由[371-G第9行](../../371-G-S1功能准入与延期资格审核.md)纠正。当前不应再把延期观测和正式三轮加回材质/灯光开发前置。

失败及修复原证据见[10记录](10-动态多视图与native参数消费.md)、[24-red.log](../../../../.artifacts/371/s2-dynamic-20261019/24-red.log)、[25-green.log](../../../../.artifacts/371/s2-dynamic-20261019/25-green.log)。本轮Compiler/Cook、BM03、全workspace及正式三轮均为0次；现在主要准备成本是受影响Rust消费者/Release DLL的多次编译链接，不能继续沿用“盲跑完整Compiler”解释这轮。分页/内存低点尚无因果证据，不归责宿主环境。

## 8. 下一步建议与复审条件

保持同一§0.25整块，先用一次有界诊断补齐最终源的互斥成本区间和实际工作量。记录Production/Graph/native及未覆盖余量，标清嵌套；同时计数候选/可见项、动态tail、临时数组、slot查询、实际批次/录制。采样输出必须在预设容量内，不再靠截断日志推测。

实施选择由该结果决定：重复物化/集合/索引处理占主要成本时，在现有owner内合并消费、减少临时分配；必要动态选择/排序本身已主导时，先具体评审算法和稳定拓扑失效边界。现阶段不先决定增加缓存、改GPU-driven或重写框架。

一组能覆盖主要剩余成本的修改一起收敛，再做一次受影响终验和一次无probe原规模反馈。最小红例必须计数实际底层工作，并包含多个规模点；不能只断言某个上层函数少调用一次。记录局部正确性与整帧收益为两个结果，某项没有整帧收益时复审假设，不再自动包装成下一整块。

仅在短反馈具备预算准入后运行必要持续窗口；完整阶段完成仍需原性能门槛、真实配方和正确性证据。正式三轮、全内存、OS仪器等继续依原登记处理。本审核没有新增批准的架构边界，也没有改变已批准合同的继续权限。
