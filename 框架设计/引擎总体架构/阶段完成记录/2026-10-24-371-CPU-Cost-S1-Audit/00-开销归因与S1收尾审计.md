# 本引擎 CPU 开销与 S1 未收尾原因

2026-10-24，用户要求在Godot基线研究后，分析本引擎开销，并解释S1是否仅受性能阻塞。本次为证据与源码分析，复用已有基线、追加一次既有DLL调用栈诊断；没有修改产品源码、构建、Cook、导出、安装或调整预算，也没有将任何S1出口改成完成。

证据根：`.artifacts/371/cpu-cost-review-20261024-1514`；机器可读结果`02-cost-analysis.json`，收尾`03-closeout.json`。此前Godot结论见[首轮波动研究](../2026-10-24-371-Godot-K1-CPU/01-Godot首轮波动与缓存对照.md)。

## 一、当前能确定的开销来源

**之前约30 ms的已测DLL主要花在渲染提交链，包含大量CPU端几何选择、命令构建与原生资源准备；不是只由玩法更新、UI或显式Present等待造成。资源缓存已经在工作，但没有消除万对象规模下的逐帧管理成本。**

这里的“已测DLL”为stage60，SHA256 `227cdbbb4d3867ea45b3888f8474f954823a8b2b2d6eb91468e72d7c3af5c70d`；Game SHA256 `a1b1bc8ee3ae37bda68edb80f6ebd05accce0bbfe0cd3dbf35d45c38c7ea13c6`。直接消费原BM03 1×K1包，与前次Godot对照使用的引擎身份相同。

### 1. 粗分段已经足够排出优先级

原`.artifacts/371/cpu-godot-k1-20261024-0603/08-engine-summary-player.json`为无新探针的720帧运行，120预热+600样本：

| 范围 | 均值 ms | P95 ms | 含义 |
| --- | ---: | ---: | --- |
| 扣除acquire/present等待的CPU关键路径 | 27.2732 | 29.7849 | 应用经过时间，仍可包含同步等待 |
| renderSubmit | 25.7389 | 28.2694 | CPU准备、图/RHI、原生资源准备及提交，不是单个queue.submit调用 |
| update | 1.2519 | 1.3090 | 当前场景更新路径 |
| AUI CPU | 0.0184 | 0.0194 | UI计时，可能嵌在更新/帧路径内 |
| acquire/present显式等待 | 0.2147 | 0.2425 | 单独记录，已从第一行扣除 |

renderSubmit均值占第一行均值约94.37%。各P95不相加，嵌套栏不相加。之前32.1387 ms、后来Trace31.1879 ms与Summary29.7849 ms都保留对应运行身份；相同源码下的不同运行数值不是优化收益。

`runtime_player_winit/src/real_window.rs`中，render计时从`render_thread_for_target_with_runtime_resources_and_presentation()`前开始，经过`geometry_texture_upload.prepare()`、`prepare_surface_resources()`，再加实际native execute span；acquire/present另计。因此不能把25.74 ms称为“GPU提交API阻塞25.74 ms”。

### 2. 大资源没有在每个采样帧重传

原Trace600样本分组：

| 几何动态上传计数 | 帧数 | renderSubmit均值 ms | renderSubmit P95 ms |
| --- | ---: | ---: | ---: |
| 176 bytes | 567 | 26.4455 | 29.3871 |
| 高于176 bytes，约120–151 KB | 33 | 27.2923 | 32.4456 |

采样期纹理tracked为1,073,741,824 bytes，几何physical backing为312,000,000 bytes，pendingAssetOperations为0。此计数不是全部驱动传输，但足以说明：**94.5%的采样帧只有极少几何动态上传，仍付出约26 ms提交链时间，不能把主要开销解释为反复上传1 GiB纹理或整套网格。** 也不能反过来说完全没有上传、没有资源检查或所有缓存都失效。

### 3. 这次新采样捕获了真实渲染路径

复用原Game/DLL和精确PDB（SHA `db3c3ac36e3aa07adb7956d1199ac15828ce670adbd7d1302fb5b469c293b260`），使用既有run-owned Windows SDK/DbgHelp采样器，只采本次启动并核对exe路径的PID25504。没有编译新采样器或改引擎。

单次运行1200帧，46.218秒、截图非零、exit0。共26个栈快照，工具总wall2.529秒。人工复核后，000–008为初始加载/首次几何发布/事件等待，不当作稳态；009–025共17个为渲染路径，未精确绑定120帧预热边界。自动触发器宽泛的`render_path_candidate`不等于稳态证明。

| 反复出现的栈路径 | 渲染路径快照数 | 可支持的判断 |
| --- | ---: | --- |
| `OrderedCompactView::finish` / `GeometryBatch::new/validate_selection` | 4 | 可见实例到批次/命令的物化与校验有实际CPU工作 |
| `Preparation::resolve` / `Bindings::include` / `RetainedDrawCommand::requirements` | 4 | 原生依赖事实消费和集合组织仍在执行 |
| `Templates::resolve_with_current/prepare` | 3 | 模板命中后检查当前原生对象、组织本次工作集仍有成本 |
| RenderGraph验证/编译、RendererFeatureBuilder | 2 | 图与RHI准备是实际渲染路径的一部分 |
| `RenderResourceManager::native_leases_valid` | 1 | 当前租约有效性检查仍在实际路径上 |
| `select_color`下的OS线程join | 1 | 存在并行选择的汇合点；不是已证明死锁或主要等待来源 |
| `Recipe::record` → RenderBundleEncoder::draw_indexed → Vec增长 | 1 | 至少该时刻重新编码了bundle；不能称每帧都重录 |
| 其它渲染路径 | 1 | 保留原栈，不强行归属 |

命中次数不是耗时百分比，也不能据此把25.74 ms精确分成几个函数的毫秒。优化二进制存在内联/符号折叠，一些邻近符号不能作精确叶函数定位。所有主线程采样成功、恢复计数正常，匹配的引擎PDB未失配；3个非主线程快照error87保留为不可用，不据此推断worker异常。

同一主线程在12.703–22.406秒窗口内，墙钟9.703秒、GetThreadTimes实际CPU9.234375秒，约0.952 CPU秒/墙钟秒。说明该定位窗有大量主线程实际执行工作，不能将全部成本推给GPU等待。GetThreadTimes记录线程在user/kernel模式执行的CPU时间，区别于渲染span经过时间。

**本次43/43竞争快照存在其他任务的编译进程，且采样会短暂停顿目标线程。** 本次诊断P95 32.1535 ms仅原样保留，不当成新性能基准、净变化或正式资格；不能由此计算编译竞争影响。没有停止其他任务。前次无所筛选竞争进程的约30 ms基线仍是开销比较依据。

### 4. 源码解释：为什么驻留后还忙

以下是现有路径，均有源码和实际栈支持，不是新设架构：

1. `ProductionGeometrySnapshot::build`/几何选择处理当前视图，可见性、深度顺序、batch边界与输出描述会变化；独立网格数量高时，输出批次数无法仅靠材质共享大幅缩小。`OrderedCompactView::finish`会按选中项构造batch并验证选择。
2. 几何输出还经过append-to-graph、图声明验证/编译及RHI计划。已有共享列表和成功事实复用，并非完全从零，但视图/选择变化仍产生当前帧工作。
3. `prepare_geometry_plan_for_extent()`的整计划快路要求command backing或完整命令比较匹配，以及当前资源条件匹配。相机/视图、顺序或可见集变化会使整计划值发生变化，进入更完整准备的可能性增加；本轮没有给出精确快路miss计数，不能称每帧必然失效。
4. 完整native准备沿命令扫描，调用视图/资源验证，构造依赖集合与`requirements_by_command`，再完成准入、参数、模板和工作集发布。即使纹理和网格已驻留，这些CPU工作并不自动消失。
5. 历史stage60的`Templates::prepare()`每次建立call-local去重表、遍历命令与facts、检查当前对象，再形成aligned/current列表。阶段51已消除密集网格逐mesh树点查，不能再次把同一树查询当成未修缺陷；新的栈定位指向其剩余消费成本。
6. `encode_geometry_draws()`已有bundle复用；ready不可直接消费时会捕获recipe并比较，不匹配才重新record。相机移动不是每帧重录的充分证据，必须区分参数改变、可见集/顺序改变、物理绑定改变，以及弱引用过期造成的失效。本轮只证明出现过重录。

`geometry.rs`、`geometry/encoding.rs`、`render_geometry.rs`、`render_geometry/commands.rs`、`render_geometry/production.rs`与stage60清单SHA相同；历史native_template从保留ZIP按字节提取后与stage60 SHA相同。当前native_template等文件已有后续修改，不把它们假定为该DLL源码。

此前阶段51探针的资源准备约13.697 ms、几何约5.999 ms、renderer约2.421 ms/native执行约3.980 ms；另一次探针native准备约15.670 ms，内部scan约7.138、templates约5.802 ms。它们来自不同临时DLL，且部分受竞争、包含嵌套span、早于密集当前表修复，只用作历史排序参考，**不相加，不冒充stage60或最新源码各函数的当前耗时**。

### 5. 可以怎样处理，哪些尚不能断言

优先沿已有owner，把静态几何/材质事实和当前视图选择、当前资源代际/租约检查的消费成本分清；先减去不随本帧实际变化而需要重复物化的工作，再细分原生模板/依赖准备与bundle失效原因。需要保留真实当前代际、资源退休、顺序、失败首因和错误拒绝，不能用永久“曾经成功”标记跳过安全条件。

此时没有证据要求重写渲染器、换语言、削减网格或增大图形预算。也未证明某一个新cache能回收全部差距。报告关闭不会自动启动上述产品修改。

## 二、S1为什么仍未收尾

**不仅是性能问题。六项原出口同时含实际产品/工具问题、完整组合验证缺口、可访问内存计量缺口及正式资格。即使把CPU降到13.3 ms，其他项仍须分别核销。**

本表依据最近`62-s1-exit-audit.json`、阶段57–66完成记录及371-A/371-G，不新增出口、不把旧失败冒称当前重新复现。

| 原出口 | 当前问题 | 性质与关闭条件 |
| --- | --- | --- |
| X1 CPU与BM01高dirty | 已测1×K1 CPU P95约29.8–32.1 ms，13.3 ms目标未达；当前BM01高dirty完整资格待补 | 已知性能不达标；先收敛真实owner残余，再做同身份受影响规模反馈与正式验收 |
| X2 故障与生命周期组合 | F04已有worker、不同mesh/material、cell卸载、关闭，但GPU实际同时在途仅1；延迟3帧/允许最大lag完整组合未证明。F05受控lost、新设备像素、迟到回调与恢复期WAV取消子例已过，完整resize/minimize/restore与剩余F11/F12组合未闭合 | 正确性/可靠性证据缺口，不能全部写成已知崩溃；需原配方实际消费者和完整组合，不重做已有效子例 |
| X3 容量与压力 | K0/K1×1/1.5/2倍率完整当前压力、轨迹、耗尽与正式轮次未完成；历史2×超载和有界超时保留。后续一次2×仅1请求帧成功，不等于持续压力通过 | 容量与稳定性仍未资格，兼有历史实际失败；当前完整负载能否通过仍需验证 |
| X4 内存backing归属 | 资产原始数据寿命已修、现有1×运行private约3.21 GiB在6 GiB内；worker/channel、graph/plan/scratch、部分parser/report容量仍未全接，std/allocator/driver另有不可见边界 | 主要是内存覆盖/计量及全规模资格缺口；不是说当前1×仍有旧1.5×6.43 GiB超标，也不能用进程总量代替所有owner归属 |
| X5 当前工具链交付 | 最近两次inspect/check通过，真实Compiler build_engine_player都碰到原300秒超时；没有启动Player或生成该次合格新交付 | 实际构建/交付问题，发生在Player前；不是游戏运行FPS失败。旧16帧三截图仅证明旧工具产物，不能冒充最新交付 |
| X6 正式运行、流式和显示 | 720帧短窗未覆盖正式三独立进程/长窗、完整K1轨迹、流式stall/reserve、10分钟/20轮生命周期及相应GPU/内存覆盖；OS显示链历史ETW access_denied/startError5仍无通过证据 | 尚未完成的正式验收与仪器限制；不是已证明应用Present坏了，不能拿应用截图/Present替代OS显示 |

原正式窗口保持：K0预热600帧，≥3600 Presents且≥60秒，3独立进程；非K0预热600/reset后≥120秒/完整轨迹/≥7200 ticks及PC Presents，3进程；流式至少10分钟×3；生命周期20轮并最终继续10分钟。原预算CPU/GPU P95≤13.3 ms、P99≤16.67 ms，进程6 GiB、图形4 GiB、系统available≥4.5 GiB。不能把600采样帧换算为这些资格。

Android、world/sim及371-G已批准延期的维度保持延期，不为这次Windows分析恢复施工；i9/4090短窗不替代原设备合同。缺仪器不应阻断其它可验证维度，但完整声明不得把unavailable改成passed。

## 三、为什么小块完成很多，总S1仍拖着

1. **此前有明确批准的依赖调整。** 2026-10-15的371-G允许按下游真实功能依赖继续S2，而将全内存观测、完整压力、正式轮次与OS显示单列延期；它明确要求S1仍保持partial。故后续材质/灯光等开发完成，不会自动关闭原S1。
2. **局部完成不等于六项总出口。** 例如F05某个红绿子例、报告容量接入、减少一类树查询都是真实工作，但每个只覆盖总出口的一部分。记录必须保留这种区别。
3. **性能诊断和交付反馈效率也有问题。** 历史多次不同DLL短窗受其他构建干扰，旧栈采样14–30秒全落在初始化，工具又连续在进入Player前超时；这些记录本身不能定位当前稳态开销或形成新交付。这个判断来自记录，不把全部时间归于指标严格或测试必要性。
4. **源码继续集成，验收身份不一致。** stage60的916条记录输入中至少15条已变；旧清单不含所有vendor源，实际变化范围不能只用15概括。新的内存回收补丁、源码测试、旧K1性能与旧工具交付分属不同身份，不能拼成“同一最终版本全部通过”。

因此，问题既有产品残余，也有缺测和推进方式。后续应保持原六项表，按证据真正减少剩余项，而不是继续把每个子步骤都称为整块收尾。

## 四、推荐接续顺序

先处理X1渲染准备这条主成本链：使用现有prepared/retained/lease owner，量化当前视图命令物化、native依赖与模板检查；局部因果修复后只验证直接影响面。X5另在原Artifact builder隔离构建缓存/300秒超时的真实原因，避免再盲跑整包。X2/X3按原缺失组合核销，复用有效子例；X4只接已登记的可访问backing，不扩大成无限驱动仪器工程。最后固定一份最终产物，完成所需正式轮次并逐项结账，OS和延期平台如实独立报告。

当前最新源码尚无同一原K1的新基准，因此不宣布本轮发现已经解决、最新源码必然仍为32 ms、或已能完成S1。分析完成，产品优化和总收尾仍未完成。

## 五、验证与收尾

`analyze_costs.py`核对600样本、分组统计、17渲染路径栈的人工分类、主线程实际CPU差分、匹配二进制/PDB、6处源码证明及当前记录输入漂移。所有采样器返回0，Player1200帧/截图/exit0、PID已结束；没有新构建/导出，没有结束其他任务、改预算或安装。准备/源码快照的换行差异按ZIP原字节纠正，分析断言的首红留在工具记录；没有因此重跑Player。

线程CPU语义使用Microsoft官方`GetThreadTimes`说明：`https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadtimes`。官方说明支持CPU时间的含义，不为本地热点比例背书。
