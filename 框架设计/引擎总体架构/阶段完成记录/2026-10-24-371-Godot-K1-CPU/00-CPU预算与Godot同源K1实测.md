# 371：CPU 预算复核与 Godot 1×K1 实测

后续首轮波动研究见[Godot首轮波动与缓存对照](01-Godot首轮波动与缓存对照.md)：同一exe追加七轮，空应用缓存两次视口CPU P95为8.170/8.459 ms，无所筛选竞争进程的三次为7.282–7.814 ms；后两轮更接近可重复稳态。历史首轮原因尚未唯一定位，驱动冷态未隔离。本页原三轮数值保持历史身份。

2026-10-24。用户要求复核“CPU P95 32.14 ms”标准并实测 Godot。本次仅做对照诊断，没有修改引擎产品源码、预算、安装或游戏 V0.0.5；S1/371 仍 partial。证据根 `.artifacts/371/cpu-godot-k1-20261024-0603`，结构化数据见 `09-comparison.json`。

## 预算解释

现行 CPU P95≤13.3 ms、P99≤16.67 ms 来自 [371-A §5](../../371-A-规模基准与资格矩阵.md)。这是项目主档的工程约定，并非所有引擎的通用标准。按 60 FPS 的 16.667 ms 帧预算理解，13.3 ms 约预留 20% 余量；这个比例是解释预算的工程判断，不是新增验收合同。

P95 表示至少 95% 的采样帧不超过该值；不能把 P95 的倒数当作平均 FPS。原 32.1387 ms 是扣除 acquire/present 等待的应用 CPU 关键路径墙钟时间，不是进程线程实际执行 CPU 指令时间，仍可能包含 worker、驱动和其它同步等待。

## 输入与方法

复用原 32.14 ms 对应的 stage60 Release：Game SHA a1b1bc8e…、DLL 227cdbbb…，原 1×K1 RuntimePackage。没有消费随后 B 路的新源码，也没有重建引擎。原硬件 RTX4090、Vulkan、窗口 1765×993、关闭 vsync、720 帧、120 预热＋600 采样。

Godot 为本机 4.7.1 stable official a13da4feb 的 Release 导出，editor/debug feature 均 false，Forward+ / Vulkan。10000 个独立 ArrayMesh / MeshInstance3D、600 万顶点、1000 万三角形、256 材质、64 张 2048² RGBA8 无压缩无 mip 纹理；没有合并网格或使用 MultiMesh。K1 原布局和透视相机保留。

10,000 个 mesh 源文件与先前转换输入逐一比较 SHA，确认字节相同后复用转换结果，并重写当前 K1 位置及材质索引；256 材质和64纹理另外核对。10320 个源文件校验记录在 `02-input-audit.json`。原 1.5× 转换器的材质索引不能直接沿用；初次准备错误断言已修正，未作为运行结果。

先运行一次有界 Trace，导出每帧 tickPair/float32 alpha，再根据原模块轨迹重建 Godot 的 720 个呈现相机姿态。姿态经过不同浮点运算，不宣称矩阵逐位相同。截图已查看：几何布局/视角对应，背景和颜色管理存在差异，未授逐像素等价。

三轮 Godot 主对照显式关闭实例裁剪，**每个采样帧实测 10000 draws / 1000 万 primitives**，防止用减少绘制量解释加速。另跑一轮默认裁剪作校核，实际 draw 范围 9993–10000，均值9995.945；本轨迹默认裁剪并未大幅减少工作。各 GPU 进程串行，采样器记录的 Cargo/rustc/link/Game 竞争快照均为空；不能因此声称所有系统/桌面/驱动活动受控。

## 结果

以下 CPU 列是 Godot 官方 viewport CPU 计时；不含整个应用主循环。帧间隔列为连续 frame_post_draw 之间的墙钟间隔，包含等待，不能称为纯 CPU。GPU 为视口 timestamp；本轮不授完整 GPU/显示资格。单位 ms，CPU及帧间隔列为 mean / P95 / P99。

| 运行 | Godot 视口 CPU | 应用帧间隔 | GPU P95 |
| --- | --- | --- | --- |
| Godot 1（全提交） | 14.761 / 24.925 / 29.046 | 22.855 / 38.883 / 45.568 | 6.823 |
| Godot 2（全提交） | 6.200 / 7.512 / 8.265 | 10.040 / 11.843 / 12.617 | 3.823 |
| Godot 3（全提交） | 7.060 / 8.690 / 9.179 | 11.280 / 13.278 / 13.872 | 4.727 |

默认裁剪一轮：视口 CPU P95 7.809 ms，应用帧间隔 P95 12.126 ms。该轮是裁剪核对，不替代三轮全提交。

本引擎 Trace：CPU mean/P95/P99 = 28.0227/31.1879/35.0097 ms；renderSubmit P95 29.5504 ms；应用采样间隔 P95 31.6526 ms。Godot 三轮使用这次 Trace 的同一相机序列。

Godot 后追加一次原 Summary 策略的本引擎控制运行，区分 Trace 与当前机器状态：CPU mean/P95/P99 = 27.2732/29.7849/31.6185 ms；renderSubmit P95 28.2694 ms。它沿自己的真实时钟，终 tick1201，Trace 为1229，不冒称逐帧相机完全相同。原 32.1387 ms 保留原身份；本轮没有源码改动，不能把数值差异称为优化收益。

首轮 Godot P95 明显较高，不能删掉或把后两轮包装成无条件稳定结果。缓存、驱动和调度原因未隔离，120 帧预热不足以保证消除跨轮差异。

## 结论与下一步

13.3 ms 可以继续作为 60 FPS 主档的工程目标；本轮没有依据放宽预算。Godot 在同源同数量且同相机回放的后两轮，应用帧间隔 P95 为 11.843 / 13.278 ms，说明该负载具备进入 60 FPS 帧预算的实测参照；首轮 38.883 ms 也说明不能只凭一轮宣称持续稳定。

本引擎本轮 CPU P95 29.7849–31.1879 ms，仍明显超出当前目标。Godot 视口 CPU 范围窄于本引擎应用关键路径，**不得据此说本引擎 CPU 比 Godot 慢固定几倍**。更接近共同口径的应用侧帧间隔也不是 OS 实际显示证据。截图时序、GPU布局、生产图、内存/资源退休机制及内部同步仍不同。

下一轮优化应优先分解当前 renderSubmit（Summary 均值25.739 ms）的 CPU 准备、编码和同步等待，再选择实际残余；不能将这 25.739 ms 全称为 CPU 计算，或仅凭 Godot 对照就指定重写渲染器/增加缓存。原 S1 长窗口、完整轮次、稳定资源和显示出口继续保留。
